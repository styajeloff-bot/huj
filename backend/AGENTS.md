# AGENTS.md — бэкенд

FastAPI-шлюз и API бэкенда Carcraft Lead Generator.

- **Стек:** Python 3.12+, FastAPI (:3002), Uvicorn, SQLAlchemy 2.0 async + Alembic, Pydantic v2, PostgreSQL, ClickHouse, Redis, Kafka, uv.
- **Архитектура:** Чистая архитектура (Clean Architecture / DDD-лайт) с разделением на четыре изолированных слоя (`domain`, `application`, `infrastructure`, `presentation`).

## Архитектурные слои и навигация

Бэкенд структурирован строго по принципам чистой архитектуры. Направление зависимостей:
`presentation` → `application` → `domain` ← `infrastructure`
(инфраструктура реализует порты домена/application, домен не зависит ни от какого внешнего слоя). Соблюдение границ контролируется через `import-linter` (`uv run lint-imports`).

Подробные правила и паттерны разработки каждого слоя описаны в отдельных руководствах:

- **[domain/AGENTS.md](domain/AGENTS.md)** — ядро приложения. Доменные сущности (`@dataclass`), бизнес-правила, инварианты, статусы (`values.py`), Protocol-порты (`domain/services/`), доменные исключения (`DomainError`). Полная изоляция от I/O, БД и внешних фреймворков.
- **[application/AGENTS.md](application/AGENTS.md)** — сценарии использования (use cases). CQRS-команды (`commands/`) и запросы (`queries/`), оркестрация бизнес-процессов, аутентификация и сессии, отправка уведомлений, маппинг доменных ошибок в HTTP (`ServiceError`, `domain_to_http`). Управление транзакциями (только `flush()`, без `commit()`).
- **[infrastructure/AGENTS.md](infrastructure/AGENTS.md)** — техническая реализация. База данных (async engine, сессии `AsyncSession`), ORM-модели SQLAlchemy (только для Alembic и сырых запросов), репозитории (строго возвращают `dict`, никогда ORM-модели), внешние интеграции (ModulBank, ModulKassa, DaData, S3/ObjectStorage, SMS), единый источник настроек `settings`.
- **[presentation/AGENTS.md](presentation/AGENTS.md)** — интерфейс API. Роутеры FastAPI (`routers/`), зависимости аутентификации (`get_current_user`, `require_roles`), Pydantic-схемы валидации и OpenAPI-документации, вебхуки платёжных систем, фиксация транзакций (`await session.commit()`).

## Запуск и окружение

Управление зависимостями и виртуальным окружением выполняется через `uv`.

### Локальный запуск через Docker Compose

Запуск и пересборка контейнера бэкенда:

```bash
docker compose build backend
docker compose up -d --build --force-recreate backend
```

Просмотр логов:

```bash
docker compose logs -f backend
```

### Локальная разработка через uv

```bash
cd backend
uv sync
uv run uvicorn main:app --host 0.0.0.0 --port 3002 --reload
```

## Обязательные проверки перед коммитом

Для любого изменения кода бэкенда необходимо выполнить статические проверки из директории `backend/`:

```bash
cd backend
uv run ruff check . --fix
uv run lint-imports
uv run mypy .
```

Все три статические проверки должны завершаться без ошибок (зелёными). Допустимы ранее существовавшие ошибки mypy в не затронутых задачей файлах, но в изменённых или добавленных файлах появление новых ошибок строго запрещено.

### Проверка соответствия ORM-моделей и схемы БД (Alembic)

После каждой задачи обязательно проверить отсутствие расхождений между ORM-моделями SQLAlchemy и схемой БД. На локальной или изолированной проверочной БД применить все миграции текущей ветки и проверить результат из `backend/`:

```bash
uv run alembic upgrade head
uv run alembic check
```

- Команда `alembic check` выполняет autogenerate-сравнение моделей и базы данных без генерации файла миграции.
- Обязательный результат — успешный код завершения (0) и вывод:
  ```text
  No new upgrade operations detected.
  ```
- Если для проверки запускается `alembic revision --autogenerate`, сгенерированные функции `upgrade()` и `downgrade()` должны быть пустыми (содержать только `pass`). Созданную пустую проверочную ревизию после проверки необходимо удалить и не коммитить.
- Запрещено маскировать расхождения схемы через `alembic stamp`, скрывать их фильтрами autogenerate или считать задачу завершённой при наличии расхождений.
- Если обнаружены расхождения, необходимо исправить ORM-модели или добавить необходимую миграцию, применить её и повторить проверку до чистого результата `No new upgrade operations detected.`.

## Правила и соглашения бэкенда

### 1. Идентификаторы сущностей
- По умолчанию все идентификаторы сущностей в Python строго типизируются как `uuid.UUID`.
- Запрещены объединения `int | UUID`, `str | int` или неявные приведения типов.
- Числовой идентификатор (`int`) допустим **исключительно** в случаях, когда актуальные ORM-модели и схемы БД явно доказывают целочисленный контракт. Требования добавления целочисленных ID без доказательства в схеме отклоняются и отправляются на согласование автору задачи.

### 2. Секреты и конфигурация
- Категорически запрещено прямое чтение переменных окружения через `os.environ` или `os.getenv`.
- Все параметры конфигурации и секреты считываются исключительно через типизированный объект `settings`:
  ```python
  from infrastructure.settings import settings
  ```
- Новые переменные объявляются в классе `Settings` (`infrastructure/settings.py`) с валидацией через `pydantic-settings`. Дефолты задаются в коде, переопределения для продакшена — через окружение.

### 3. Аутентификация и токены
- JWT-токен извлекается сначала из HttpOnly-cookie `accessToken`, а при отсутствии — из заголовка `Authorization: Bearer <token>`.
- Токены подписываются асимметричным алгоритмом **ES256** с использованием ключей из каталога `settings.jwt_keys_dir`.
- Токены обязаны содержать идентификатор ключа `kid` в заголовке. Алгоритм HS256 для access- и refresh-токенов запрещён и не поддерживается.
- При аутентификации в роутерах используется зависимость `get_current_user` (быстрый путь проверки JWT без обращения к БД). Если требуется актуальный снапшот пользователя из базы данных, используется `get_current_user_with_db`. Проверка ролей осуществляется через фабрику `require_roles(...)`.

### 4. Публичные эндпоинты (без аутентификации)
Большинство маршрутов `/api/v1/` требуют авторизации. Публично доступны только следующие эндпоинты:
- `GET /api/v1/health` — проверка работоспособности сервиса;
- `GET /api/v1/section-visibility/public` — видимость разделов интерфейса;
- `GET /api/v1/cars/model-showcase` — витрина моделей каталога;
- `GET /api/v1/storefronts/{storefront_slug}/cars/model-showcase` — витрина моделей конкретного дилера/витрины;
- `GET /api/v1/company/search` — публичный поиск компаний по ИНН/наименованию;
- `GET /api/v1/cars/{id}/images` и `GET /api/v1/cars/{id}/images/{filename}` — публичные изображения автомобилей;
- Публичные эндпоинты спецтехники (только для чтения):
  - `GET /api/v1/special-equipment/categories*`
  - `GET /api/v1/special-equipment/marks`
  - `GET /api/v1/special-equipment/products*`
  - `GET /api/v1/special-equipment/facets`
  - `GET /api/v1/special-equipment/images/{id}/content`

Для всего остального пространства `/api/v1/` требуется валидный токен.

### 5. Маршрутизация API и редиректы
- Backend-маршруты под `/api/*` не должны приводить к внешним HTTP 307-редиректам из-за завершающего слеша (`/`).
- Для предотвращения утечки внутренней схемы/хоста за Nginx работает внутренний middleware `ApiTrailingSlashMiddleware`, нормализующий пути со слешами внутри ASGI-приложения.
- Фронтенд и клиенты обязаны обращаться по каноническим путям без лишних редиректов.
- Запрещено возвращать широкое доверие к прокси-заголовкам вида `--forwarded-allow-ips "*"` ради исправления схемы или хоста перенаправления.

### 6. Webhooks
- Эндпоинты вебхуков (например, платёжные `/api/v1/payments/webhook/*`) **не используют JWT**.
- Аутентификация запроса выполняется исключительно по проверке криптографической подписи провайдера (например, двойной SHA-1 хэш ModulBank).
- Вебхук обязан строго соблюдать документированный контракт ответа платёжного шлюза:
  - Всегда возвращать HTTP 200, даже при ошибке обработки, предотвращая лавинообразные повторные отправки (retry storms);
  - На ошибках в теле ответа возвращать структурированный статус вида `{"ok": False, "processed": False, "error_code": "..."}`, без утечки внутреннего текста исключений;
  - Фоновые задачи (например, фискализация чеков) запускаются после успешного `commit` транзакции в изолированном контексте с собственной сессией БД.

### 7. Логирование
- В сервисе используется единственный именованный логгер:
  ```python
  import logging
  logger = logging.getLogger("carcraft-backend")
  ```
- Логирование структурировано через `infrastructure.logging` с автоматическим маскированием чувствительных данных (`_REDACTED`), поддержкой контекстных переменных и ограничением глубины и длины сообщений.
- Запросы health check (`/api/v1/health`) исключаются из access-логов Uvicorn (`uvicorn.access`), чтобы не засорять журнал мониторингом.

### 8. ClickHouse и аналитика DWH
- **Запись в ClickHouse:** сервис FastAPI **никогда не пишет** напрямую в ClickHouse. Все события публикуются в Kafka, а сохранение в ClickHouse выполняет consumer-сервис `event-worker`.
- **Чтение из ClickHouse:** FastAPI разрешено выполнять только аналитические read-only запросы через модуль `infrastructure/clickhouse_readonly.py`.
- Любой аналитический запрос в ClickHouse от имени дистрибьютора обязательно фильтруется по области видимости `scope_dealer_ids` для предотвращения утечки данных между компаниями.

### 9. Поиск компаний через DaData
- Ключ `DADATA_API_KEY` доступен только бэкенду и хранится в `settings.dadata_api_key`. Вызовы DaData напрямую с фронтенда запрещены.
- Поиск компаний инкапсулирован в эндпоинте `GET /api/v1/company/search`.
- Фронтенд получает данные через автокомплит и передаёт готовый сериализованный объект компании (`{ name, inn, kpp, ogrn, legal_address, manager_name, ... }`). Бэкенд создаёт запись компании непосредственно из этих полей; повторный поиск через DaData при регистрации или сохранении компании не выполняется.

## Запрещённые практики на бэкенде

1. **Нарушение слоёв архитектуры:**
   - Импорт из внешних слоёв во внутренние (например, импорт `infrastructure` или `presentation` в `domain`). Нарушения блокируются линтером `lint-imports`.
2. **Использование ORM-моделей за пределами инфраструктуры:**
   - Модели SQLAlchemy (`infrastructure/models/*`) не должны передаваться в `application` или `presentation` и не должны использоваться как DTO. Репозитории обязаны возвращать чистые словари (`dict` / `list[dict]` или `TypedDict`).
3. **Вызовы `session.commit()` внутри application или infrastructure:**
   - Репозитории и командные хендлеры `application` не вызывают `session.commit()`. Если хендлеру нужен сгенерированный ID, вызывается `await session.flush()`.
   - Единственным местом вызова `await session.commit()` являются FastAPI-роутеры в слое `presentation` после успешного завершения обработки запроса.
4. **Использование `float` для денежных сумм:**
   - Все финансовые расчеты, цены, платежи, остатки и проценты обязаны использовать тип `Decimal` (`from decimal import Decimal`). Использование `float` категорически запрещено из-за ошибок округления двоичной арифметики.
5. **Прямое чтение `os.environ`:**
   - Запрещено использовать `os.environ` и `os.getenv` в любом месте кодовой базы бэкенда. Все параметры должны быть объявлены в `infrastructure/settings.py`.
6. **Самовольное добавление unit- и архитектурных тестов:**
   - Не добавлять и не запускать unit-, интеграционные или архитектурные тесты без прямого запроса пользователя. Основной способ подтверждения изменений — проверка сквозного E2E-сценария на работающем приложении.
