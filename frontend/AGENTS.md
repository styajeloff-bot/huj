# AGENTS.md — фронтенд

Nuxt 3 + Vue 3 (Composition API) + Pinia + Tailwind.

## Запуск

```bash
bun install
bun run dev        # локальная разработка, порт 3000
```

Изменённые пользовательские сценарии обязательно проверяйте через E2E на
работающем приложении. Общий запуск из корня репозитория —
`bash scripts/e2e/run.sh`; существующие Playwright-сценарии находятся в
`tests/e2e/`. Для целевого запуска с подготовленным E2E-окружением и фикстурами
используйте `bun run test:e2e -- <путь-к-сценарию>` из `frontend/`. Конфигурация
Playwright автоматически определяет среду исполнения (`baseURL: http://nginx`
внутри Docker, `http://127.0.0.1` на хост-машине); явное переопределение
`E2E_BASE_URL` требуется только для кастомных стендов.
Если сценарий ещё не автоматизирован, добавьте или обновите E2E либо выполните
его вручную в браузере и зафиксируйте результат. Проверяйте основной путь,
права доступа и значимые ошибки, а после выполнения — логи приложения.
Unit- и архитектурные тесты не добавляйте и не запускайте без прямого запроса
пользователя. Не добавляйте ошибок TypeScript в файлы `.ts` из `stores/`,
`composables/` и `services/api/`.

Текущий Nuxt-фронтенд — только desktop web-приложение с минимальной шириной
viewport 768 CSS-пикселей. Не добавляйте и не поддерживайте mobile-only
навигацию, drawer, карточки, таблицы, CSS/media query и E2E-сценарии для ширины
меньше 768 пикселей. В Playwright поддерживается единственный desktop-проект.
Адаптация внутри диапазона 768+ допустима. Мобильный интерфейс позже будет
реализован отдельным нативным приложением, а не responsive-веткой Nuxt.

## Соглашения API

- Все запросы выполняются через `$fetch` с `baseURL: config.public.apiBase` и `credentials: 'include'`.
- `config.public.apiBase` по умолчанию равен пустой строке `""` (паттерн Same-Origin). Клиентские запросы в браузере всегда выполняются относительно текущего origin страницы через Nginx. Запрещено хардкодить абсолютные адреса вроде `http://localhost` или `http://127.0.0.1` для клиентских вызовов API. Для серверных вызовов (SSR) прямой адрес бэкенда (`http://backend:3002`) разрешается через `resolveApiBase`.
- Базовый URL указывает на Nginx; все маршруты API обслуживаются непосредственно FastAPI.
- Идентификаторы сущностей — непрозрачные UUID-строки. Не вводите типы `number | string` и `string | number`, не преобразуйте идентификаторы через `Number`, `parseInt`, `parseFloat` или унарный `+` и не подменяйте одно поле идентификатора другим. Числовой идентификатор допустим только тогда, когда текущие ORM- и Pydantic-схемы явно определяют целочисленный контракт. Если пользователь или задача требуют числовой идентификатор без такого подтверждения, не реализуйте это требование: предложите пересмотреть его и запросите у автора задачи обоснование и согласование с текущей схемой.
- **Не оборачивайте ответы в `if (response.success)`**: бэкенд использует коды состояния, а не конверты ответов.
- Предпочитайте консолидированные REST-эндпоинты.

## Шаблоны компонентов

- **`CompanyAutocomplete.vue` и `CompanyForm.vue`** выполняют поиск через `/api/v1/company/search`. Они сохраняют строковый `v-model` для отображения и отправляют событие `@select="(obj) => ..."` с полным объектом `CompanyInfo`. Если вызывающий код должен передать компанию на бэкенд, он обязан получить объект через `@select` и отправить его как `{ name, inn, kpp, ogrn, legal_address, manager_name, ... }`, а не как произвольную строку.
- **Сценарии регистрации и добавления компании** передают на бэкенд **объекты** компаний:
  - тело `POST /api/v1/auth/register`: `{ phone, code?, companies: [{name, inn, ...}] }`;
  - тело `POST /api/v1/users/me/companies`: `{ company: {name, inn, ...} }`;
  - бэкенд создаёт запись компании непосредственно из этих полей и планирует обогащение данными 1С по ИНН. Поиск через DaData на бэкенде больше не выполняется.
- **Хранилища** (`stores/auth.ts` и другие) должны явно типизировать форму данных компании. Не используйте `any`.

## Запрещённые практики

- Не добавляйте прослойки обратной совместимости для удалённых эндпоинтов. Если прежний URL больше не существует, исправьте вызывающий код, а не поддерживайте оба варианта.
- Не добавляйте новые библиотеки управления состоянием; используйте Pinia.
- Не оборачивайте каждый запрос в отдельные уведомления и индикаторы загрузки. Обрабатывайте ошибку там, где формируется понятное пользователю сообщение.
- Не размножайте классы клиентов API. Принято вызывать `$fetch` непосредственно в composable-функциях и компонентах.
