## Подтверждённое текущее состояние

1. В режиме создания комплектации блок характеристик после выбора марки,
   модели и модификации показывает подсказку «Создайте комплектацию». Кандидаты
   загружаются только по существующему `trim_id` через
   `GET /trims/{trim_id}/attribute-candidates`, поэтому выбрать группы и
   характеристики до первого сохранения невозможно.
2. Текущий picker уже соблюдает порядок «группа → характеристики»: новая
   комплектация не получает required-кандидатов автоматически, выбранная
   группа раскрывает только свои характеристики, снятие optional-группы
   очищает её локальный выбор.
3. DOCX просит «поправить дизайн отображения у комплектаций», но целевой
   макет, ссылка на дизайн и описание отличий в файл не вложены. Скриншот на
   второй странице показывает текущее состояние, а не подтверждённый TO-BE.
4. Public detail уже выводит сохранённые группы и значения комплектации
   отдельно от модификации, но заголовок называется
   «Характеристики комплектации», а не «Параметры комплектации».
5. В блоке «Собрано из» frontend самостоятельно строит ссылку на компонент из
   `id` и `slug`. В проекции заявки backend и fallback checkout также могут
   строить URL вида `/special-equipment/products/{id}/equipment`. Наличие URL
   не доказывает, что целевое объявление по-прежнему публично доступно.
6. Склад и компания-продавец хранятся в товаре раздельно. Backend проверяет
   совпадение владельца склада с `seller_company_id`, но frontend-тип активного
   склада не содержит уже возвращаемые admin API поля `company_id` и
   `dealer_id`, а выбор склада не синхронизирует продавца. Видимость заявки у
   дилера определяется `seller_company_id` позиции заявки, а не самим
   `warehouse_id`.
7. Detail-представление форматирует boolean как `Да`/`Нет`. Поэтому значение
   `true` показывается отдельным словом, а `false` остаётся видимой строкой.
   Та же проекция используется в ключевых характеристиках, блоках компонентов
   и характеристиках комплектации на странице товара.
8. После MR !320 `price_on_request = true` требует `price_from > 0` во
   frontend, Pydantic/domain validation, ORM CHECK-ограничениях и XLSX v5.
   Публичное отображение при заполненной границе — `от N ₽`; пустая граница
   сейчас не может быть сохранена.

## Область follow-up

В работу входят:

- настройка групп и характеристик ещё не созданной комплектации сразу после
  выбора модификации;
- согласованная визуальная доработка picker после получения целевого макета;
- отдельный публичный блок «Параметры комплектации»;
- устранение неработающих ссылок на объявления спецтехники в составе и
  сценариях заявки;
- согласованность склада, продавца и дилерской видимости заявки;
- detail-only представление boolean-характеристик;
- цена по запросу с опциональной нижней границей, dealer workflow и импорт v5;
- каскадный фильтр объявлений по уровням категорий с URL-восстановлением;
- регрессионные тесты, обязательные проверки, Docker и desktop browser smoke.

Не входят:

- изменение порядка «сначала группа, затем характеристики»;
- копирование значений комплектации в товар или модификацию;
- изменение UUID-контрактов и числовое преобразование идентификаторов;
- скрытие boolean-характеристик в фильтрах, административной панели или API;
- изменение каталога автомобилей;
- мобильный интерфейс уже 768 CSS-пикселей;
- произвольный редизайн без переданного целевого макета.

## Проектные уточнения для согласования

1. Формулировка DOCX «сразу отображать группы и характеристики» означает, что
   picker доступен до создания комплектации. Сами характеристики по-прежнему
   раскрываются только после явного выбора группы согласно MR !315.
2. Неработающая ссылка не заменяется догадкой о slug. Сервер возвращает
   nullable канонический `detail_url`; frontend показывает ссылку только когда
   такой URL подтверждён. Для недоступной цели карточка остаётся текстовой без
   клика.
3. При выборе склада с одним однозначным владельцем форма синхронизирует
   `seller_company_id` с владельцем склада. Несовместимую ручную комбинацию
   нельзя сохранить; смена продавца очищает несовместимый склад с явным
   сообщением.
4. `price_from` становится опциональным только при
   `price_on_request = true`. Если граница заполнена, сохраняется текущий
   mixed-application workflow и предварительный total. Если границы нет,
   цена считается неизвестной: в одну заявку допускается только одна единица
   такой спецтехники без автомобилей и других платных позиций, а общая сумма
   остаётся неизвестной до ответа дилера.
5. Пункт о дизайне picker не имеет проверяемого TO-BE. Его реализация и
   визуальные критерии остаются заблокированы до передачи макета; остальные
   пункты можно реализовать независимо после согласования этой спецификации.
6. Фильтр объявлений учитывает как категории, назначенные самому товару, так и
   effective-категории его модификации. Это сохраняет действующий точный
   management-контракт и исключает расхождение с остальными фильтрами
   спецтехники.

## Функциональные требования

### 1. Характеристики новой комплектации до создания

1. После выбора `modification_id` в форме создания комплектации frontend сразу
   загружает кандидатов и показывает picker групп. Нажимать «Создать» для
   получения кандидатов больше не требуется.
2. Backend предоставляет read-only preview кандидатов по модификации, не
   требующий `trim_id`. Планируемый путь:
   `GET /api/v1/admin/special-equipment/modifications/{modification_id}/trim-attribute-candidates`.
3. Preview и действующий
   `GET /trims/{trim_id}/attribute-candidates` используют один application
   resolver. Схема ответа, порядок, effective-категории, активность,
   `modification_value`, `is_available`, `block_reason` и конфликт
   `CATEGORY_ATTRIBUTE_GROUP_CONFLICT` идентичны.
4. До выбора группы показывается только список групп и подсказка «Сначала
   выберите группу». После выбора видны только характеристики этой группы;
   доступные required-характеристики отмечаются в этот момент.
5. Выбор групп, характеристик и типизированных значений хранится локально до
   сохранения. Смена марки, модели или модификации очищает staged state и не
   позволяет позднему ответу старого запроса восстановить его.
6. По кнопке «Создать» сначала идемпотентно создаётся scalar-комплектация,
   затем staged назначения и значения сохраняются через действующие
   ETag/If-Match mutation endpoints. UUID и серверные валидаторы не обходятся.
7. Если scalar-комплектация создана, а последующая синхронизация назначения
   завершилась ошибкой, форма переходит в edit созданной сущности, сохраняет
   несинхронизированный локальный выбор и предлагает повторить. Повтор не
   создаёт вторую комплектацию.
8. Edit-гидратация, persisted unavailable assignment, loading/error/retry и
   пустой effective-набор сохраняют действующее поведение.

### 2. Дизайн picker комплектации

1. До получения макета поддерживаются существующие семантические блоки:
   «Группы характеристик», «Характеристики выбранных групп», действие
   «Применить» и состояния empty/loading/error/retry.
2. Целевой макет должен определить как минимум компоновку, отступы, состояния
   checkbox, длинные названия и адаптацию desktop 768+. После его передачи
   критерии дополняются в этом же файле до реализации визуального пункта.
3. Визуальная доработка не меняет API, порядок выбора, клавиатурное управление,
   focus-visible и доступные подписи.

### 3. Параметры комплектации в публичном объявлении

1. На странице `/special-equipment/products/{product_id}/{slug}` сохранённые
   группы и непустые значения выбранной комплектации выводятся отдельным
   блоком с точным заголовком «Параметры комплектации».
2. Группы сохраняют серверный порядок и названия; nullable-группа отображается
   как «Без группы». Number, text, select и boolean используют detail-only
   presentation из раздела 6.
3. Блок модификации остаётся самостоятельным. Значения комплектации не
   смешиваются с `component_blocks`, не копируются в товар и не дедуплицируются
   с модификацией.
4. При отсутствии `trim_id` либо при отсутствии непустых назначенных значений
   блок не показывается. Loading публичной страницы не создаёт пустой
   заголовок.
5. Management read-only блоки и API-поле `trim_attribute_groups` сохраняются;
   breaking change wire-контракта не требуется.

### 4. Ссылки на объявления спецтехники

1. Выполняется аудит всех ссылок на public detail спецтехники в:
   - блоке «Собрано из» составного объявления;
   - checkout/application creation и предложениях;
   - карточке состава заявки клиента, дилера и CarCraft;
   - корзине и избранном, если они используют общий detail URL.
2. Public component/application projections возвращают nullable канонический
   `detail_url` только для объявления, которое доступно через public detail в
   текущем storefront scope. URL содержит фактические UUID и slug.
3. Frontend не конструирует fallback `/products/{id}/equipment` и не подменяет
   отсутствующий URL каталогом. Он использует только безопасный server URL или
   уже загруженную public product-проекцию с фактическим slug.
4. При `detail_url = null` название, изображение, роль и статус позиции
   остаются видимыми, но `NuxtLink`, overlay-link и текст «Открыть объявление»
   не рендерятся.
5. Для доступной цели ссылка открывает public detail без 404/redirect loop.
   Архивирование или исключение из storefront превращает URL в `null` при
   следующем чтении, не раскрывая закрытое объявление.

### 5. Склад, продавец и видимость заявки у дилера

1. TypeScript-модель admin-склада включает nullable `company_id` и
   `dealer_id`, уже возвращаемые `/api/v1/admin/warehouses`. Идентификаторы
   остаются непрозрачными UUID-строками.
2. При выборе активного склада форма определяет единственного владельца:
   `company_id`, legacy `dealer_id` либо одинаковое значение обоих полей, и
   устанавливает того же продавца объявления.
3. Склад с различающимися `company_id` и `dealer_id` не предлагается для
   назначения и диагностируется как неконсистентный. Склад без владельца не
   подставляет продавца; для публикации пользователь обязан выбрать активную
   компанию явно.
4. Ручная смена продавца на несовместимого со складом очищает `warehouse_id`,
   помечает поле touched и показывает причину. Backend-проверка владельца
   остаётся обязательной защитой от обхода frontend.
5. Созданное объявление сохраняет явно выбранные `condition`, `sale_status` и
   `publication_status`; выбор склада сам по себе не переводит его в «Новое»,
   не скрывает из management list и не меняет публикационный статус.
6. Для published/available объявления склад участвует в public stock как
   раньше. При создании заявки `seller_company_id` позиции берётся из
   подтверждённого продавца объявления и совпадает с владельцем склада.
7. Дилер, чья компания владеет позицией, видит заявку в
   `/workspace/applications`; другой дилер её не видит. Проверка выполняется по
   child item ownership и не зависит от родительского fallback приложения.
8. Регрессия покрывает цепочку: warehouse owner → product seller → application
   item seller → dealer list/detail.

### 6. Boolean-характеристики только на public detail

1. На странице public detail значение boolean `true` показывается только
   названием характеристики. Видимый текст `Да`, `true` или единица рядом с
   названием отсутствует.
2. Boolean `false` полностью исключается из detail: не показываются ни
   название, ни значение.
3. Правило применяется ко всем характеристикам на этой странице:
   `card_attributes`, `component_blocks` модификации/надстроек и
   `trim_attribute_groups` комплектации.
4. Если после фильтрации группа или весь блок не содержит видимых
   характеристик, пустой контейнер и заголовок не показываются.
5. Для screen reader у выбранного boolean допускается невидимая семантика
   «выбрано», но визуально остаётся только название.
6. Public API продолжает возвращать типизированные `true`/`false`, а
   `display_value` сохраняется для совместимости. Catalog cards, фильтры,
   facets, admin и import не меняют отображение или семантику.

### 7. Цена по запросу без нижней границы

#### 7.1. Management и данные товара

1. При `price_on_request = true` поле `price_from` становится nullable. Если
   оно заполнено, значение обязано быть больше нуля; ноль и отрицательное
   значение по-прежнему запрещены.
2. Поле «От, ₽» показывается как необязательное без звёздочки. Подсказка
   объясняет: заполненная сумма будет показана как «от N ₽», пустое поле — как
   «Цена по запросу».
3. `price_on_request = false` по-прежнему приводит `price_from` к `null`.
   Обычная и специальная цены остаются скрытыми, но не стираются при включении
   режима.
4. Запрет менять `price_on_request` после первой публикации сохраняется.
   Положительный `price_from` можно изменить или очистить без переключения
   режима через действующий ETag/If-Match-контракт.
5. ORM и следующая Alembic-миграция разрешают сочетание
   `price_on_request = true, price_from = null`, сохраняя CHECK
   `price_from IS NULL OR price_from > 0` и запрет ненулевого `price_from` при
   выключенном режиме.
6. `on_order` допускает активный request-price режим без нижней границы.
   Товар с пустым `price_from` нельзя переводить в `reserved`/`sold`: цена,
   согласованная дилером, принадлежит позиции заявки и не изменяет цену
   исходного объявления.

#### 7.2. Public catalog

1. При request-price с заполненным `price_from` карточки и detail показывают
   `от N ₽` как сейчас.
2. При `price_from = null` показывается точный текст «Цена по запросу» без
   `от`, нуля, валюты и пустого placeholder.
3. Public `price`, `base_price`, `special_price` и `price_from` в этом режиме
   возвращаются `null`; `price_on_request` остаётся `true`.
4. Numeric price filter не включает товар без нижней границы в совпадение по
   min/max. Price sort помещает неизвестную цену после известных с
   детерминированным fallback по существующим полям.
5. Cart, favorites, compatible attachments и detail используют один helper и
   не расходятся в подписи.

#### 7.3. Заявка и цена дилера

1. При положительном `price_from` сохраняется текущий workflow MR !320:
   mixed-заявка разрешена, preliminary total использует нижнюю границу,
   позиция получает `price_status = pending`.
2. При `price_from = null` допускается только одна единица одной billable
   позиции спецтехники без автомобилей, других платных позиций и количества
   больше одного. Бесплатные технические component-строки допустимы.
3. Для такой позиции создаются `price_status = pending`,
   `unit_price = null`, `total_price = null`; snapshot содержит явные
   `price_on_request = true` и `price_from = null`. Общая сумма заявки до
   согласования равна `null`, а не нулю.
4. DB consistency CHECK допускает у `pending` либо обе положительные суммы,
   либо обе `null`. Для `set` обе суммы положительные и заполнены setter/time;
   component-строки сохраняют `price_status = none` и нулевые суммы.
5. В кабинете владеющего позицией дилера действие «Выставить стоимость»
   доступно как для request-price с нижней границей, так и без неё. В modal
   отсутствующая предварительная цена показывается как «Не указана».
6. После установки дилером положительной цены `unit_price`, `total_price`,
   `price_status`, setter/time, audit log и `application.total_amount`
   обновляются атомарно. Повторное изменение и гонки с назначением ЛК
   сохраняют контракт MR !320.
7. До `price_status = set` назначение ЛК, покупка, резерв и онлайн-оплата
   заблокированы сервером независимо от frontend.

#### 7.4. XLSX v5

1. Колонки XLSX v5 не переименовываются; версии v1-v4 сохраняют текущие
   заголовки и update-совместимость.
2. Для новой строки v5 применяется матрица:
   - `price` пусто и `price_on_request` пусто →
     `price_on_request = true`, `price_from = null`;
   - `price` заполнено и `price_on_request` пусто → fixed-price режим;
   - `price_on_request = true`, `price_from` пусто → request-price без нижней
     границы;
   - `price_on_request = true`, `price_from > 0` → request-price с нижней
     границей;
   - заполненное неположительное `price_from` → validation issue.
3. Для PATCH существующей строки отсутствие request-price колонок не меняет
   сохранённый режим. Явная очистка `price_from` при активном режиме разрешена;
   опубликованный товар по-прежнему не позволяет переключить сам режим.
4. Normalized plan и preview явно показывают вычисленные
   `price_on_request`/`price_from`, чтобы не было скрытой конвертации только во
   время apply.
5. ATOMIC/BEST_EFFORT используют одинаковую доменную валидацию и машинные коды;
   шаблон, parser, preview, apply и management API имеют одинаковую семантику.

### 8. Каскадный фильтр объявлений по категориям

1. `GET /api/v1/admin/special-equipment/products` принимает nullable UUID
   `level_1_id` ... `level_5_id` одновременно с действующими `q`,
   `normalization_state`, role/mark/model/category/status и pagination.
2. Непустые уровни образуют непрерывную последовательную цепочку существующих
   категорий. Пропуск уровня, неизвестный UUID или пара, не связанная ребром
   parent → child, образуют несовместимую цепочку и возвращают пустой список с
   `total = 0`, а не результаты без фильтра.
3. Последняя выбранная категория определяет ветвь: в scope входят она сама и
   все её транзитивные потомки в DAG. Продукт совпадает, если хотя бы одна его
   прямая категория либо категория его модификации входит в этот scope.
4. Фильтр применяется в SQL до подсчёта total, сортировки, offset и limit;
   счётчик и страницы соответствуют отфильтрованной выдаче. Миграция БД не
   требуется.
5. Во вкладке «Объявления» рядом с «Нормализацией» показываются каскадные
   searchable select: без выбора виден только «Уровень 1», после выбора —
   следующий уровень с непосредственными детьми, максимум до уровня 5.
6. Смена родителя или очистка уровня удаляет все дочерние уровни и сбрасывает
   страницу на первую. Выбранные `q` и `normalization_state` сохраняются.
7. Поиск, смена нормализации и ручная пагинация сохраняют выбранную цепочку;
   ручная пагинация сохраняет номер страницы до следующего изменения самого
   категорийного фильтра.
8. URL содержит `level_*_id` и восстанавливает непрерывную цепочку после
   обновления. Несовместимая, но UUID-валидная цепочка передаётся backend для
   безопасного пустого результата, а не молча превращается во «Все».
9. Вкладка «Категории» сохраняет действующий каскад и сортировку; общие pure
   helpers переиспользуются без связывания product-filter с category sort.

## Архитектурные границы

1. Resolver кандидатов комплектации принимает `modification_id` и не зависит
   от FastAPI. Trim-route сначала разрешает trim → modification и вызывает тот
   же resolver; preview-route вызывает его напрямую.
2. Frontend create-flow хранит unsaved picker state отдельно от server ETag.
   После появления `trim_id` он переходит на существующий sync seam, не
   создавая второй набор mutation API.
3. Канонический public detail URL формирует backend presentation/query слой.
   Frontend отвечает только за безопасный render nullable URL.
4. Связь склад → владелец разрешается по admin warehouse DTO; backend остаётся
   владельцем проверки seller/warehouse и dealer child ownership.
5. Detail-only attribute presentation является чистой frontend-функцией. API,
   repository rows и filter projection не модифицируются ради скрытия boolean.
6. Коммерческие инварианты request-price централизуются в domain helper и
   используются management, composite create, PATCH, импортом и commerce.
7. Все деньги backend обрабатывает через `Decimal`; идентификаторы — UUID.
   Application/domain слои не импортируют presentation или ORM.
8. Разрешение category-level scope остаётся чистой domain-функцией. Repository
   применяет полученный scope к прямым и modification-категориям до pagination;
   frontend хранит URL/query state через существующий `registryQuery` seam.
