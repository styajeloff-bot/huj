# Bitrix #22006 — финальное КП без предварительного

- **Статус:** требуется подтверждение спецификации
- **Задача:** https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/22006/

## Проблема

Лизинговая компания может заполнить итоговое КП в интерфейсе без предварительного, но при отправке сервер отклоняет действие. В доменной машине статусов переход в `approved_final` разрешён только из статусов предварительного одобрения (`approved_scoring` и `approved_scoring_another_cond`).

Для новой или возвращённой в работу заявки статус ЛК обычно `under_review`; при запросе документов возможны также `documents_required` и `under_review_with_docs`. Во всех этих состояниях предварительное КП может отсутствовать, поэтому финальное КП не отправляется.

## Цель и бизнес-результат

Лизинговая компания может сразу направить клиенту корректно заполненное финальное КП, не создавая и не отправляя предварительное. Это сокращает лишний этап для заявок, по которым ЛК уже готова дать окончательное предложение.

## Решение

### Рекомендуемый вариант — расширить серверные допустимые переходы

Изменить единственный источник бизнес-правила — машину статусов `LeasingCompanyApplication`:

1. Разрешить переход в `approved_final` и `approved_final_another_cond` из активных дофинальных статусов `under_review`, `documents_required` и `under_review_with_docs`.
2. Не менять правило полноты: финальное одобрение по-прежнему требует хотя бы одно заполненное КП.
3. Не менять остальные переходы, блокировку повторной отправки, права ЛК и клиентский сценарий выбора ЛК.
4. Добавить интеграционные регрессии API: ЛК отправляет финальное КП без предварительного из каждого указанного статуса; итоговый статус — `approved_final`, повторная отправка блокируется.
5. Актуализировать описание машины статусов, чтобы оно отражало бизнес-правило.

### Рассмотренные варианты

- Менять только frontend — **не подходит**: UI уже позволяет заполнять итоговое КП, а окончательную блокировку создаёт серверная валидация. Прямой API-вызов остался бы заблокирован.
- Разрешить переход только из `under_review` — **недостаточно**: после запроса документов ЛК снова не смогла бы направить финальное КП без предварительного.

## Границы

- Миграция БД не требуется: изменяется прикладная проверка переходов, а не перечисление статусов.
- Данные существующих заявок не меняются.
- Интерфейс и API-контракт не меняются.

## Критерии готовности

- ЛК со статусом `under_review` и заполненным финальным КП может отправить решение `approve` с `kind=final` без предварительного КП; API возвращает успех, а статус становится `approved_final`.
- Тот же сценарий работает из статусов `documents_required` и `under_review_with_docs`.
- Без заполненного КП финальное одобрение по-прежнему отклоняется.
- Повторная отправка финального решения после успешного одобрения по-прежнему отклоняется.
- Существующий поток «предварительное КП → финальное КП» не меняется.
- Пройдены релевантные и полный backend-набор тестов, линтеры, проверка типов, Docker build и проверка merge с актуальной `test`.

## Вопросы

Блокирующих вопросов нет. Решение распространяется на все активные дофинальные статусы, поскольку во всех них предварительное КП может отсутствовать.
