Для первых семи сущностей выполнена проверка одиночного и пакетного методов:

прочитать результат из PostgreSQL. У модели изменяется только категория,
у характеристик изменяются мощность и трансмиссия; остальные перечисленные
сущности сохраняют старые значения.

Минимальный пример кузова:

- Первая запись: «Универсал».
- Повторный вход и результат парсинга: «Внедорожник».
- Фактическая запись после повторного импорта: «Универсал».
- Контрольный SQL с изменением только действия при конфликте ключа на
  обновление `body_type` сохраняет «Внедорожник» в обоих режимах.

Ещё один дефект: [парсер](../backend/infrastructure/services/catalog_parser.py)
возвращает словарь из 157 опций, но при пустых значениях выставляет
`has_options=False`. Обработка строки пропускает такой словарь, поэтому
полностью очистить прежние опции через импорт невозможно.

При реализации согласованной проверки пути по VIN найден дополнительный
дефект порядка записи: в смешанном пакете строка с UUID помещает иерархию
в буфер и отмечает её обработанной, а следующая строка только с VIN начинает
одиночную запись до сохранения этого буфера. Возникает нарушение внешнего
ключа опций на ещё не сохранённую модификацию. Исправление в рамках этой
задачи сохраняет буфер перед переходом к одиночной обработке; критерий —
успешный импорт в обоих порядках строк, с корректными счётчиками и без дублей.

## 3. Требуемое поведение

### 3.1. Единый контракт повторного импорта

1. При новом ключе импорт создаёт запись; при существующем обновляет
   все предусмотренные импортом поля сущности.
2. Первичные ключи существующих записей не меняются. Повторная загрузка
   не создаёт копии марки, модели, конфигурации, комплектации или автомобиля.
3. Внешние ключи на родительские сущности обновляются по входным данным
   с сохранением ограничений ссылочной целостности и порядка записи родителей.
4. Для nullable-полей пустое значение входного снимка очищает старое значение
   до `NULL`. Непустые значения не должны сохраняться через `COALESCE`
   вопреки новому снимку. Существующая нормализация чисел, флагов и категории
   транспорта сохраняется.
5. Обновляются только поля, предусмотренные текущим контрактом импорта.
   Колонки БД вне этого контракта не обнуляются. Например,
   `specifications.engine_feeding` не получает искусственного пустого значения.
6. Одинаковый контракт действует для одиночной записи и пакетного импорта.
   Повторная загрузка файла проходит обновление независимо от того,
   сколько строк и пакетов содержал предыдущий импорт.
7. Существующее поведение идентификации автомобиля по UUID/VIN сохраняется.
   Идентификаторы иерархии остаются непрозрачными строками согласно текущим
   ORM-моделям; числовые преобразования не вводятся.

### 3.2. Поля обновления

| Сущность | Поля, обновляемые при существующем ключе |
| --- | --- |
| Марка | Название, кириллическое название, популярность, страна |
| Модель | Названия, класс, годы выпуска, категория, связь с маркой |
| Поколение | Название, годы начала и окончания, рестайлинг, связь с моделью |
| Конфигурация | Количество дверей, тип кузова, название, связь с поколением |
| Модификация | Цены от/до, группа, связь с конфигурацией |
| Опции | Все поля текущего `OPTIONS_MAPPING`, включая очистку |
| Характеристики | Все поля текущего `SPECIFICATIONS_MAPPING`; сохранить уже работающий upsert |
| Автомобиль и склад | Проверить уже работающие обновления цены, цвета, связей и привязки к складу |

Перечень входных колонок определяется
[парсером](../backend/infrastructure/services/catalog_parser.py),
перечень доступных полей — [ORM-моделями](../backend/infrastructure/models/catalog.py).
Новые колонки Excel и новая схема БД для исправления не требуются.

### 3.3. Пустые опции и повторяющиеся строки

- Снимок опций должен доходить до записи даже когда все его значения пустые.
  Очистка одной опции и всего набора должна работать в обоих режимах импорта.
- Повторяющиеся ID внутри пакета не должны приводить к ошибке PostgreSQL
  о повторном обновлении одной строки в одном `INSERT`.
- Сохраняется существующий выбор строки при противоречащих данных для одного
  ID внутри одного файла. Новая политика разрешения таких противоречий
  в этот багфикс не входит.
  Для общих родительских ID сохраняется первый записанный снимок; внутри
  первого пакетного буфера — последнее значение из разных цепочек ID,
  как при существующем заполнении словарей. Полностью повторная цепочка
  пропускается. Историческое исключение `model.category` сохраняет последнее
  значение из разных цепочек, не меняя остальные поля выбранного снимка.
  Отметки обработанных сущностей действуют только в пределах одной загрузки.
  Для опций сохраняется первый записанный непустой снимок, а внутри первого
  буфера — последний непустой. Пустые соседние строки не вытесняют выбранный
  непустой снимок. Если во всей загрузке опции пустые, прежние значения
  очищаются; следующая загрузка выбирает и обновляет снимок заново.
- Дедупликация в пределах загрузки не должна переноситься в следующую
  загрузку и блокировать её обновления.

## 4. План реализации

После подтверждения спецификации выполнить независимые части подагентами:

1. Репозиторий: заменить insert-only и частичный update на полный upsert
   импортируемых полей марки, модели, поколения, конфигурации, модификации
   и опций, согласовав одиночные и пакетные методы.
2. Обработка строк: обеспечить сохранение полностью пустого снимка опций;
   проверить одиночный путь, пакетный путь и переход по VIN.
3. Регрессионные проверки: PostgreSQL-тесты всех сущностей и интеграционный
   сценарий двух загрузок с неизменными идентификаторами.

Использовать существующие точки проверки:
[интеграционные тесты загрузки](../backend/tests/integration/test_catalog_upload.py),
[тесты upsert характеристик](../backend/tests/integration/test_catalog_specifications_upsert.py),
[тесты фоновой обработки](../backend/tests/test_catalog_tasks.py).

кода. Существующая инвалидация фильтров после завершения импорта сохраняется.

универсальный административный импорт не расширяются.

## 5. Проверки и критерии готовности

- Для каждой сущности проверены создание, изменение всех импортируемых полей,
  повтор той же загрузки без дубликатов и очистка nullable-полей.
- PostgreSQL-тесты проходят для одиночных и пакетных методов.
- Сквозной тест через реальные парсер и обработку строк выполняет две
  загрузки с прежними ID и подтверждает обновление иерархии, опций,
  характеристик и автомобиля.
- Пример «Универсал → Внедорожник» подтверждён чтением из PostgreSQL и
  публичной выдачей каталога после завершения импорта.
- Очистка всех опций не сохраняет старые значения; колонки вне импортируемого
  контракта остаются нетронутыми.
- Проверены несколько автомобилей с общими справочными ID и импорт,
  разбитый на несколько пакетов.
- Проверен смешанный пакет с UUID-строками и строками поиска по VIN в обоих
  порядках: родительские записи сохранены до зависимых, счётчики не удвоены.
- В backend выполнены обязательные проверки:

```bash
uv run ruff check . --fix
uv run lint-imports
uv run mypy . --ignore-missing-imports
uv run pytest -q
```

- Приложение собрано и запущено в Docker, проверены
  `/api/v1/health`, завершение задания импорта и логи backend/worker.
- В браузере на синтетических данных проверены актуальный кузов,
  характеристики и фильтры после повторной загрузки.
- После проверок создан MR только в `test`; пройдены обязательные review
  и проверки, выполнено автоматическое объединение при отсутствии блокировок.
- Доставка кода, развёртывание и повторный импорт реального LADA.xlsx
  фиксируются отдельно. Успешный MR не считается подтверждением обновления
  существующих серверных записей LADA.
