# Bitrix 22170: новые характеристики каталога автомобилей

## Источники и статус

- Задача Bitrix: <https://carcraftpro.bitrix24.ru/company/personal/user/738/tasks/task/view/22170/>.
- Исходный файл: `1-шаблон-сделать.xlsx`, лист `Лист1`.
- Требования уточнены в чате 1 сентября 2026 года: изменения относятся к импорту обычного каталога автомобилей из админки и карточке автомобиля на фронтенде. Каталог спецтехники не входит в задачу.
- Требования повторно уточнены аналитиком 8 сентября 2026 года: строка характеристик из файла считается актуальным снимком данных. При повторном импорте обновляются все характеристики, которые формирует парсер, включая пустые значения; пустое значение очищает соответствующее поле в базе.
- В исходном файле красным выделены десять колонок `LB:LK`; именно они считаются новыми характеристиками.
- По прямому указанию пользователя содержимое страницы Bitrix не сверяется: объём задачи определяется приложенным файлом и требованиями из чата.
- Первоначальная реализация выполнена в MR !337. Дополнение выполняется в ветке `bugfix/22170` от актуальной `test` (`5a41cd2d`).
- Статус дополнения: требования подтверждены пользователем 8 сентября 2026 года, реализация разрешена.

## Цель

Администратор загружает каталог автомобилей из Excel с новыми характеристиками. Значения сохраняются вместе с характеристиками автомобиля, возвращаются API детальной карточки и отображаются на странице автомобиля. Строка характеристик в последнем импорте является источником истины для существующей комплектации: новые значения заменяют старые, а пустые очищают ранее сохранённые значения. Пустые характеристики на фронтенде не занимают место и не показываются.

## Новые колонки и модель данных

| Заголовок Excel | Поле `Specifications` | Изменение | Подпись в карточке |
| --- | --- | --- | --- |
| `Допустимая полная масса` | `full_weight` | Новый заголовок для существующего поля | `Допустимая полная масса` |
| `Колесная формула` | `wheel_formula` | Новое nullable-поле | `Колесная формула` |
| `Колесная база` | `wheel_base` | Новый заголовок для существующего поля | `Колесная база` |
| `Допустимая нагрузка на оси (передняя / задняя)` | `permitted_axle_loads` | Новое nullable-поле | `Допустимая нагрузка на оси (передняя / задняя)` |
| `Кабина` | `cabin` | Новое nullable-поле | `Кабина` |
| `Экокласс` | `emission_euro_class` | Новый заголовок для существующего поля | `Экокласс` |
| `Пассажировместимость` | `seats` | Новый заголовок для существующего поля | `Пассажировместимость` |
| `Допустимая полная масса (тягача / автопоезда)` | `permitted_gross_train_weight` | Новое nullable-поле | `Допустимая полная масса (тягача / автопоезда)` |
| `Подвеска (передняя / задняя)` | `suspension` | Новое nullable-поле | `Подвеска (передняя / задняя)` |
| `Топливные баки` | `fuel_tanks` | Новое nullable-поле | `Топливные баки` |

Для четырёх семантически совпадающих характеристик используются существующие поля, чтобы не создавать дубли в базе и карточке. Старые заголовки `Полная масса (кг)`, `Колёсная база (мм)`, `Экологический класс` и `Количество мест` продолжают поддерживаться.

Если в одной строке заполнены и новый, и старый заголовок одной характеристики, приоритет имеет непустое значение из нового заголовка. Пустая новая ячейка не должна затирать значение из старого заголовка.

## Функциональные требования

### Импорт из админки

1. Текущий сценарий загрузки каталога автомобилей через `POST /api/v1/catalog/upload` принимает `.xlsx` и `.xls` без изменения пользовательского потока.
2. Парсер распознаёт все десять заголовков из таблицы выше с точным учётом их текста.
3. Значения колонок характеристик необязательны. Пустые ячейки и штатные пустые маркеры импортируются как `NULL`.
4. Строковые значения очищаются от внешних пробелов, но их содержимое не разбирается и не пересчитывается. Составные значения, разделители и единицы измерения сохраняются без потери данных.
5. Добавление альтернативных заголовков для существующих полей реализуется без зависимости от порядка обхода словаря и без затирания непустого значения пустым.
6. Старые файлы каталога без новых колонок продолжают приниматься. Отсутствующие в таком файле характеристики считаются пустыми и очищают соответствующие значения существующей комплектации.
7. При повторной загрузке обновляются все поля характеристик, которые формирует парсер из `SPECIFICATIONS_MAPPING`, а не только десять полей из первоначального изменения. Пустое импортированное значение записывается как `NULL` и стирает ранее сохранённое значение. Upsert выполняется и тогда, когда все 57 импортируемых характеристик строки пусты.
8. Ограничивающий список `_REFRESHABLE_SPECIFICATION_COLUMNS` удаляется. Для конфликта по `complectation_id` каждое импортируемое поле получает значение из `excluded` без `coalesce`, `nullif` и сохранения старого значения.
9. Технический ключ `complectation_id` не обновляется. Поле `engine_feeding`, для которого в текущем шаблоне и `SPECIFICATIONS_MAPPING` нет источника, не считается импортируемым и не должно искусственно очищаться.
10. Импорт спецтехники, его шаблоны, API и таблицы не изменяются.

### Хранение и API

1. В таблицу `specifications` добавляются шесть nullable-колонок типа `String(100)`:
   `wheel_formula`, `permitted_axle_loads`, `cabin`,
   `permitted_gross_train_weight`, `suspension`, `fuel_tanks`.
2. Миграция создаётся следующей после актуальной ревизии `106`; downgrade удаляет только эти шесть колонок.
3. Для существующих записей обратное заполнение не требуется: новые колонки остаются `NULL`.
4. Репозиторий и ответ детальной карточки автомобиля передают шесть новых полей наряду с существующими характеристиками.
5. Контракт списка автомобилей не расширяется: новые значения нужны только детальной карточке.

### Карточка автомобиля

1. Тип данных детальной карточки дополняется шестью новыми nullable-полями.
2. Все десять характеристик выводятся с подписями из таблицы выше, если соответствующее значение присутствует.
3. Значения с уже указанными единицами показываются как импортированы, без автоматического разбиения на переднюю и заднюю части и без повторного добавления единиц измерения. Для числовых значений старых полей сохраняется историческое добавление `кг` или `мм`.
4. Для четырёх переиспользованных полей существующая строка карточки получает новую подпись; отдельная дублирующая строка не создаётся.
5. Для отсутствующих, пустых или состоящих только из пробелов значений строка характеристики не отображается.
6. Логика видимости секций карточки учитывает новые поля: секция отображается, если в ней есть хотя бы одна непустая характеристика.
7. Изменения выполняются только для desktop-интерфейса обычного каталога автомобилей при ширине viewport от 768 CSS-пикселей.

## Подтверждённая причина дополнения

- Парсер корректно преобразует `598 л.с.` из колонки `Модификация` в `horse_power="598"` и передаёт полный словарь из 57 импортируемых характеристик.
- Репозиторий обновлял при конфликте только десять полей из `_REFRESHABLE_SPECIFICATION_COLUMNS`; `horse_power` в список не входил, поэтому в базе оставалось старое значение `4.4hyb AT (598 л.с.) 4WD`.
- `coalesce(nullif(excluded.<поле>, ''), specifications.<поле>)` дополнительно сохранял старое значение вместо очистки пустым импортом.
- Одиночный и пакетный ingestion вызывали upsert только при `has_specifications=True`, поэтому полностью пустой снимок характеристик не мог очистить существующую запись.
- `engine_feeding` — единственное nullable-поле `Specifications` без источника в `SPECIFICATIONS_MAPPING`; оно не входит в импортный снимок и не очищается.

## Планируемые изменения

### Backend

- Расширить ORM-модель `Specifications` шестью новыми полями.
- Добавить Alembic-миграцию с ревизией после `106`.
- Расширить сопоставление колонок обычного автомобильного каталога.
- Добавить явное разрешение альтернативных заголовков для четырёх существующих полей с приоритетом нового непустого значения.
- Удалить `_REFRESHABLE_SPECIFICATION_COLUMNS` и обновлять при конфликте все поля, переданные парсером характеристик, включая значения `NULL`.
- Использовать один и тот же контракт полного обновления для одиночного и пакетного upsert; `complectation_id` и не представленные в импорте поля не обновлять.
- Проверить передачу новых значений через репозиторий и схему детальной карточки.
- Обновить регрессионные тесты одиночного и пакетного upsert: непустые значения заменяются, пустые очищаются, а ограничивающий список отсутствует.

### Frontend

- Расширить тип детальной карточки автомобиля.
- Добавить условные строки характеристик с пользовательскими подписями.
- Обновить вычисление видимости секций.
- Проверить карточку с полным набором новых значений и карточку без них в desktop-браузере.

## Тестовые сценарии

1. Файл только с десятью новыми заголовками: все непустые значения импортируются в ожидаемые поля.
2. Файл старого формата: существующие характеристики импортируются без регрессии.
3. В строке заполнены новый и старый варианты одного заголовка: сохраняется новый вариант.
4. Новый вариант пуст, старый заполнен: сохраняется старое значение.
5. Составные значения с `/`, запятыми, дефисами и единицами измерения сохраняются без преобразования.
6. Повторный импорт обновляет все импортируемые характеристики существующей комплектации, в том числе поля вне прежнего списка `_REFRESHABLE_SPECIFICATION_COLUMNS`.
7. Повторный импорт пустой ячейки или штатного пустого маркера записывает `NULL` и очищает ранее сохранённое значение.
8. Повторный импорт файла `AURUS.xlsx` заменяет прежнее значение `horse_power` строкой `598`, полученной из колонки `Модификация`; карточка больше не собирает строку из устаревшего `4.4hyb AT (598 л.с.) 4WD`.
9. Одиночный и пакетный методы upsert имеют одинаковое поведение при заполненных и пустых характеристиках.
10. Детальный API возвращает шесть новых полей и четыре значения, импортированные через новые альтернативные заголовки.
11. Карточка с заполненными характеристиками показывает все десять подписей и значения.
12. Карточка с частично заполненными характеристиками не показывает пустые строки, но сохраняет видимой секцию с непустыми данными.
13. Карточка без новых характеристик не показывает новые строки и не получает пустых секций.
14. Импорт и карточки спецтехники не меняются.

## Критерии готовности

- Все десять красных колонок `LB:LK` учитываются импортом обычного каталога автомобилей.
- Старые варианты четырёх заголовков остаются совместимыми и не создают дубли характеристик.
- Шесть новых значений сохраняются в `specifications` и доступны в детальном API.
- Повторный импорт полностью заменяет все характеристики, представленные в строке импорта: пустые значения очищают данные в `specifications`, непустые заменяют прежние.
- Значение `horse_power` из исправленного `AURUS.xlsx` после повторного импорта равно `598`, поэтому карточка показывает корректное значение двигателя без старого текста модификации.
- На карточке автомобиля отображаются только присутствующие значения с согласованными подписями.
- Составные значения отображаются без потери или искажения данных.
- Каталог спецтехники не затронут.
- Автоматические проверки, миграция, Docker-запуск, логи и ручной desktop-сценарий успешно проверены.
- Для дополнения создан отдельный merge request только в `test`; после обязательных проверок и review он объединён. Существующий `specs/337.md` остаётся единственным артефактом задачи 22170.

- Добавление новых фильтров, сортировок и поиска по характеристикам.
- Вывод новых характеристик в списке/плитке автомобилей.
- Разбор составных характеристик на отдельные числовые поля.
- Мобильный интерфейс для viewport уже 768 CSS-пикселей.
