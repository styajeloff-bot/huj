## Требования к корзине

1. Поле с явной связанной подписью «Количество ТС, шт.», заметной границей и удобными кнопками уменьшения/увеличения. Остаток «В наличии: N шт.» расположен рядом с управлением, обычным читаемым текстом не менее 14 px; без скрытия больших остатков.
2. По умолчанию допускается целое количество от 1 до актуального доступного остатка N. Ручной ввод, вставка и кнопки проходят одну нормализацию. Значение больше N заменяется N. Очистка поля автоматически возвращает 1; 0 и отрицательное значение тоже возвращают 1. Дробные значения нормализуются до целого вниз, затем применяются границы. Не отправлять промежуточное невалидное значение в расчёт или API.
3. Под количеством — button, визуально оформленный как гиперссылка «Указать больше доступного». По нажатию снимается ограничение складским остатком только у данной позиции. Отображается пояснение «Количество сверх наличия согласует поставщик» и действие «Ограничить наличием»; возврат в обычный режим приводит значение к остатку.
4. Режим сохраняется вместе с позицией корзины, переживает перезагрузку и перенос гостевой корзины. Предлагаемое поле — allow_overstock: bool, по умолчанию false. Режим и количество меняются атомарно.
5. «Любое количество» означает отсутствие бизнес-лимита по остатку и искусственного ограничения 100 для ТС. Сохраняется технический предел целого PostgreSQL Integer (2147483647) и проверка представимости денежных результатов. Переполнение даёт понятную ошибку, без усечения и записи частичных данных. Проверить остальные лимиты схем и калькулятора.
6. При нулевом остатке обычный режим не позволяет отправить позицию: значение 1 может оставаться в поле, рядом «Нет в наличии». Включение заказа сверх наличия позволяет запросить поставку по модели при доступности такого заказа. Проданный/чужой VIN не превращается в доступный автомобиль. При неизвестном остатке показывать «Остаток уточняется»; не подставлять выдуманный максимум.
7. Backend проверяет режим и актуальный остаток при изменении корзины и отправке заявки. При изменившемся остатке возвращает конфликт с актуальным остатком; UI предлагает привести количество к нему либо явно включить заказ сверх наличия. Не создавать заявку с молча изменённым количеством.
8. Калькулятор, сумма позиции и отправляемая заявка используют одно нормализованное количество. Изменение количества инвалидирует старый расчёт и пересчитывает его до отправки.
9. Область задачи — автомобили/ТС. Складские ограничения спецтехники и комплектов не ослабляются автоматически; общий CartItemCard должен сохранить их контракт. Перед реализацией проверить все пути заказа по модели и конкретному VIN.

## Предлагаемое хранение количества в заявке

В PostgreSQL, у позиции `application_vehicles`, а не у заявки целиком:

| Поле | Смысл |
| --- | --- |
| requested_quantity | Исходное количество при создании позиции из запроса клиента, неизменяемое для новых заявок |
| confirmed_quantity | Последнее подтверждённое поставщиком количество; NULL до первого подтверждения |
| quantity | Рабочее количество для существующих расчётов: confirmed_quantity, если заполнено, иначе requested_quantity |

Обновление confirmed_quantity и quantity — одна транзакция. Дублирование рабочего quantity служит текущим потребителям; не допускается независимое изменение трёх полей разными обработчиками. Инвариант централизуется в существующем application use case, ORM и SQL остаются в infrastructure/repositories, HTTP и ролевые зависимости — в presentation.

При создании фиксировать requested_quantity из принятого сервером запроса. Для старых позиций нельзя выдавать текущее количество за доказанный исходный запрос: requested_quantity оставить NULL, показывать «Исходное количество не зафиксировано», существующее quantity сохранить. confirmed_quantity также NULL, если подтверждение не доказано историей.

В существующую историю действий записывать старое/новое количество, автора, роль и время. Если для количества нет подходящей записи истории — расширить существующий механизм истории, без отдельной аналитической подсистемы. API публикует события в Kafka; запись в ClickHouse остаётся за event-worker.

## Интерфейс дилера и дистрибьютора

- В позиции заявки показать «Запрошено клиентом: X шт.» и «Подтверждено поставщиком: ещё не подтверждено / Y шт.».
- У назначенного дилера или дистрибьютора доступен интерфейс «Подтвердить и наполнить заказ»: подтверждённое количество, подбор конкретных машин со склада, предварительный пересчёт, сохранение и отмена. Изменение одного числа без возможности наполнить заказ не закрывает задачу.
- Предлагаемое ограничение: редактирование на этапе обработки поставщиком до передачи заявки лизинговой компании. Закрытые, отклонённые и уже переданные на финансирование позиции не изменять данным действием. Точные enum статусов связать с существующими guards перед реализацией.
- Подтверждение не ограничивать складским остатком: закупка под заявку является целью задачи. Значение 0 не использовать вместо существующего действия отказа.
- Изменение доступно только поставщику, которому назначена позиция; принадлежность и статус проверяются сервером, включая прямой запрос к API. Конкурентное изменение даёт конфликт, а не потерю чужих правок.
- После сохранения атомарно пересчитать цену позиции, итог заявки и зависимый расчёт с сохранением условий (срок, аванс, ставки, поддержка, опции). При невозможности пересчёта не сохранять частичный результат и показать ошибку.
- Обе цифры видны клиенту и участникам заявки. Подтверждённое количество используется в дальнейшем расчёте и формируемых представлениях; существующие выданные документы не переписываются задним числом.
- Запрос и подтверждение количества не создают фиктивные VIN, остатки или резервы. Фактический резерв продолжает учитывать только реальные ТС.

## Уточнение пользователя: наполнение заказа со склада

Требование из диалога 15.09.2026: поставщику необходим интерфейс наполнения заказа машинами с его текущего склада; изменение количества должно затрагивать все зависимые стоимости без регрессий.

### Состав поставки

- В интерфейсе подтверждения показывать исходный запрос, подтверждённое количество, подобранные машины и сколько ещё требуется подобрать. Предложение для заказа под закупку: можно подтвердить 10, подобрать 6 сейчас и видеть «Осталось подобрать: 4». Не считать неподобранные единицы зарезервированными или готовыми к отгрузке. Частичное наполнение не должно блокировать фиксацию обещанного количества.
- Список склада — таблица с множественным выбором, поиском по VIN и фильтрами по модели/комплектации, состоянию и складу. Показывать VIN, модель, комплектацию, цвет, год, цену и доступность. Использовать UUID машин; свободный ввод VIN не заменяет связь с реальной складской записью.
- Сервер ограничивает выбор складом и организациями, доступными данному поставщику по действующим правилам владения. Чужие, проданные и зарезервированные другим заказом машины недоступны. Подобранные в этот заказ остаются видимыми при повторном открытии.
- Подбирать машины, соответствующие позиции заказа; подмена модели/комплектации не выполняется неявно и использует существующее отдельное действие замены.
- Разрешены добавление, удаление и замена машин до фиксирующего этапа текущего процесса. Нельзя подобрать больше подтверждённого количества. При уменьшении количества ниже уже подобранного нужно явно выбрать, какие машины исключить; сервер не удаляет их произвольно.
- Новые машины после закупки можно добавить после их появления в доступном складе. Резервировать только реальные выбранные машины по действующему процессу резервирования. При удалении освобождать только резерв этого заказа, не затрагивая чужие обязательства.
- Сохранение состава, количества, связанных резервов (если действие их меняет), денежных результатов и истории согласовано в одной транзакции. Повтор запроса не создаёт дублей. При конкурентном захвате машины другим заказом — конфликт и откат всей операции.

### Модель данных и существующие VIN-пути

`backend/application/commands/application_vehicles/assign_vin.py` назначает один VIN/vehicle_id одной строке application_vehicles. Путь дистрибьютора принимает VIN строкой; это не готовый механизм множественного складского подбора.

Сохранить исходную позицию как владельца requested_quantity/confirmed_quantity и создать подчинённые связи состава поставки (предлагаемая таблица application_vehicle_allocations: UUID связи, application_vehicle_id, vehicle_id, автор и время). Точную интеграцию с существующим резервом определить до реализации после проверки схемы резервов. Каждая связь представляет одну физическую машину; количество подобранных вычисляется по активным связям, не хранится третьим независимо редактируемым числом.

Не копировать requested_quantity в каждую физическую машину и не умножать агрегат позиции повторно на число связей. Проверить и адаптировать существующие назначение/замену VIN, статусы, представления кабинетов, документы, события и резервирование к составу из нескольких машин. Не оставлять старый одиночный VIN-путь обходом нового контракта. Для старых записей переносить только доказанную связь с реальной машиной, без создания фиктивных единиц для quantity > 1.

## Целостность всех стоимостей

- Единственный авторитетный расчёт — серверный. Изменение количества или состава сначала даёт предварительный расчёт; сохранение проверяет актуальность данных и возвращает согласованную версию количества, состава и сумм. UI не показывает новый состав со старой итоговой суммой как сохранённый результат.
- Проверить полный граф зависимостей: цена единицы, стоимость позиции, общая стоимость ТС/заявки, оборудование, услуги, скидки, наценки, программы поддержки, аванс в процентах и рублях, сумма финансирования, ежемесячный платёж, общая сумма платежей, выкуп, проценты, НДС/возврат НДС и налоговая экономия — где соответствующие поля присутствуют в действующем расчёте.
- Не умножать каждый показатель линейно на новое количество: сохранять семантику разовой услуги и услуги на единицу, фиксированной и процентной скидки, режим аванса, округление и условия поддержки. Повторно запускать существующие формулы на новом составе/количестве.
- Подбор VIN сам по себе не должен молча заменять согласованную цену на текущую складскую. В предварительном расчёте показывать расхождения; изменение цены проводить через действующие права/действия ценообразования. Для будущих неподобранных единиц используется согласованная цена позиции. При необходимости индивидуальной цены конкретной машины она учитывается ровно один раз, вместе с оставшимся количеством, а не поверх полной стоимости позиции.
- Обновлять сохранённые расчёты/проекции всех участников и новые выгрузки/документы, которые используют изменяемую заявку. Ранее выданные документы не переписывать; запрещать передачу устаревшего расчёта дальше по процессу. Проверить потребителей событий и аналитические суммы, исключить двойной учёт агрегата и его состава.
- Ошибка пересчёта, неактуальная версия или невозможность резервирования откатывает всю операцию. Не оставлять новое quantity при старой сумме или новый резерв после отменённого сохранения.

### Дополнительные обязательные проверки

1. Запрос 10 → подтверждение 7 → подбор 5: исходный запрос 10, рабочее количество 7, подобрано 5, осталось 2; итог рассчитан на 7, не на 5, 12 или 35.
2. Подбор оставшихся двух машин завершает состав из 7 без повторного умножения сумм; повторное сохранение не меняет итог и не дублирует резерв.
3. Уменьшение 7 → 4 при пяти подобранных требует исключить конкретную машину; увеличение 4 → 8 создаёт потребность добора, не фиктивные VIN.
4. Машины с разными ценами, фиксированные/процентные скидки, наценки, разовые и поштучные опции, поддержка, оба режима аванса, округления: сверить серверные результаты с независимыми ожидаемыми значениями, а не только с тем же расчётным helper.
5. Интеграционные тесты сохранения и повторного чтения: одинаковые количество и суммы в клиентском, дилерском, дистрибьюторском представлениях, расчёте и итогах заявки; новые документы/экспорт используют текущую версию.
6. Конкурентный подбор одного VIN двумя заказами, устаревшая версия, ошибка расчёта и повтор запроса: не возникает двойного резерва или частичного сохранения.
7. Регрессии одиночного VIN, заказа по модели, смешанной заявки, старых заявок, резервирования и передачи в ЛК. Реальный браузерный сценарий: клиентский запрос → поставщик меняет количество и подбирает склад → клиент видит актуальные количество и суммы.

## Бронирование и замена машин — уточнение 15.09.2026

### Проверенные существующие механизмы

В application_vehicles ограничение UniqueConstraint(application_id, vehicle_id) не обеспечивает эксклюзивность между заявками. В application_vehicle_repository.py есть предварительная проверка vin_used_on_other и блокировка родительской заявки; в purchase_repository.py имеются блокировки физических машин. Проверка VIN перед записью сама по себе не является гарантией от гонки разных заявок. Это наблюдения исходников, не утверждение о воспроизведённом двойном резерве. Существующий процесс истечения резерва использует reserve_expires_at и статус позиции; его нужно согласовать с новым составом, а не запускать независимый конкурирующий механизм.

### Когда машина считается занятой

- Корзина и исходный запрос клиента — потребность, не эксклюзивный резерв. Несколько клиентов могут запросить одну модель; одна физическая машина не может одновременно быть подтверждена/активно закреплена за двумя заказами.
- Выбор чекбокса в открытой таблице — локальный черновик. При нажатии «Сохранить подбор» выбранные машины закрепляются за заявкой и резервируются. До сохранения UI явно сообщает, что наличие проверяется при сохранении.
- Заказ на 10 единиц с подобранными 6 резервирует ровно 6 реальных машин. Оставшиеся 4 — потребность к закупке, без фиктивного остатка и VIN.
- Одна активная запись владения резервом на vehicle_id для всех коммерческих путей: подбор, назначение/замена VIN, покупка, ручное действие сотрудника, подтверждение поставщика. Не создавать изолированный лизинговый реестр, который игнорирует существующие продажи.

### Серверная и БД-защита

Предлагаемая реализация: единый PostgreSQL-реестр резервов с vehicle_id (UUID), владельцем заказа/позиции, статусом, сроком, автором и временем, связанный с составом поставки. До реализации проверить возможность расширить существующий механизм, чтобы не оставить два источника владения. Ограничение БД — UNIQUE(vehicle_id) для активного состояния резерва (частичный уникальный индекс). Исторические завершённые резервы не мешают повторной продаже освобождённой машины.

Каждое изменение выполняется через общий прикладной контракт: блокировка заявки, затем её позиций, затем физических машин в стабильном порядке UUID; единый порядок соблюдать также в покупке, замене и обработчике истечения. Под блокировкой повторно проверить права, статус машины, активный резерв, срок и версию заявки. Уникальное ограничение — последняя защита, конфликт преобразуется в HTTP 409. UI получает список недоступных выбранных машин и сохраняет остальные черновые выборы; частичное сохранение без явного действия пользователя не выполняется.

vehicle.status остаётся согласованным с коммерческим состоянием, но сам по себе не хранит владельца резерва. Продажа допускается только в рамках соответствующего резерва/разрешённого процесса; чужой резерв не снимается изменением строки статуса. Повтор сохранения идемпотентен. События и уведомления не должны сообщать об успехе откатившейся транзакции; использовать действующий механизм доставки после успешной фиксации.

### Срок и освобождение

- Срок резерва показывается в заявке и списке состава. Использовать действующий бизнес-срок/правило даты окончания, не вводить произвольный новый срок. Продление — отдельное действие уполномоченного поставщика с историей.
- Истечение снимает только активный резерв этой машины у этого заказа. Обработчик повторно проверяет срок и версию под блокировкой, чтобы не снять продлённый резерв. Время само не исключает строку из уникального индекса: требуется явный переход состояния; проверять просроченность и при попытке нового захвата, а не полагаться только на расписание worker.
- При истечении машина перестаёт входить в активный подобранный состав, остаётся в истории; заявка показывает нехватку и требует повторного подбора. Исходный запрос и обещанное количество не уменьшаются автоматически. Шаг процесса, требующий обеспеченности резервом, блокируется.
- Отмена заявки/отказ от позиции и явное исключение машины освобождают только принадлежащие им резервы. Завершённая продажа переводит машину в проданное состояние и не возвращает её в доступные при очистке резервов.
- До включения ограничения проверить старые активные назначения и резервы. При конфликтах не выбирать победителя автоматически: миграция выдаёт конкретные конфликтующие записи для разбора, не теряет существующие обязательства.

### Работа пользователя при замене

1. В составе заявки у каждой машины видны VIN, модель/комплектация, согласованная цена, состояние резерва и срок; доступны «Заменить» и «Исключить» в разрешённых статусах.
2. «Заменить» открывает доступный склад поставщика. Старая машина остаётся в составе и в резерве, пока пользователь выбирает новую. Отмена окна ничего не меняет.
3. После выбора показать «Было / станет»: VIN, характеристики, цену и изменения итоговой стоимости, аванса и платежа. Запросить причину замены; отклонение модели/комплектации проходит явный существующий процесс согласования замены, а не скрывается за заменой VIN.
4. «Сохранить замену» выполняет атомарную операцию: занять новую машину, обновить состав и расчёт, освободить старую, записать историю. Проверки и пересчёт выполняются до commit; при любой ошибке старая машина и её резерв остаются, новый резерв не сохраняется.
5. При замене одна на одну requested_quantity и confirmed_quantity не меняются. Цена не подменяется молча складской ценой; согласованное изменение цены отображается до сохранения и пересчитывается сервером. История содержит старую/новую машину, цену, автора, причину и время.
6. Исключение машины освобождает резерв и увеличивает «Осталось подобрать», но не уменьшает обещанное количество автоматически. Уменьшить подтверждённое количество — отдельное явное действие с полным пересчётом.
7. После передачи в ЛК обычная замена заблокирована согласно текущему предложению о статусах. Не менять состав под уже согласованным расчётом/документами: если потребуется замена на этом этапе, это отдельный явно согласованный возврат на пересогласование, без расширения данной задачи по умолчанию.

### Проверки защиты от двойного использования

- Два независимых соединения PostgreSQL одновременно резервируют одну машину для разных заявок: ровно один успех, другой 409; в БД один активный резерв. Проверка выполняется интеграционно, не на mock-репозитории.
- Подбор конкурирует с покупкой, старым назначением VIN и ручным действием сотрудника: ни один путь не обходит эксклюзивность.
- Замена A → B при занятой B или ошибке пересчёта сохраняет A, её резерв, состав и старые суммы полностью.
- Успешная замена A → B освобождает только A, занимает только B, сохраняет количество и согласованные суммы; повтор запроса не дублирует историю/резерв.
- Истечение одновременно с продлением, заменой или продажей не снимает новый/продлённый резерв и не возвращает проданную машину в наличие.
- Закрытие окна, ошибка сети и повтор операции не оставляют «зависшие» резервы; после неопределённого сетевого результата UI перечитывает состояние операции/заявки, а не объявляет откат без проверки.

## Текущий статус машины в БД и всех складах

Уточнение пользователя: у каждой машины должен быть текущий статус «Куплена», «Забронирована» или «На складе», видимый дилеру, дистрибьютору и администратору в существующих складских интерфейсах.

### Единый контракт

В текущей ORM Vehicle уже есть nullable status с default available; домен допускает available/reserved/sold. Расширять существующий контракт, не создавать параллельный purchase_status или отдельный статус для каждой роли.

| Код в vehicles.status | Текст во всех интерфейсах склада | Значение |
| --- | --- | --- |
| available | На складе | Свободна от коммерческого резерва и не продана |
| reserved | Забронирована | Имеет действующий эксклюзивный резерв за заказом |
| sold | Куплена — только при доказанном завершении покупки | Сейчас код также используется на этапе ожидания оплаты; уточнение ниже обязательно |

«Куплена» означает продажу конечному покупателю, а не закупку поставщиком для пополнения своего склада. Приём закупленной поставщиком машины на склад не помечает её sold.

Перед миграцией проверить реальные NULL/неизвестные статусы и противоречия с продажами/резервами. По доказанным данным привести значения к каноническим, затем закрепить NOT NULL и CHECK допустимых значений в БД. Не назначать available по умолчанию всем неизвестным записям: спорные случаи требуют разбора, а не освобождения машины. Здесь проверена ORM, состояние живой БД пока не исследовано.

is_available не использовать как второй независимо редактируемый коммерческий статус: проверить его существующую семантику публикации/видимости и сохранить её. Доступность подбора и публичный остаток учитывают канонический статус, активный резерв и действующие ограничения видимости/склада.

### Переходы

- Сохранение подбора создаёт резерв и меняет available → reserved в одной транзакции.
- Отмена, исключение, успешная замена или истечение освобождают принадлежащий заказу резерв и меняют reserved → available, только если машина не продана и нет другого действующего обязательства.
- Целевое отображение «Куплена» требует подтверждения завершённой покупки. Текущий путь full_purchase устанавливает sold уже при создании заказа, в том числе до callback оплаты. Нельзя менять этот момент изолированно или представлять текущий sold как доказательство оплаты. Сохранение кодов и текущей блокировки покупки обязательно; для pending-заказа UI должен уточнять «Ожидает оплаты» по коммерческому заказу. Нормализация pending-покупки в reserved допустима только после согласованной адаптации всего платёжного цикла и соответствующих тестов. Создание лизинговой заявки/подтверждение количества не означает покупку.
- sold нельзя сбрасывать через обычное редактирование карточки, массовое обновление, импорт или обработчик истечения. Импорт каталога не освобождает резервы и не возвращает купленные машины в продажу.
- Ручные действия администратора используют те же проверки владения резервом и историю; dropdown не должен обходить коммерческий процесс. Все обновления статуса и реестра резервов согласованы.

### Риски, требующие корректировки реализации

1. **Ожидание оплаты уже может быть sold.** purchases.py:_create_single_order вызывает target_vehicle_status без зависимости от use_gateway; full_purchase получает sold до платёжного callback. Успешный callback закрепляет sold, неуспешный и timeout могут возвращать available. Сохранить текущую недоступность ожидающего оплаты автомобиля и платёжные контракты; не вводить правило «sold никогда не освобождается» для ещё неоплаченного отменённого заказа. Завершённую продажу отличать от временного захвата покупкой.
2. **Освобождение без нового владельца.** payment_gateway.py (failure/timeout), purchases.py (отмена/reclaim) обновляют status напрямую. После появления реестра резерва каждый такой путь должен освобождать только собственное обязательство, а поздний callback старого платежа не должен менять машину нового владельца. Это обязательная часть задачи, а не будущий отдельный фикс.
3. **Лизинговый резерв сейчас отдельный.** dealer_action reserve изменяет car_status позиции; release_expired_reservation очищает статус/срок позиции, не выполняя освобождение физической машины. Новый состав/резерв нужно подключать согласованно к этим use cases, не считать старые confirmed автоматически полноценными эксклюзивными резервами.
4. **Проверка VIN учитывает историю.** vin_used_on_other ищет VIN во всех других строках application_vehicles без фильтра активного обязательства. При переходе к истории состава оставить такую проверку без изменения нельзя: освобождённый VIN может навсегда блокироваться старой заявкой. Активный резерв — защита эксклюзивности, историческая запись — только история.
5. **Повторный импорт меняет доступность.** catalog_parser.py:738–739 подставляет available/true при отсутствии статуса; catalog_repository.update_vehicle_by_id/by_vin разрешают перезапись обоих полей. data_import._upsert_vehicle тоже задаёт статус/флаг. В новом контракте импорт описания/цены не может снимать коммерческое обязательство; оба пути требуют проверки и тестов. Сохранить предназначенные для оператора изменения доступности, отличая их от технических defaults импорта.
6. **Ручная карточка — ещё один writer.** update_vehicle.py проверяет допустимость итоговой сущности, но не применяет compute_status_after_bulk_update; bulk-guard запрещает выход из sold, но сам по себе не защищает reserved от освобождения. Единый контракт обязан охватить оба пути.
7. **Фронтенд уже имеет тест именно 21924.** cart-vehicle-quantity-21924.test.ts закрепляет безусловное снятие max для автомобилей (коммит c3a01a43). Новое требование сознательно меняет это поведение: заменить этот тест проверками двух режимов и реального пользовательского ввода, не сохранять несовместимое старое ожидание.
8. **Склад уже возвращает status.** warehouse_repository.list_warehouse_vehicles выдаёт поле status и все привязанные машины без фильтра available. Доработка колонки не требует переопределять смысл складской принадлежности. available не доказывает физическую привязку к складу; проверять VehicleWarehouse и видимость отдельно.

## Критерии готовности

- При N=3 ввод 5 без включённого режима даёт 3; кнопка увеличения не превышает 3; очистка даёт 1; одинаковые результаты при вставке и клавиатурном вводе.

- Нулевой/неизвестный остаток, смена остатка между расчётом и отправкой, дроби, отрицательные числа, большие значения и переполнение обработаны предсказуемо.
- Для новой заявки 5 → подтверждение 4 сохраняет requested_quantity=5, confirmed_quantity=4, quantity=4; повторное подтверждение 6 оставляет requested_quantity=5 и сохраняет историю.
- Чужой поставщик, клиент и запрещённый статус не позволяют изменить подтверждение через UI или прямой API; конкурентные правки не теряются.
- Суммы и расчёт соответствуют рабочему количеству; ошибка пересчёта откатывает изменение.
- Старые заявки сохраняют прежние суммы/количество; не получают выдуманной истории исходного запроса.
- Нет регрессии резервов/VIN, спецтехники, комплектов, гостевой корзины и расчёта опций/поддержки.
