# Bitrix 22128: доработки каталога спецтехники

## Источник и цель

Источник требований — задача Bitrix 22128 «ТЗ: Доработки каталога спецтехники» и приложенный пользователем DOCX от 24.08.2026.

Цель — завершить публичный и административный сценарии каталога спецтехники: расширить фильтрацию и карточку объявления, корректно отображать надстройки в лизинговых заявках, улучшить наследование характеристик и синхронизировать новые поля с XLSX-шаблоном импорта.

## Подтверждённое текущее состояние

- Публичный каталог уже поддерживает общий поиск, статические и динамические фильтры, но на desktop фильтры постоянно открыты в боковой панели.
- Общий поиск включает код, описание, марку, модель и модификацию. Отдельных условий «содержит в описании» и «не содержит в описании» нет.
- Динамические характеристики уже вычисляются с учётом текущей категории и её предков.
- Связь категории с характеристикой уже содержит флаг `is_visible` с подписью «На карточке» и `sort_order`, но публичная плитка объявления эти характеристики не показывает и ограничение в шесть характеристик не проверяется.
- Количество доступных единиц уже вычисляется как `available_count`: одинаковые физические объявления объединяются в одно публичное предложение. Отдельное редактируемое поле количества противоречило бы текущей модели резервирования одной физической единицы.
- У объявления спецтехники нет связи со складом. Справочник складов уже существует и используется для автомобилей.
- Публичный контракт уже возвращает комплектацию (`trim`), однако категория и комплектация не оформлены на плитке как отдельные характеристики.
- Общий компонент состава лизинговой заявки строит ссылку для любой позиции спецтехники, поэтому по надстройке сейчас можно перейти в самостоятельное объявление.
- XLSX v2 уже передаёт настройку «В карточке» и порядок на листе характеристик категорий, но не поддерживает ссылки на изображения, склад и специальную цену.

## Функциональные требования

### 1. Фильтры каталога

1. На всех поддерживаемых ширинах от 768 CSS-пикселей фильтры открываются кнопкой «Все фильтры» в drawer/dialog. Постоянная desktop-панель фильтров удаляется.
2. Общий поиск по каталогу остаётся самостоятельным полем над результатами.
3. В «Все фильтры» добавляются два независимых текстовых поля:
   - «Поиск по описанию» — оставить объявления, описание которых содержит строку без учёта регистра;
   - «Исключить из описания» — исключить объявления, описание которых содержит строку без учёта регистра. Объявления без описания не исключаются.
4. Параметры добавляются в URL и в оба публичных запроса: список объявлений и фасеты. Список и счётчики фасетов всегда строятся по одинаковым условиям.
5. Все существующие статические и динамические фильтры сохраняются внутри «Все фильтры».
6. Динамическая характеристика показывается только в контексте категории, для которой она эффективна с учётом наследования и имеет признак «В фильтре». На корневой странице каталога динамические фильтры не показываются.
7. Активные значения обоих новых фильтров отображаются в чипах, сбрасываются отдельно и очищаются общим действием «Сбросить».

### 2. Переходы из лизинговой заявки

1. Переход на самостоятельное объявление недоступен для надстройки, добавленной дочерней позицией к основной технике.
2. То же правило применяется к небазовому компоненту составного объявления.
3. Основная техника и базовый компонент сохраняют переход, если объявление доступно по публичному маршруту.
4. Решение реализуется через явный безопасный `detail_url` в нормализованной проекции позиции заявки. Для надстройки backend возвращает `null`, а frontend не рисует ссылку и не создаёт кликабельный overlay.
5. Изменение технически выполнимо без миграции данных: роль позиции и признак базового компонента уже сохраняются. Оценка трудоёмкости этой части — малая, затрагиваются проекция ответа, тип frontend, общий компонент списка и регрессионные тесты.

### 3. Наследование характеристик категорий

1. После выбора родительской категории форма создания/редактирования сразу показывает эффективные группы и характеристики всех выбранных родителей.
2. Наследуемые связи визуально отличаются от прямых и не дублируются в дочерней категории.
3. Пользователь может добавить прямую настройку или переопределить разрешённые поля существующего правила в дочерней категории.
4. Backend остаётся источником истины и вычисляет эффективный набор по всему DAG категорий. Изменение родителя немедленно влияет на потомков; снимки у дочерних категорий не создаются.
5. Циклы, неизвестные родители и несовместимые наборы по-прежнему отклоняются до сохранения.

### 4. Склад и количество

1. Каждая физическая единица спецтехники получает необязательную связь `warehouse_id` с существующим справочником складов.
2. При выборе склада backend проверяет его существование и, если у склада задан владелец, совместимость владельца с продавцом объявления.
3. Одинаковые физические объявления продолжают объединяться в публичное предложение. Backend возвращает:
   - общее `available_count`;
   - `warehouse_stock` — список складов с количеством доступных физических единиц в каждом складе.
4. Плитка и детальная карточка показывают общее количество и склад. Если предложение распределено по нескольким складам, показывается список складов с количеством по каждому.
5. Для статуса «Под заказ» отсутствие склада допустимо; интерфейс явно показывает «Под заказ» и не выдумывает складской остаток.
6. Отдельное редактируемое поле количества не добавляется: количество вычисляется из числа доступных физических единиц. В XLSX каждая физическая единица остаётся отдельной строкой с уникальным кодом. Это сохраняет действующие гарантии резервирования и продажи конкретной единицы.

### 5. Категория, комплектация и характеристики на плитке

1. Backend возвращает для публичного предложения `terminal_category`:
   - в контекстном каталоге — последнюю категорию подтверждённого `category_path`;
   - без контекста — основную конечную категорию модификации;
   - если основную категорию определить нельзя, значение равно `null`, без выбора случайной категории.
2. Плитка объявления отдельными подписями показывает конечную категорию и название комплектации. Существующее значение `trim` переиспользуется.
3. На плитке выводятся заполненные характеристики, для которых эффективная связь категории имеет «На карточке».
4. Характеристики сортируются по порядку группы, затем по `sort_order`, названию и UUID для стабильного результата.
5. В одной модификации допускается не более шести эффективных характеристик «На карточке» по объединению её категорий и наследуемых правил.
6. Frontend показывает счётчик выбранных характеристик и блокирует очевидное превышение. Backend авторитетно проверяет лимит при изменении связей категории, родителей категории, категорий модификации и при импорте.
7. Публичный ответ содержит не более шести заполненных значений; пустые значения не выводятся.

### 6. Специальная цена

1. У объявления добавляется необязательная `special_price` типа `Decimal`.
2. Специальная цена допустима только при заданной обычной цене, должна быть больше нуля и строго меньше обычной цены. Проверка действует в HTTP API, домене, БД и импорте.
3. Поле добавляется в создание и редактирование объявления в административном каталоге.
4. На публичной плитке и детальной карточке при наличии специальной цены:
   - обычная цена показывается зачёркнутой;
   - специальная цена становится основной;
   - показывается метка «Спецпредложение».
5. Сортировка, фильтрация по цене, группировка одинаковых предложений, корзина, заявка и расчёт покупки/лизинга используют эффективную цену `special_price ?? price`, чтобы показанная и оплачиваемая стоимость не расходились.

### 7. XLSX-шаблон и импорт

1. Исходная версия повышается до v3; последующее расширение полного контракта комплектациями и цветами выпускается как v4. Уже выданные v1–v3 продолжают распознаваться без изменения их точных заголовков.
2. В лист «Объявления» добавляются поля:
   - «Специальная цена»;
   - «ID склада»;
   - «Ссылка на изображение».
3. В лист «Категории» добавляется поле «Ссылка на изображение».
4. Существующие поля «В карточке» и «Порядок» сохраняются и проходят новую проверку лимита шести эффективных характеристик на модификацию.
5. Ссылка задаёт одно основное изображение. В режиме PATCH пустая ячейка не меняет изображение, значение «Очистить» удаляет основное изображение, URL создаёт или заменяет основное изображение. Дополнительные изображения объявления не удаляются.
6. Разрешены только HTTPS-источники из настроенного allowlist. Загрузка использует существующую SSRF-защищённую проверку DNS/IP, лимиты размера и пикселей, декодирование JPEG/PNG/WebP и сохранение оптимизированного WebP во внутреннее хранилище.
7. Импорт валидирует склад, совместимость продавца, специальную цену и лимит характеристик до применения. Ошибки содержат лист, строку и поле без раскрытия storage key или исходного URL в логах/ответах.
8. В v4 добавляются листы «Комплектации», «Характеристики комплектаций», «Значения комплектаций» и «Цвета». Комплектация идентифицируется парой «Код модификации» + «Код комплектации», потому что её код уникален только внутри модификации. Короткое имя листа значений соблюдает лимит Excel в 31 символ.
9. Лист «Объявления» v4 дополнительно содержит «Код комплектации», «Код цвета кузова» и «Код цвета салона». Ссылки разрешаются по стабильным кодам, а не по UUID.
10. Импорт проверяет принадлежность активной комплектации выбранной модификации, допустимость характеристик комплектации, типизированные значения, активность цвета и его применимость к кузову или салону.
11. Импорт применяет те же авторитетные ограничения, что management API: не обходит commerce-owned переходы продажи и архивирования, не оставляет модификацию без категорий, проверяет зависимости графа характеристик и полное финальное состояние затронутых опубликованных объявлений.
12. FULL_SNAPSHOT учитывает комплектации, цвета, связи и значения комплектаций: отсутствующие справочники деактивируются, отсутствующие связи и значения удаляются в безопасном порядке.
13. Генератор шаблона, парсер, preview, apply и инструкции в XLSX обновляются согласованно. Ошибки новых полей содержат лист, строку и название колонки.

## Планируемые изменения

### Backend и БД

- Добавить Alembic-миграцию для `special_equipment_products.warehouse_id` и `special_price`, внешнего ключа, ограничений и индексов.
- Расширить доменные проверки специальной цены и лимита карточных характеристик.
- Расширить management-схемы, команды и repository для склада и специальной цены.
- Добавить параметры включения/исключения описания в публичные router/query/repository контракты.
- Расширить публичную проекцию предложения полями `warehouse_stock`, `terminal_category`, `card_attributes`, `price` и `base_price`/`special_price` без неоднозначной трактовки эффективной цены.
- Расширить проекцию позиций лизинговой заявки безопасным `detail_url`.
- Обновить XLSX-контракт до v4, генератор, нормализацию, preview/apply и перенос изображений; сохранить точный разбор v1–v3.
- Добавить в импорт справочники комплектаций и цветов, связи и значения характеристик комплектаций и ссылки объявления на комплектацию и цвета.

### Frontend

- Заменить постоянную desktop-панель единым drawer/dialog «Все фильтры» и сохранить доступность клавиатуры, focus trap, Escape и возврат фокуса.
- Добавить два фильтра описания, URL-сериализацию, чипы и сброс.
- Показать наследуемые правила в форме категории и лимит карточных характеристик.
- Добавить выбор склада и специальную цену в форму объявления.
- Обновить плитку и детальную карточку: склады, количество, конечная категория, комплектация, до шести характеристик и спецпредложение.
- Использовать серверный `detail_url` в составе заявки и не создавать ссылку для надстроек.

## Тестирование

### Backend

- Unit-тесты доменных правил: специальная цена, лимит шести характеристик, наследование из нескольких родителей.
- Integration-тесты публичных endpoints: включение/исключение описания, одинаковые условия для listing/facets, terminal category, card attributes, складские остатки и effective price.
- Integration-тесты management API: склад, специальная цена и проверки лимита.
- Регрессия проекции лизинговой заявки: основная техника кликабельна, надстройка и небазовый компонент получают `detail_url = null`.
- Тесты XLSX: точные заголовки и инструкции v4, неизменность v1–v3, parser/preview/apply, комплектации, цвета, очистка и замена изображения, ошибки склада, цены, лимита и parity с management-защитами.
- Проверки миграции upgrade/downgrade и существующих строк с `NULL` в новых необязательных полях.

### Frontend

- Architecture/Vitest-тесты query parse/serialize, состава фильтров, лимита шести характеристик, безопасного `detail_url`, цены, полей карточки и загрузки актуального шаблона v4.
- Ручной browser smoke в desktop Chromium при ширине не менее 768 CSS-пикселей:
  - открыть и закрыть «Все фильтры» мышью и клавиатурой;
  - применить оба фильтра описания и динамический фильтр категории;
  - проверить URL, чипы, сброс и отсутствие фильтров чужой категории;
  - проверить карточку со складом, несколькими складами, комплектацией, характеристиками и специальной ценой;
  - проверить отсутствие перехода по надстройке из клиентской и LC-версии заявки;
  - проверить создание/редактирование объявления и наследование категории в админке.

## Критерии готовности

1. Все десять требований исходного DOCX покрыты реализацией и тестами.
2. Listing и facets дают согласованные результаты для новых и старых фильтров.
3. Надстройка в лизинговой заявке не имеет кликабельного перехода, а основная техника не теряет его.
4. Наследуемые характеристики видны при выборе родителя и не копируются в дочернюю категорию.
5. Публичная плитка и детальная карточка показывают складской остаток, конечную категорию, комплектацию и не более шести выбранных характеристик.
6. Специальная цена одинакова во всех публичных, корзинных, заявочных и платёжных расчётах.
7. XLSX v4 импортирует склад, специальную цену, основные изображения объявления/категории, комплектации, их характеристики и значения, цвета кузова и салона; v1–v3 остаются совместимыми.
8. Обязательные backend-проверки, frontend-тесты, Docker-логи и browser smoke зелёные.
9. Создан MR в `test`, спецификация переименована в номер MR и MR объединён после обязательных проверок и review.

## Вне объёма

- Отдельный мобильный сценарий для viewport уже 768 CSS-пикселей.
- Ввод агрегированного количества одной строкой объявления и изменение модели резервирования физических единиц.
- Импорт нескольких дополнительных изображений из одной ячейки; требование покрывается одной ссылкой на основное изображение.
- Изменения каталога автомобилей, кроме переиспользования существующего справочника складов.

## Регрессионный багфикс: сохранение категории при историческом превышении лимита

Merge request багфикса: [!326](https://gitlab.carcraft.ru/carcraft/carcraft-leadgenerator/-/merge_requests/326).

### Проблема и причина

Создание или редактирование любой категории может завершиться ошибкой «Для карточки модификации можно выбрать не более 6 характеристик», даже если в изменяемой категории выбрано не более шести характеристик или не выбрано ни одной. Причина в том, что management-команда после изменения категории повторно проверяет все модификации каталога. Поэтому историческое превышение лимита в несвязанной ветке блокирует текущую операцию.

### Требования

1. Изменение категории проверяет лимит карточных характеристик только у модификаций, на которые это изменение способно повлиять: назначенных самой категории либо любому её потомку в итоговом графе.
2. Каждая затронутая модификация проверяется по полному набору назначенных ей категорий, включая наследование из нескольких веток и объединение одинаковых характеристик.
3. Историческое превышение лимита в несвязанной ветке не блокирует создание, редактирование родителей или замену характеристик текущей категории.
4. Превышение лимита у затронутой модификации по-прежнему отклоняется с действующим текстом ошибки и HTTP 422.
5. Авторитетным остаётся доменное правило `ensure_card_attribute_limit`; подсчёт выполняется по уникальным видимым `attribute_id`, а группа характеристик не считается характеристикой.
6. Исправление не меняет HTTP-контракты, frontend, схему БД и существующие данные.

### Планируемые изменения

- Добавить чистую доменную проверку изменения категории: вычислить область влияния «категория + все потомки» и применить существующий лимит только к связанным модификациям.
- Сохранить orchestration и чтение repository в application-слое; новые repository-методы и SQL-запросы не добавлять.
- Использовать итоговый граф категорий после применения новых родителей и полный снимок правил с подстановкой изменяемых связей.
- Удалить глобальную проверку всех модификаций из `_validate_category_attributes`.

### Тестирование багфикса

- Регрессионный command-тест: создание пустой несвязанной категории проходит при существующей модификации с историческими 15 видимыми характеристиками.
- Domain-тесты: несвязанное превышение пропускается; превышение у напрямую связанной модификации и у модификации в дочерней категории отклоняется.
- Проверить модификацию с несколькими категориями по полному объединению её эффективных характеристик.
- Сохранить зелёными существующие сценарии «7 отклоняется / 6 сохраняется» и допустимое редактирование объявления с историческим превышением.
- Выполнить обязательные backend-проверки, Docker build/up, просмотр логов и локально подтвердить исправленный сценарий.

### Критерии готовности багфикса

1. Локальный сценарий из дефекта проходит: новая категория без характеристик сохраняется при несвязанной исторической модификации с 15 видимыми характеристиками.
2. Реальное превышение лимита в затронутой ветке по-прежнему блокируется.
3. Изменение покрыто регрессионными тестами, обязательные проверки зелёные.
4. Создан MR в `test`, pipeline и обязательный review пройдены, после чего MR объединён.
