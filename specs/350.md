# Единые структурированные JSON-логи и локальный просмотр в Grafana

## Контекст

- Внутренняя техническая задача без Bitrix: изменение не влияет на
  пользовательские бизнес-функции, но должно упростить разработку,
  эксплуатацию и поиск причин ошибок.
- Основной рабочий сценарий — просмотр всех логов тестового окружения в
  Grafana/Loki по Kubernetes namespace `carcraft-leadgenerator-test`.
- Экспорт
  `/Users/a_belianskii/Downloads/Logs-2026-09-03 15_18_22.txt` содержит 5000
  строк за 32 минуты 48 секунд и представляет только 4,56% выбранных 12 часов.
- В этом экспорте 4860 строк (97,2%) не содержат распознаваемого уровня и
  отображаются в Grafana как `unknown`.
- 2313 строк (46,3%) — технические `repository_query`, которые создаются для
  каждого вызова функции репозитория независимо от длительности и результата.
- Каждый из 265 HTTP-запросов записан дважды: стандартным `uvicorn.access` и
  `RequestTimingMiddleware`.
- Не менее 1236 строк (24,7%) относятся к отладочному выводу AWS SDK. В 25
  строках присутствует подписанный заголовок `Authorization`, который не должен
  попадать в централизованные логи.
- В одной ленте без явного источника смешаны FastAPI, event-worker, Taskiq
  worker/scheduler, Nginx, PostgreSQL, Redis, ClickHouse и Redpanda.
- Текущий `CompactLogFormatter` намеренно оставляет только текст сообщения и
  удаляет уровень и имя логгера. Существующие тесты закрепляют этот контракт.
- Локальная compose-конфигурация не содержит Loki и collector, а имеющийся
  Grafana datasource настроен только на Prometheus. Поэтому визуально проверить
  итоговый вид логов локально сейчас невозможно.

## Цель и ожидаемый результат

Все процессы должны выдавать однострочные, безопасные и однозначно
атрибутированные события. При просмотре namespace в Grafana для каждой строки
должны быть сразу видны:

- уровень события и соответствующий ему цвет;
- сервис и компонент, создавшие событие;
- понятное действие и его результат, а не только имя Python-функции;
- идентификатор запроса или фоновой операции, по которому можно восстановить
  связанную цепочку;
- основные диагностические поля: HTTP-метод, шаблон маршрута, статус,
  длительность, имя задачи или топик.

Обычная лента должна содержать только итоговые события границ системы,
значимые этапы бизнес-процессов, предупреждения и ошибки. Массовые технические
измерения должны находиться в метриках, trace или диагностическом режиме, а не
перегружать INFO-логи.

После реализации должен существовать локальный opt-in сценарий, который
запускает приложение вместе с Loki, collector и Grafana, создаёт безопасные
тестовые события и позволяет пользователю визуально проверить итоговую ленту,
фильтры и цвета до серверного развёртывания.

## Выбранное решение

Использовать единый структурированный JSON-контракт для процессов, которыми
владеет приложение, и нормализацию native-логов инфраструктурных контейнеров в
collector.

Формат хранения и формат показа разделяются:

- процесс пишет одну JSON-запись в stdout;
- collector добавляет метаданные окружения, нормализует native-форматы и
  отправляет записи в Loki;
- Grafana через LogQL `line_format` показывает короткую человекочитаемую строку;
- цвет определяется нормализованным полем/label `level`, а не поиском случайных
  слов в `message`.

OpenTelemetry и Tempo в эту задачу не входят. Поля `trace_id` и `span_id`
резервируются в схеме, чтобы последующее подключение трассировки не потребовало
смены формата логов.

## Контракт прикладного события

Каждая запись приложения является одним валидным JSON-объектом на одной строке.
Переносы строк в сообщении и stacktrace экранируются JSON-сериализатором и не
создают дополнительные Loki events.

Обязательные поля:

- `timestamp` — UTC в формате RFC 3339 с миллисекундами;
- `schema_version` — целая версия контракта, начальное значение `1`;
- `level` — одно из `debug`, `info`, `warning`, `error`, `critical`;
- `service_name` — стабильное имя процесса;
- `component` — низкокардинальная функциональная область внутри сервиса;
- `event` — стабильное имя события в lower-case dotted notation;
- `message` — короткое описание, понятное человеку;
- `environment` — `local`, `test` или другое значение из настроек окружения;
- `service_version` — версия/commit развёрнутого приложения, если передана
  окружением, иначе явное безопасное значение `unknown`.

Опциональные поля контекста:

- `request_id`, `correlation_id`, `trace_id`, `span_id`;
- `task_id`, `task_name`, `job_id`, `attempt`;
- `http_method`, `http_route`, `http_status_code`, `duration_ms`;
- `topic`, `partition`, `offset`, `consumer_group`, `batch_size`;
- `dependency`, `operation`, `result`;
- `error_type`, `error_message`, `stacktrace`;
- `code_module`, `code_function`, `code_line` для раскрываемых технических
  деталей, но не для основного текста и не для агрегаций.

Пример записи приложения:

```json
{"timestamp":"2026-09-03T12:17:48.381Z","schema_version":1,"level":"info","service_name":"carcraft-api","component":"http","event":"http.request.completed","message":"GET /api/v1/notifications -> 200 in 6.83 ms","environment":"local","service_version":"a1a1d060","request_id":"7c8e64ba-9730-40e5-b2c5-fcf650705b18","correlation_id":"7c8e64ba-9730-40e5-b2c5-fcf650705b18","http_method":"GET","http_route":"/api/v1/notifications","http_status_code":200,"duration_ms":6.83}
```

Ожидаемое представление той же записи в Grafana:

```text
INFO  carcraft-api/http  GET /api/v1/notifications -> 200 in 6.83 ms  req=7c8e64ba…
```

## Интерфейс модуля логирования

Глубокий модуль размещается в `backend/infrastructure/logging.py` и скрывает
JSON-сериализацию, контекст async-выполнения, нормализацию типов, redaction,
форматирование исключений, ограничение размера записи и настройку сторонних
логгеров.

Публичный интерфейс должен оставаться небольшим:

```python
def configure_logging(*, service_name: ServiceName) -> None: ...

def bind_log_context(**fields: LogValue) -> AbstractContextManager[None]: ...

def log_event(
    level: LogLevel,
    event: str,
    message: str,
    /,
    *,
    error: BaseException | None = None,
    **fields: LogValue,
) -> None: ...
```

Инварианты интерфейса:

- внутри backend сохраняется единственный именованный logger
  `carcraft-backend`;
- `configure_logging` вызывается один раз в entrypoint и остаётся идемпотентным:
  повторный вызов не создаёт дополнительный handler или дубль строки;
- `service_name`, `timestamp`, `schema_version`, `level` и другие зарезервированные
  поля нельзя переопределить через `fields`;
- `bind_log_context` использует `ContextVar`, изолирует параллельные async-задачи
  и гарантированно восстанавливает предыдущий контекст в `finally`;
- допустимы JSON-совместимые scalar-значения и короткие списки scalar-значений;
  UUID, `datetime`, `Decimal` и enum нормализуются внутри модуля;
- ошибка сериализации лога не должна менять ответ HTTP-запроса, результат задачи
  или транзакцию; вместо этого создаётся безопасное событие
  `logging.serialization_failed` без исходного опасного значения;
- существующие вызовы стандартного `logger.info/warning/error/exception`
  продолжают работать и автоматически получают обязательные поля. Пока такой
  вызов не переведён на `log_event`, formatter использует `event=python.log`;
- вывод выполняется только в stdout/stderr и не отправляется из бизнес-кода
  напрямую в Loki или по сети.

Модуль не импортирует FastAPI, Starlette, Taskiq, Kafka или SQLAlchemy.
HTTP-контекст остаётся в presentation, адаптеры Taskiq/Kafka — в infrastructure,
а domain не получает зависимость от логирования.

## Идентификаторы и корреляция

### HTTP

- На входе используется валидный UUID из `X-Request-ID`; при отсутствии или
  некорректном значении создаётся UUID4.
- `X-Request-ID` возвращается клиенту в ответе.
- В начале обработки `request_id` и равный ему начальный `correlation_id`
  помещаются в log context.
- В лог пишется шаблон FastAPI route, например `/api/v1/cars/{id}`, а не
  фактический UUID-путь.
- Query string и его значения в стандартной записи не сохраняются. При
  необходимости допустим только список имён query-параметров либо отдельный
  явно согласованный allowlist безопасных значений.
- На один запрос создаётся ровно одно итоговое событие
  `http.request.completed` или `http.request.failed`.
- `uvicorn.access` отключается; health check и `/metrics` остаются исключёнными
  из прикладного access-log.

### Taskiq

- API или scheduler передаёт `correlation_id` как метаданные задачи, не как
  Loki label.
- Worker связывает контекст с `task_id`, `task_name`, `attempt` и длительностью.
- Штатные `Sending task` и `Executing task` переводятся в DEBUG или подавляются.
- На штатное завершение создаётся один `task.completed`; на окончательную ошибку
  — один `task.failed` с исключением.
- Для периодической задачи без входящего контекста создаётся новый
  `correlation_id` на каждый запуск.

### Kafka/event-worker

- При публикации `correlation_id` передаётся в Kafka headers без изменения
  бизнес-payload.
- Consumer извлекает его до запуска обработчика и связывает с topic, partition,
  offset и consumer group.
- Для batch-обработки логируется один итог batch, а не перечень событий и не
  отдельная INFO-строка на каждую внутреннюю функцию.
- Инфраструктурные Kafka debug/rebalance-сообщения не подменяют прикладное
  итоговое событие.

## Политика уровней и объёма

- `debug` — временная техническая диагностика; в обычном `local`, `test` и
  production запуске отключена.
- `info` — одно итоговое событие границы системы или значимое изменение
  состояния. Обычные HTTP 2xx/3xx и ожидаемые 4xx не считаются ошибкой.
- `warning` — retry, деградация, fallback, отклонённая проверка безопасности или
  другое состояние, требующее внимания, но не сорвавшее операцию.
- `error` — операция не выполнена либо пользователь получил 5xx/неожиданный
  результат.
- `critical` — сервис не может корректно запуститься или продолжать работу.

`repository_query` больше не создаётся на INFO для каждого успешного вызова.
Декоратор репозитория:

- не пишет быстрый успешный вызов в лог;
- создаёт `db.repository.slow` на WARNING только при превышении настраиваемого
  порога `REPOSITORY_SLOW_QUERY_MS`, по умолчанию 200 мс;
- создаёт `db.repository.failed` на ERROR при исключении и повторно выбрасывает
  исходное исключение;
- сохраняет агрегированное измерение длительности в существующем metrics-контуре
  без высококардинальных аргументов и UUID.

Для `botocore`, `aiobotocore`, `boto3`, `aioboto3`, `httpx`, `httpcore`, Taskiq,
Kafka и FastStream во всех entrypoint устанавливается безопасный минимальный
уровень WARNING или более строгий уровень, уже требуемый конкретным процессом.
Ошибки зависимостей сохраняются, но их request/response bodies и полные headers
не выводятся.

Повторяющееся предупреждение Redpanda о лицензии не скрывается как шум: collector
должен распознать его как `warning`. Устранение причины лицензирования или
кластерной настройки является отдельной инфраструктурной задачей.

## Безопасность и redaction

В централизованные логи запрещено записывать:

- `Authorization`, Cookie/Set-Cookie и refresh/access tokens;
- пароли, SMS-коды, API keys, secret keys, подписи и credential;
- полные request/response bodies внешних провайдеров;
- URL с userinfo или query-параметрами, содержащими временный доступ;
- паспортные данные, полные телефоны, email и другие персональные данные без
  отдельного согласованного основания.

Redaction применяется рекурсивно к структурным полям по denylist ключей. Для
legacy-текстов сохраняются фильтры известных чувствительных query-параметров.
Первым рубежом остаётся отключение небезопасного DEBUG у SDK, вторым — formatter,
третьим — collector. Наличие последующих рубежей не разрешает создавать
опасную запись в процессе.

## Имена сервисов и обработка native-логов

В Grafana должны использоваться следующие стабильные `service_name`:

- `carcraft-api`;
- `carcraft-event-worker`;
- `carcraft-taskiq-worker`;
- `carcraft-taskiq-scheduler`;
- `carcraft-frontend`;
- `carcraft-nginx`;
- `postgres`;
- `redis`;
- `clickhouse`;
- `redpanda`;
- `redpanda-console`.

Python-процессы формируют JSON самостоятельно. Nginx получает JSON access-log с
request ID, status, request/upstream duration и безопасным route/path без query
values. Nuxt/Nitro server stdout и native-логи PostgreSQL, Redis, ClickHouse,
Redpanda и Redpanda Console нормализуются collector по отдельным pipeline:

- `service_name` определяется из стабильной метки workload/container;
- native severity переводится в общий `level`;
- исходное сообщение сохраняется в `message`;
- неизвестный формат получает `level=unknown` и попадает в отдельную панель
  parser miss, а не молча считается INFO.

Браузерные `console.*` не являются stdout Kubernetes-сервиса и не отправляются
массово в Loki в рамках этой задачи. Сбор клиентских ошибок требует отдельного
контракта, согласия на передачу данных и отдельной задачи.

## Loki labels и structured metadata

Индексируемые Loki labels ограничиваются низкокардинальными значениями:

- `cluster`;
- `namespace`;
- `environment`;
- `service_name`;
- `level`.

`component`, `event`, `pod`, `container`, `service_version`, `request_id`,
`correlation_id`, `trace_id`, `span_id`, route, task/job IDs, UUID сущностей и
client address не становятся индексируемыми labels. Они хранятся как JSON
fields либо structured metadata, если серверная версия Loki и схема хранения
это поддерживают. При отсутствии поддержки structured metadata поля остаются в
JSON и фильтруются после `| json`.

Базовое представление Grafana:

```logql
{namespace="$namespace", service_name=~"$service", level=~"$level"}
| json
| line_format `{{.level}} {{.service_name}}/{{.component}} {{.message}} req={{.request_id}}`
```

Dashboard содержит:

- переменные `namespace`, `service_name`, `level`;
- общую ленту с цветом по `level` и скрытым по умолчанию raw JSON;
- быстрые фильтры по `component`, `event`, `request_id` и `correlation_id`;
- таблицу HTTP route/status/duration/request ID;
- таблицу Taskiq/Kafka operation/result/duration/correlation ID;
- отдельную панель `unknown/parser_miss`;
- data link, который открывает всю цепочку по `correlation_id`.

## Локальный observability-контур

Добавить opt-in compose profile `observability`, который не запускается при
обычном `docker compose up` и включает:

- Loki с зафиксированной версией и локальным volume;
- Grafana с зафиксированной версией, provisioned Loki datasource и dashboard;
- Grafana Alloy с зафиксированной версией для чтения логов локальных compose
  контейнеров, enrichment `environment=local` и применения тех же pipeline;
- существующий Prometheus datasource и dashboard без удаления или изменения их
  назначения.

Доступ collector к Docker API допускается только в локальном opt-in профиле,
не публикуется наружу и отдельно отмечается как привилегированный доступ к
локальному Docker daemon. Loki и Grafana не используют `latest` image tags.

Локальный smoke-сценарий должен:

1. запустить приложение и профиль observability;
2. дождаться health checks;
3. выполнить безопасный публичный GET-запрос без изменения бизнес-данных;
4. дождаться одной периодической Taskiq-задачи либо запустить специально
   предназначенную безопасную диагностическую задачу;
5. создать санитизированные тестовые события всех пяти уровней с уникальным
   маркером `local_observability_smoke` без секретов и персональных данных;
6. проверить LogQL-запросом наличие обязательных полей и отсутствие дубля
   HTTP-summary;
7. открыть локальный Grafana dashboard во встроенном браузере и визуально
   проверить источник, текст, фильтры и цвета;
8. сохранить screenshot только как временное подтверждение пользователю, не
   добавляя новый постоянный текстовый артефакт задачи.

## Планируемые изменения

### Backend: общий модуль и настройки

- `backend/infrastructure/logging.py`
  - заменить `CompactLogFormatter` на однострочный JSON formatter;
  - реализовать малый интерфейс `configure_logging`, `bind_log_context` и
    `log_event`;
  - добавить нормализацию типов, reserved fields, redaction и безопасное
    форматирование исключений;
  - унифицировать настройку root и `carcraft-backend` logger без дубликатов;
  - централизовать уровни сторонних библиотек.
- `backend/infrastructure/settings.py`
  - добавить `environment`, `service_version` и
    `repository_slow_query_ms` с безопасными значениями по умолчанию;
  - использовать только `settings`, без прямого чтения `os.environ`.
- `backend/main.py`, `backend/event_worker.py`,
  `backend/infrastructure/taskiq_broker.py` и
  `backend/infrastructure/taskiq_scheduler.py`
  - вызывать единый configurator с конкретным `service_name`;
  - удалить дублирующие варианты настройки formatter/handlers;
  - сохранить защиту от повторной конфигурации logging со стороны Taskiq CLI.

### Backend: HTTP, Taskiq, Kafka и репозитории

- `backend/presentation/middleware/request_timing.py`
  - превратить middleware в владельца единственного HTTP-summary;
  - добавить request/correlation context, шаблон route, response header,
    duration и корректную запись исключений;
  - не сохранять query values и исключать health/metrics.
- Конфигурация Uvicorn/container entrypoint
  - отключить `uvicorn.access`, не создавая второй access event.
- `backend/infrastructure/repository_timing.py`
  - убрать INFO на каждый вызов;
  - оставить slow/error events и агрегированную метрику.
- Taskiq middleware/entrypoint
  - передавать correlation context и создавать единый terminal event;
  - подавить штатные дубли `Sending/Executing task`.
- Kafka publisher/consumer adapters
  - передавать correlation metadata в headers;
  - привязывать consumer events без изменения бизнес-payload и владения
    ClickHouse-записью event-worker.

### Nginx и frontend server

- `nginx.dev.conf` и применимые шаблоны Nginx
  - перейти на валидный JSON access-log;
  - прокидывать `X-Request-ID` в backend и возвращать его клиенту;
  - исключить query values, Authorization и cookies.
- Nuxt/Nitro server
  - не отправлять браузерный console в Loki;
  - настроить collector parser для server stdout и стабильный
    `service_name=carcraft-frontend`.

### Локальные Loki, Alloy и Grafana

- `compose.observability.yml`
  - добавить изолированный opt-in overlay/profile `observability` поверх
    локального `docker-compose.yml`;
  - не менять и не включать в Git пользовательский базовый compose с локальными
    настройками и секретами;
  - не менять обычный запуск приложения без overlay.
- `monitoring/loki/`
  - добавить локальную конфигурацию Loki и volume с ограниченным retention.
- `monitoring/alloy/`
  - добавить discovery compose-контейнеров, JSON/native parsers, enrichment,
    redaction и отправку в Loki.
- `monitoring/grafana/provisioning/datasources/datasources.yml`
  - добавить provisioned Loki datasource, сохранив Prometheus.
- `monitoring/grafana/dashboards/`
  - добавить отдельный dashboard структурированных логов.
- Добавить безопасный локальный smoke runner в `monitoring/`; он не должен
  обращаться к production/test серверу, менять бизнес-данные или содержать
  секреты.

### Deployment-контракт

- Репозиторий не содержит Kubernetes/Alloy/Promtail-конфигурации серверного
  кластера. Реализация фиксирует требуемое соответствие Kubernetes workload ->
  `service_name`, severity -> `level` и правила labels/metadata в локальной
  конфигурации и тестах.
- Перенос эквивалентной конфигурации в серверный deployment выполняется только
  в репозитории/конфигурации, которая фактически владеет collector. Локальная
  проверка не считается подтверждением серверного внедрения.

## Тесты и проверки

### Автоматические backend-тесты

- Каждая запись formatter является одной строкой валидного JSON.
- Все обязательные поля присутствуют и имеют правильные типы/значения.
- Уровни Python logging корректно преобразуются в общий `level`.
- Старый стандартный logger-call получает `event=python.log` и service context.
- Исключение сохраняет тип и stacktrace, но не создаёт многострочную запись.
- UUID, `datetime`, `Decimal` и enum сериализуются детерминированно.
- Reserved fields нельзя подменить из caller fields.
- Ошибка сериализации не ломает вызывающую операцию.
- Вложенные контексты и параллельные async tasks не смешивают request/task IDs.
- Повторная конфигурация API, event-worker, Taskiq worker и scheduler не создаёт
  duplicate handlers.
- Небезопасные логгеры зависимостей имеют эффективный уровень не ниже WARNING.
- Authorization, cookies, tokens, passwords, signatures, API keys, signed URL,
  query secrets и тестовые персональные данные отсутствуют в результате.
- Один HTTP-запрос создаёт один summary и возвращает `X-Request-ID`.
- Фактический UUID-путь нормализуется до route template.
- Health и metrics не создают access events.
- Быстрый успешный repository call не создаёт INFO-запись; slow и failed calls
  создают ожидаемые события и не меняют исходный результат/исключение.
- Correlation ID переносится через Taskiq/Kafka adapters без добавления в
  бизнес-payload.

### Конфигурационные и архитектурные тесты

- Сохраняется единственный backend logger `carcraft-backend`.
- `infrastructure.logging` не зависит от FastAPI, Starlette, SQLAlchemy,
  application или presentation.
- Compose profile не включается в обычный `docker compose config --services` без
  явного `--profile observability`.
- Loki, Alloy и Grafana используют зафиксированные версии, health checks и не
  публикуют Loki/Alloy наружу.
- Grafana provisioning содержит Prometheus и Loki datasource и dashboard без
  ручной настройки после старта.
- Collector извлекает `service_name` и `level` из каждого известного локального
  сервиса и не превращает high-cardinality fields в labels.
- Parser miss остаётся видимым и измеримым.

## Критерии готовности

- Все прикладные Python-процессы формируют однострочный JSON с обязательными
  `level`, `service_name`, `component`, `event` и `message`.
- В локальном Grafana каждый известный сервис выбирается отдельным фильтром, а
  источник строки понятен без раскрытия raw labels.
- INFO, WARNING, ERROR и другие уровни имеют корректную и стабильную цветовую
  визуализацию; прикладные записи не попадают в `unknown`.
- Один безопасный HTTP-запрос создаёт ровно один итоговый backend request event с
  route template, status, duration и request ID.
- По `request_id`/`correlation_id` можно получить связанную цепочку HTTP,
  Taskiq/Kafka и event-worker там, где эти переходы реально происходят.
- Быстрые успешные repository-вызовы и штатные Taskiq `Sending/Executing` не
  перегружают INFO-ленту.
- Ошибки и медленные операции остаются видимыми с длительностью, компонентом и
  безопасным контекстом.
- AWS/Kafka/HTTP SDK debug-шум отсутствует в обычном запуске; ошибки библиотек
  не скрыты.
- Authorization, cookies, tokens, signatures, API keys, signed URL и
  request/response bodies отсутствуют в автоматических и локальных smoke-логах.
- Nginx и все native-сервисы получают нормализованные `service_name` и `level`;
  неизвестный формат явно отображается как parser miss.
- Loki labels не содержат request/trace/task/user/entity IDs, фактические route
  UUID, pod ID или client address.
- Обычный compose-запуск не зависит от observability profile и продолжает
  работать без Grafana/Loki/Alloy.
- Opt-in профиль поднимается одной документированной командой, не требует
  ручного добавления datasource/dashboard и позволяет визуально проверить
  результат во встроенном браузере.
- Результаты Ruff, import-linter, mypy, pytest, применимых frontend-проверок,
  Docker build/up, LogQL smoke и визуального просмотра Grafana зафиксированы в
  этой спецификации перед созданием MR.
- MR создаётся только в `test`; после создания файл переименовывается в
  `specs/<номер-MR>.md`.

## Границы и риски

- Задача не меняет бизнес-правила, API response contracts, данные, роли,
  аутентификацию, платежи или схему БД.
- Задача не добавляет OpenTelemetry SDK, OTLP exporter, Tempo и distributed
  tracing. Схема только резервирует совместимые поля.
- Задача не отправляет browser console/errors в Loki.
- Задача не исправляет Redpanda license configuration и не скрывает её
  предупреждения.
- Задача не меняет retention/alerting серверного Loki и не выполняет deployment
  в отсутствующую в репозитории Kubernetes-конфигурацию.
- Полный перевод каждого существующего сообщения на собственный стабильный
  `event` не является условием первого MR. Formatter обязан немедленно сделать
  legacy-вызовы структурированными; ключевые HTTP, repository, Taskiq, Kafka и
  startup/shutdown события переводятся в рамках этой задачи.
- Возможные риски: временная смесь JSON и native-форматов, повторная настройка
  логгера Taskiq CLI, высокая кардинальность из-за ошибочных labels, потеря
  полезной ошибки при слишком широком suppression и доступ локального Alloy к
  Docker daemon. Они закрываются раздельными collector pipeline, allowlist
  labels, контрактными тестами, сохранением WARNING/ERROR и opt-in профилем.
- Реализация начата после review и явного подтверждения пользователем командой
  `делай`.
