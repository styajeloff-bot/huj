# Bitrix №22214 — ограничение первоначального взноса в корзине

- **Задача:** https://carcraftpro.bitrix24.ru/company/personal/user/738/tasks/task/view/22214/
- **Ветка:** `bugfix/22214`
- **Статус:** `draft`
- **Область:** публичная desktop-корзина, лизинговый калькулятор.

## Текущее поведение

В `frontend/features/cart/calculator/CartLeasingCalculator.vue` у поля первоначального взноса и ползунка указан HTML-атрибут `max="49"`. Он задаёт границу для ползунка, но не нормализует ручной ввод в числовом поле. При вводе значения выше 49 поле хранит это значение, а запрос расчёта получает недопустимый `down_payment_percent`.

Backend уже защищает контракт: калькулятор принимает первоначальный взнос только в диапазоне от 0 до 49 процентов. Из-за расхождения между интерфейсом и контрактом API создание лизинговой заявки может быть заблокировано.

## Целевое поведение

Для любого пользователя, включая гостя без авторизации:

1. При ручном вводе процента первоначального взноса выше `49` поле сразу принимает значение `49`.
2. Ползунок отображает то же значение `49`.
3. Сумма первоначального взноса пересчитывается от `49%` и последующий расчёт отправляется только с `down_payment_percent: 49`.
4. При изменении суммы первоначального взноса, если вычисленный процент превышает 49, процент и сумма также нормализуются к 49% — это сохраняет единое правило для всех путей изменения одних и тех же параметров.
5. Текущее минимальное значение, определяемое поддержкой дистрибьютора, остаётся в силе. Значения ниже него не становятся частью этой задачи.
6. Backend-валидация `0…49` не меняется: это независимая защита API от внешних и устаревших клиентов.

## Бизнес-причина

Пользователь не должен получать блокировку расчёта или оформления заявки из-за допустимого в интерфейсе ручного ввода. Фронтенд должен не допускать в расчёт значение, которое backend гарантированно отклонит.

## Выбранный безопасный вариант

Нормализация выполняется в единой функции внутри `CartLeasingCalculator.vue` и используется всеми путями изменения процента. Не меняются формулы, API, backend, авторизация и структура сохранённого состояния.

Это безопаснее, чем менять backend на «молчаливую» подстановку: API сохранит прозрачное отклонение некорректных внешних данных, а интерфейс покажет пользователю фактическое значение 49.

## План реализации

1. В `CartLeasingCalculator.vue` добавить локальную константу верхней границы `49` и небольшую функцию нормализации процента с учётом существующего минимального значения.
2. Вызывать нормализацию в `updateDownPaymentFromPercent` до расчёта суммы и запуска отложенного пересчёта.
3. Применить ту же нормализацию при пересчёте процента из суммы первоначального взноса и при восстановлении значения из scoped storage, чтобы интерфейс, ползунок, сумма и API-параметр никогда не расходились.
4. Добавить точечный frontend-тест в `frontend/tests/architecture/`, который закрепляет наличие единого ограничителя и его использование для ручного ввода, суммы и восстановленного состояния.
5. Запустить точечный Vitest-тест, связанные регрессионные архитектурные тесты и production-сборку frontend. При доступном Docker окружении дополнительно проверить публичную корзину в desktop-браузере без JWT: ввод `60` должен показать `49` и сдвинуть ползунок на 49.

## Критерии готовности

- В публичной корзине ручной ввод `60` в процент первоначального взноса заменяется на `49`.
- После замены и поле, и ползунок содержат/показывают `49`.
- Сумма первоначального взноса соответствует 49% от текущей стоимости имущества.
- Расчёт не отправляет значение больше 49.
- Сценарий не зависит от наличия JWT или роли пользователя.
- Не изменены формулы расчёта, API-контракт и backend-ограничение.
- Новая проверка и связанные frontend-проверки проходят; production-сборка frontend проходит.

## Вопросы

Блокирующих вопросов нет. Значение 49 является фиксированным действующим максимумом backend-контракта и явно подтверждено постановкой.
