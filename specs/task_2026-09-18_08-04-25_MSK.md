# Bitrix #21700 — цели приобретения и регионы по каждой позиции техники

- **Задача:** https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/21700/
- **Ветка:** `bugfix/21700-per-item-purpose-regions`
- **База:** актуальный `origin/test` (`403da013`)
- **Статус:** ожидает согласования перед реализацией

## Постановка

Внешняя карточка заявки в кабинетах содержит «Цель приобретения» и «Регион», выбранные из первой позиции с заполненными данными. При заявке с несколькими позициями это вводит в заблуждение: значения относятся к конкретной технике, а не ко всей заявке.

Одновременно в кабинете лизинговой компании в разделе «Техника в заявке» цели и регионы не выводятся для позиций из единой витрины `items`.

Пользователь подтвердил, что отображение требуется для **всех позиций техники**, включая автомобили и спецтехнику.

## Текущее поведение

1. `ApplicationCard.vue` на внешней карточке заявки выводит цель и регионы единственной первой автомобильной позиции с заполненными полями.
2. API уже возвращает `leasing_purpose` и `regions` отдельно в каждой позиции `items` — как для автомобиля, так и для спецтехники.
3. Общий компонент `CommerceApplicationItemsSummary.vue`, используемый в деталях дилера и в кабинете лизинговой компании, не показывает эти поля.
4. Предыдущее решение по #21700 восстанавливало внешний блок на карточке. Новое требование сознательно меняет это правило: общие значения на внешней карточке больше не показываются.

## Желаемое поведение

1. На внешней карточке заявки цели приобретения и регионы не отображаются вовсе.
2. В детальном просмотре заявки дилером у каждой активной позиции техники отдельно выводятся:
   - «Цель приобретения»;
   - «Регион».
3. В кабинете лизинговой компании в разделе «Техника в заявке» у каждой активной позиции техники отдельно выводятся те же поля.
4. Автомобили и спецтехника используют собственные значения соответствующей позиции.
5. Если у конкретной позиции отсутствует цель или регионы, не выводится только соответствующая пустая строка; значения другой позиции не подставляются.
6. При нескольких регионах остаётся существующий компактный вывод: первый регион и ссылка раскрытия остальных.
7. В карточках клиента и административных экранах эти поля не появляются как побочный эффект изменения.

## Бизнес-причина

Лизинговая компания и дилер должны оценивать назначение и географию по каждой единице техники. Отображение одного значения на уровне всей заявки создаёт риск принять решение по неверным данным, особенно в смешанных заявках из нескольких автомобилей и спецтехники.

## Варианты реализации

### Вариант A — рекомендованный

Добавить в общий компонент позиций необязательный режим показа цели и регионов. Включить его только в детальном окне дилера и на странице заявки лизинговой компании. Убрать устаревший общий блок из внешней `ApplicationCard`.

Преимущества:

- использует уже возвращаемый API-контракт без изменений backend и БД;
- единый формат для автомобиля и спецтехники;
- не меняет клиентские и административные экраны;
- не создаёт дублирующих запросов и компонентов.

Риск:

- общий компонент используется в нескольких местах.

Защита:

- режим показа будет выключен по умолчанию и передан явно только в два требуемых интерфейса.

### Вариант B — отдельные блоки в каждом экране

Сделать два независимых представления: одно в деталях дилера, второе в кабинете лизинговой компании.

Недостатки:

- дублирование разметки и правил отображения;
- выше риск, что автомобили и спецтехника будут выглядеть по-разному;
- сложнее сопровождать раскрытие нескольких регионов.

### Вариант C — показывать значения во всех местах, где используется общий компонент

Технически самый короткий путь, но он добавит поля в кабинет клиента и административные экраны без требования задачи.

Недостаток:

- меняет больше интерфейсов, чем согласовано.

## Решение

Выбрать **вариант A**.

## Планируемые изменения

1. В `frontend/features/applications/components/ApplicationCard.vue` удалить общий блок цели и региона и связанную логику выбора первой позиции.
2. В `frontend/features/commerce/components/CommerceApplicationItemsSummary.vue` добавить явный необязательный параметр отображения цели и региона по позиции.
3. При включённом параметре выводить данные непосредственно внутри карточки каждой активной позиции:
   - использовать существующий `formatLeasingPurpose`;
   - использовать существующий `VehicleRegionsDisplay` для одного или нескольких регионов;
   - отображать каждую строку только при наличии значения у текущей позиции.
4. В `frontend/features/applications/components/ApplicationDetailModal.vue` включить этот параметр только для роли дилера.
5. В `frontend/pages/workspace/leasing-applications/[id]/index.vue` включить этот параметр для кабинета лизинговой компании.
6. Не изменять backend, миграции и API-контракт: проверка показала, что `items` уже содержит `leasing_purpose` и `regions` для автомобилей и спецтехники.
7. Добавить или обновить E2E-сценарий для подтверждённого пользовательского поведения, включая смешанную заявку с несколькими позициями.

## Критерии готовности

- [ ] В списке/внешней карточке заявки дилера нет строк «Цель приобретения» и «Регион».
- [ ] В деталях дилера у каждого автомобиля отображаются его собственные цель и регионы.
- [ ] В деталях дилера у каждой позиции спецтехники отображаются её собственные цель и регионы.
- [ ] В кабинете лизинговой компании эти значения видны у каждой соответствующей позиции.
- [ ] Значения одной позиции не выводятся у другой.
- [ ] При двух и более регионах работает существующее раскрытие списка.
- [ ] У позиции без цели или регионов отсутствует только соответствующая строка без пустых подписей.
- [ ] Клиентский и административный экраны не получают новые блоки без отдельного требования.
- [ ] Выполнен E2E-сценарий на работающем приложении для дилера и лизинговой компании; проверены основной путь, права доступа и журнал приложения.
- [ ] Выполнены обязательные для затронутого фронтенда линтеры, Docker-проверка и проверка итогового diff.
- [ ] Alembic autogenerate не обнаруживает изменений схемы БД.

## Открытые вопросы

Блокирующих вопросов нет.

Неблокирующее ограничение: задача охватывает активные позиции техники. Исторические/заменённые/удалённые позиции продолжают отображаться в существующем разделе истории без новых строк, чтобы не смешивать актуальные условия с историей.
