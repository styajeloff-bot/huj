## Резюме

Спецификация определяет доработку существующего процесса, в котором лизинговая компания (ЛК) запрашивает у клиента дополнительные документы по лизинговой заявке. Изменение добавляет типовой каталог документов, фиксированные дополнительные формы для четырёх типов, обязательную загрузку одного файла при каждом ответе и безопасное отображение данных формы.

Целевой результат: ЛК выбирает типовой документ из каталога либо создаёт произвольный запрос; клиент в отдельном модальном окне видит название и общий комментарий ЛК, заполняет требуемую форму при её наличии и обязательно прикладывает один файл. Ответ сохраняется один раз и остаётся в истории конкретного запроса.

## Источники и контекст

- Задача Bitrix: [№20418](https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/20418/).
- Текущая реализация уже хранит запросы в `application_document_requests`, объединяет их в пакеты `request_batch_id` и использует статусы `requested`, `provided`, `approved`, `rejected`, `superseded`.
- ЛК создаёт пакет через `PUT /api/v1/leasing/applications/{application_id}/request-documents`.
- История читается через `GET /api/v1/applications/{application_id}/document-requests` и уже ограничивает ЛК собственными запросами.
- Клиент загружает один файл для конкретного запроса через `POST /api/v1/documents` с `application_id` и `document_request_id`.
- В `document_types` уже хранится справочник типов документов; endpoint `GET /api/v1/documents/types` только возвращает записи справочника. Его наполнение выполняется миграцией данных.

## Проблема

1. У автоматически прикреплённого к заявке ЛК документа `company_requisites` внутренний статус `approved` корректен, но после переименования пропала его пользовательская подпись «Принят» в соответствующем представлении ЛК.
2. ЛК может вводить названия дополнительных документов только вручную и не может использовать единый каталог типовых документов.
3. Запрос документа не содержит фиксированного контракта дополнительной формы и не хранит введённые клиентом данные формы.
4. Кнопка «Выбрать файл» сразу открывает системный выбор файла; клиент не видит в одном контексте название запроса, комментарий ЛК и дополнительные поля.
5. Текущая операция ответа построена только вокруг файла и не обеспечивает единую, идемпотентную отправку файла вместе с `form_data`.

## Цели и границы

### Цели

- Исправить отображение статуса автоматически созданного `company_requisites` как «Принят» без изменения внутреннего статуса `approved`, его переходов или данных в БД.
- Расширить типовой каталог `document_types` полями `has_form` и `form_schema`.
- Добавить тринадцать согласованных типовых типов документов.
- Для четырёх типов хранить и валидировать фиксированные данные `form_data` в рамках конкретного запроса документа.
- Дать ЛК каталог типовых документов с возможностью скорректировать отображаемое название и с отдельной корпоративной опцией произвольного запроса.
- Заменить немедленный выбор файла модальным окном ответа клиента.
- Сохранить существующую модель одного файла на один запрос и сделать файл обязательным для любого ответа.
- Обеспечить изоляцию данных между заявками и ЛК, а также защитить СНИЛС от утечки в логи, события и лишние представления.

### Не входит в объём

- Изменение значений статусов в БД или глобальное переименование `approved` во всех интерфейсах.
- Свободный конструктор произвольных JSON-форм.
- Добавление новых ограничений по расширениям или размерам файлов сверх действующих платформенных ограничений.
- Автоматическое одобрение новых типов документов.
- Несколько файлов в одном ответе на запрос.
- Редактирование или повторная отправка ответа клиента по уже предоставленному запросу.
- Справочник банков и интеграция с внешним банковским каталогом.
- Проверка контрольной суммы СНИЛС.

## Роли и сценарии

### Лизинговая компания

ЛК, выбранная в заявке, создаёт от одного до десяти запросов одним пакетом и указывает единый необязательный комментарий. Для каждой строки ЛК выбирает тип из каталога либо выбирает опцию «Произвольный документ» и вводит название вручную.

При выборе каталожного типа система подставляет его `display_name`. ЛК может изменить только отображаемое название конкретного запроса. Технический тип и состав дополнительной формы после этого не меняются.

Опция **«Произвольный документ»** означает запрос, отсутствующий в корпоративном каталоге. ЛК вводит понятное клиенту название; система создаёт технический код по действующему безопасному правилу формирования `slug`, не добавляет запись в глобальный справочник и всегда устанавливает `has_form=false`, `form_schema=null`.

### Клиент

Клиент видит запросы только своей компании и своей заявки. Для каждого запроса в статусе `requested` он открывает модальное окно ответа. В окне последовательно показаны:

1. название требуемого документа;
2. общий комментарий ЛК к пакету, если он указан;
3. обязательные поля дополнительной формы, если `has_form=true`;
4. обязательное поле выбора одного файла;
5. кнопки «Отмена» и «Отправить».

Клиент может отправить ответ только при заполнении всех обязательных полей и выборе файла. После успешной отправки запрос получает статус `provided`. Клиент не может редактировать форму, менять файл или отправлять ответ повторно. Если ЛК нужны иные сведения, она создаёт новый запрос; старый ответ остаётся в истории.

### Сотрудник CarCraft

Сотрудник CarCraft получает доступ к данным формы только при наличии предусмотренного бизнес-права на обработку документов заявки. Само наличие роли сотрудника не отменяет проверку доступа к заявке и запросу.

## Требования

### Функциональные требования

**FR-1. Отображение `company_requisites`.** В экране ЛК, где показывается автоматически прикреплённый документ `company_requisites`, значение `approved` отображается как «Принят». Это точечное отображение: код статуса, его хранение, API и подписи других документов не изменяются.

**FR-2. Справочник типов.** Таблица `document_types` получает:

- `has_form`: обязательный boolean, по умолчанию `false`;
- `form_schema`: nullable JSONB с контрактом формы.

Сервер обязан соблюдать инвариант:

- при `has_form=false` значение `form_schema` равно `null`;
- при `has_form=true` значение `form_schema` — непустой объект фиксированной поддерживаемой схемы;
- состояние `has_form=true` и `form_schema=null` недопустимо при миграции данных, создании или обновлении записи.

**FR-3. Типовые документы.** Миграция данных добавляет в `document_types` следующие строковые `type_code` и названия:

- `ceo_passport_page23` — «Паспорт ген. директора (2 и 3 страницы)»;
- `appointment_docs` — «Документация о назначении (решение/протокол: номер, дата, срок полномочий)»;
- `licenses` — «Наличие лицензий»;
- `sro` — «Членство в СРО»;
- `main_counterparties` — «Основные контрагенты (поставщики/покупатели)»;
- `open_bank_accounts` — «Перечень открытых расчётных счетов»;
- `loans_docs` — «Сведения о кредитах, займах, лизинге (таблица с суммой, остатком, обеспечением)»;
- `third_member_guarantees` — «Поручительства за третьих лиц»;
- `additional_collateral` — «Возможность предоставления дополнительного обеспечения»;
- `management_company` — «Сведения об управляющей компании (если применимо)»;
- `beneficial_owner` — «Выгодоприобретатель по сделке»;
- `state_defense_order` — «Вопрос о гособоронзаказе (сопровождаемая сделка)»;
- `snils` — «СНИЛС».

Для всех этих типов не устанавливаются дополнительные ограничения на тип файла со стороны данного изменения и не включается автоодобрение. `has_form=true` устанавливается только для `main_counterparties`, `open_bank_accounts`, `beneficial_owner` и `snils`. Для остальных новых типов `has_form=false`, `form_schema=null`.

**FR-4. Снимок контракта запроса.** Каждый созданный запрос документа хранит собственные `has_form`, `form_schema` и `form_data`. Значения `has_form` и `form_schema` копируются из выбранного типа каталога в момент создания запроса. Последующее изменение справочника не меняет уже созданные запросы и историю.

**FR-5. Создание запроса ЛК.** Каноническим остаётся endpoint `PUT /api/v1/leasing/applications/{application_id}/request-documents`. Он не принимает `file_ids` и не принимает клиентское `form_data`. Он создаёт только запросы ЛК. Для каждого элемента запроса передаются источник (`catalog` или `custom`), технический `document_type` и `display_name`.

Для `catalog` `document_type` обязан существовать в `document_types`; сервер получает `has_form` и `form_schema` только из справочника, а не из тела клиента. Для `custom` `document_type` — сформированный сервером уникальный `slug` внутри пакета; форма отсутствует. Все идентификаторы сущностей в запросах и ответах являются UUID-строками; числовые идентификаторы не используются.

**FR-6. Получение истории.** Каноническим остаётся `GET /api/v1/applications/{application_id}/document-requests`. Структура сохраняет группировку по пакетам. Каждый элемент `items` дополнительно возвращает `document_type`, `has_form`, `form_schema`, `form_data` и один объект `attachment` после ответа клиента. Поле `attachment` содержит UUID `application_documents.id`, UUID документа, имя файла, пользовательское название, статус и время загрузки. Массив `attachments` не вводится: один запрос допускает только один файл.

**FR-7. Единый ответ клиента.** `POST /api/v1/documents` для `document_request_id` принимает один файл и опциональное сериализованное поле `form_data`. Для запроса без формы `form_data` отсутствует. Для запроса с формой `form_data` обязательно и валидируется сервером по сохранённому снимку `form_schema` до фиксации ответа.

Файл обязателен для каждого ответа, независимо от `has_form`. При успешной отправке файла и валидных данных формы сервер в одной транзакции создаёт файл, его связь с запросом, сохраняет `form_data` и переводит запрос из `requested` в `provided`. При ошибке ни ответ, ни новые данные формы не считаются предоставленными.

**FR-8. Защита от повторной отправки.** Клиент создаёт UUID `Idempotency-Key` при первом нажатии «Отправить» и передаёт его в запросе загрузки. Пока запрос выполняется, элементы формы, кнопки закрытия и отправки недоступны. Повтор того же ключа возвращает ранее созданный результат без дубликатов. Новый ключ после перехода запроса в `provided` получает `409 Conflict`; интерфейс перечитывает историю и сообщает, что ответ уже отправлен.

**FR-9. Формы.** Поддерживаются только четыре фиксированные формы из раздела «Контракт `form_schema` и `form_data`». Фронтенд строит поля по `form_schema`; backend независимо проверяет их структуру, обязательность, количество строк и формат. Произвольные дополнительные ключи и значения, не соответствующие форме типа, отклоняются с `422`.

**FR-10. Общий комментарий.** Комментарий ЛК хранится на уровне пакета, не отдельного документа, и показывается в каждом модальном окне ответа на элемент этого пакета. Клиент не редактирует этот комментарий.

### Нефункциональные требования

**NFR-1. Изоляция.** Клиент читает и изменяет только запросы своей компании и своей заявки. ЛК читает и изменяет только собственные запросы. Одна ЛК не получает `form_data`, вложение и статус ответа по запросу другой ЛК. Сотрудник CarCraft получает доступ только по существующей авторизации заявки и бизнес-праву обработки документов.

**NFR-2. Персональные данные.** Полный номер СНИЛС не записывается в application-логи, HTTP-ошибки, уведомления, Kafka-события, DWH или аналитические события. При повторном чтении клиент получает маскированное значение вида `***-***-*** 01`. Полное значение возвращается только ЛК-владельцу запроса и уполномоченному сотруднику CarCraft, которым оно требуется для обработки заявки.

**NFR-3. Атомарность.** Если загрузка файла, проверка формы или запись связи с запросом завершается ошибкой, ответ не переводится в `provided`; повторная попытка остаётся возможной. Внешнее хранилище файла при неуспешной транзакции должно быть очищено либо помечено механизмом компенсации, принятым существующим загрузочным потоком.

**NFR-4. Совместимость.** Существующие запросы без форм продолжают отображаться и загружаться как раньше. Новые поля для старых строк имеют безопасные значения `has_form=false`, `form_schema=null`, `form_data=null`.

## Решения и инварианты

- `form_data` не является свободным пользовательским JSON. Это фиксированное дополнение конкретного запроса, структура которого определяется сохранённым `form_schema`.
- `form_schema` — единый контракт между интерфейсом и сервером; фронтенд не является единственным валидатором.
- Каталог используется только как шаблон для новых запросов. Исторический запрос хранит неизменяемый снимок формы.
- Пользовательское изменение `display_name` каталожного типа не меняет `document_type`, `has_form` или `form_schema`.
- Ручной запрос не попадает в каталог и не может иметь форму.
- Один запрос связан ровно с одним ответным файлом. Нельзя заменить, добавить второй или удалить файл через данный сценарий.
- Переход в `provided` возможен только из `requested`, только после получения обязательного файла и, при наличии формы, валидного `form_data`.
- Новый запрос вместо исправления создаёт новый UUID и новый статус `requested`; предыдущая запись и её ответ остаются в истории.
- `approved` у `company_requisites` остаётся внутренним значением и не меняет общую статусную модель.

## Контракт `form_schema` и `form_data`

`form_schema` — JSONB-объект версии 1. Он содержит `schema_version`, `kind` и фиксированное описание полей. Backend использует `kind` как выбор строгого валидатора; frontend использует описание для построения формы, меток, обязательности, минимального и максимального числа строк.

### Основные контрагенты

`form_schema` имеет `kind: "main_counterparties"`, поле `counterparties`, минимальное количество 1, максимальное 10. Каждый элемент содержит обязательные `inn` и `name`.

`form_data`:

```json
{
  "counterparties": [
    {
      "inn": "7707083893",
      "name": "ООО Ромашка"
    }
  ]
}
```

ИНН обязателен для каждого контрагента. Допускаются 10-значный ИНН юридического лица и 12-значный ИНН физического лица. Контрагент без ИНН не принимается. Повторяющиеся ИНН разрешены. В интерфейсе показаны поля «ИНН» и «Название», а кнопка «Добавить ещё контрагента» добавляет следующую строку. Название документа и комментарий ЛК остаются только для чтения над формой и не входят в `form_data`.

### СНИЛС

`form_schema` имеет `kind: "snils"`, одно обязательное поле `number`.

`form_data`:

```json
{
  "number": "12345678901"
}
```

Интерфейс принимает ввод цифрами, с пробелами и с дефисами. Сервер удаляет пробелы и дефисы, принимает ровно 11 цифр и сохраняет нормализованное значение. Контрольная сумма не проверяется. Повторные номера разрешены.

### Открытые расчётные счета

`form_schema` имеет `kind: "open_bank_accounts"`, поле `accounts`, минимальное количество 1, максимальное 10. Каждый элемент содержит обязательные название банка, БИК и номер счёта.

`form_data`:

```json
{
  "accounts": [
    {
      "bank": {
        "name": "АО Банк",
        "bik": "044525225"
      },
      "acc_number": "40702810000000000001"
    }
  ]
}
```

В проекте нет отдельного справочника банков, поэтому применяется свободный ввод. Подсказка поля: «Укажите наименование банка и БИК». БИК содержит ровно 9 цифр, номер счёта — ровно 20 цифр. Повторяющиеся счета разрешены. В интерфейсе кнопка «Добавить ещё счёт» добавляет следующую группу полей.

### Выгодоприобретатель по сделке

`form_schema` имеет `kind: "beneficial_owner"`, одно обязательное поле `fio`.

`form_data`:

```json
{
  "fio": "Иванов Иван Иванович"
}
```

Запрашивается одно лицо; сведения о дате рождения, ИНН, гражданстве, доле участия и другие данные не входят в объём.

## Технические контракты

### Frontend

- В модальном окне ЛК каждая строка запроса содержит селектор каталога, опцию «Произвольный документ» и поле отображаемого названия.
- При выборе каталожного типа название подставляется автоматически; редактирование отображаемого названия не меняет тип и форму. Интерфейс явно сообщает: «Тип документа и состав обязательных полей сохраняются».
- При выборе «Произвольный документ» каталог не используется, ЛК вводит название, а дополнительная форма не показывается.
- В истории клиента действие «Выбрать файл» заменяется открытием модального окна ответа. Системный выбор файла доступен только внутри этого окна.
- Форма не отправляется при отсутствии файла, невалидных значениях либо повторной отправке. Ошибка сервера выводится в модальном окне без раскрытия чувствительных значений.
- После успеха модальное окно закрывается, история перечитывается, а отображение показывает один прикреплённый файл и отправленные данные формы в разрешённом для роли виде.

### Backend и API

- `GET /api/v1/documents/types` возвращает `has_form` и `form_schema` для каждого типа наряду с существующими полями.
- `PUT /api/v1/leasing/applications/{application_id}/request-documents` расширяется для происхождения каталожного/произвольного типа и возвращает созданные элементы со UUID, техническим типом, отображаемым названием и снимком формы. Это создание запроса ЛК, а не ответ клиента.
- `GET /api/v1/applications/{application_id}/document-requests` сохраняет группировку `batches`; данные конкретной формы возвращаются внутри соответствующего `items[]` и фильтруются по роли и владельцу ЛК.
- `POST /api/v1/documents` с `document_request_id` принимает ровно один файл, `application_id`, опциональный `form_data` и заголовок `Idempotency-Key`. Для отсутствующего файла, второго файла, отсутствующего `form_data` при форме, невалидной формы или чужого запроса сервер возвращает ошибку и не меняет запрос.
- `409 Conflict` возвращается, если запрос уже не находится в `requested` или не может быть атомарно переведён в `provided`.
- `422 Unprocessable Entity` возвращается для нарушения структуры или формата `form_data`.

### Данные и миграции

Миграция добавляет `document_types.has_form` и `document_types.form_schema`, а также в `application_document_requests` поля `has_form`, `form_schema`, `form_data` и технические данные идемпотентности, необходимые для единой отправки.

Миграция:

- задаёт безопасные значения для существующих типов и запросов;
- добавляет тринадцать типовых записей;
- сохраняет `auto_approve=false` для новых записей;
- не меняет существующие статусы, файлы и историю;
- добавляет ограничения согласованности `has_form` и `form_schema`;
- не переводит UUID в числовой формат.

После изменения схемы должны быть обновлены ER-диаграммы и журнал схемы по правилам проекта.

### События и интеграции

Существующие события изменения заявки и ЛК могут сообщать об изменении статуса без `form_data`. `form_data`, особенно СНИЛС, не публикуется в Kafka, не записывается event-worker в ClickHouse и не включается в уведомления. Внешние интеграции и новый банковский справочник не добавляются.

## Ошибки и граничные случаи

- Неизвестный каталожный `document_type` при создании запроса — `422`.
- Попытка передать `has_form` или `form_schema` в теле запроса ЛК как источник правил — `422`; эти значения определяет сервер.
- Пустое либо повторяющееся отображаемое название внутри одного пакета обрабатывается действующими правилами уникальности `slug`.
- В `main_counterparties` менее одного или более десяти контрагентов, ИНН не из 10 или 12 цифр, пустое название — `422`.
- В `snils` после удаления пробелов и дефисов не 11 цифр — `422`; контрольная сумма не проверяется.
- В `open_bank_accounts` менее одного или более десяти счетов, БИК не из 9 цифр, номер счёта не из 20 цифр, пустое название банка — `422`.
- Для `beneficial_owner` пустое ФИО — `422`.
- Отсутствующий файл для любого запроса — `400` или `422` в соответствии с единым upload-контрактом, но без сохранения `form_data` и без смены статуса.
- Ошибка хранилища файла, валидации или записи БД не создаёт частично предоставленный ответ.
- Повтор с тем же `Idempotency-Key` возвращает исходный результат; запрос с новым ключом после успеха — `409`.

## Безопасность и приватность

- Проверка прав выполняется backend до чтения, выдачи presigned-ссылки, сохранения формы и загрузки файла.
- Проверяется полный контекст владения: заявка, компания клиента, ЛК-владелец запроса и пользователь.
- Технические UUID не заменяются числовыми идентификаторами и не принимаются как взаимозаменяемые типы.
- Полный СНИЛС доступен только уполномоченной ЛК-владельцу запроса и сотруднику CarCraft с правом обработки документов; при последующих чтениях клиент видит маску.
- Валидационные ошибки называют поле и правило, но никогда не повторяют полный СНИЛС или другие чувствительные значения.

## Наблюдаемость

Логи содержат только технические данные: UUID заявки, запроса, ЛК, тип формы, статус результата и код ошибки. Логи не содержат `form_data`, имени контрагента, номера счёта, БИК или СНИЛС. Метрики допускают счётчики создания запросов, ответов, отказов валидации и конфликтов идемпотентности без значений форм.

## Совместимость, rollout и rollback

Изменение разворачивается миграцией, затем backend и frontend в одном релизе. До выпуска frontend backend обязан корректно читать исторические строки без новых данных. Откат приложения не должен удалять новые колонки, данные форм или загруженные файлы. Откат миграции возможен только отдельной согласованной процедурой и не является частью штатного rollout.

## Проверка и тестирование

- Backend unit-тесты на все инварианты `has_form` и `form_schema`, четыре валидатора `form_data`, маскирование СНИЛС и нормализацию разделителей.
- Backend интеграционные тесты на создание каталожного и произвольного запроса, снимок формы, обязательный файл, атомарность, UUID-контракт, идемпотентность и `409` при повторной отправке.
- Тесты авторизации и изоляции: чужой клиент, другая ЛК, сотрудник без права обработки, доступ к вложению и к полному/маскированному СНИЛС.
- Frontend тесты на выбор каталожного типа, редактирование только названия, произвольный документ, динамические поля четырёх форм, ограничения от 1 до 10 строк, обязательный файл, блокировку повторной отправки и обновление истории.
- Регрессия отображения `company_requisites` со статусом `approved` как «Принят» в целевом представлении ЛК.
- Проектные линтеры, типовые проверки, миграционный smoke, Docker-запуск, API-проверки и browser-проверки выполняются исполнителями; пользователю не требуется открывать локальные адреса.

## Критерии приёмки

- **AC-1.** В целевом интерфейсе ЛК автоматически прикреплённый `company_requisites` со значением `approved` отображается как «Принят», а значение в API и БД остаётся `approved`.
- **AC-2.** `GET /api/v1/documents/types` возвращает `has_form` и `form_schema`; записи с `has_form=true` и пустой/`null` схемой отсутствуют.
- **AC-3.** Все тринадцать перечисленных типов присутствуют в каталоге с согласованными строковыми кодами и названиями; автоодобрение для них выключено.
- **AC-4.** ЛК может создать каталожный запрос, изменить только его отображаемое название и создать произвольный запрос без формы.
- **AC-5.** Созданный каталожный запрос сохраняет снимок формы; изменение записи `document_types` впоследствии не меняет уже созданный запрос.
- **AC-6.** Клиент для запроса видит модальное окно с названием, общим комментарием ЛК, обязательными полями формы при необходимости и обязательным выбором одного файла.
- **AC-7.** Система отклоняет отправку без файла для любого запроса и без валидного `form_data` для запроса с формой.
- **AC-8.** Система принимает только согласованные формы: 1–10 контрагентов с ИНН из 10/12 цифр; СНИЛС из 11 цифр с допустимыми разделителями; 1–10 счетов с названием банка, БИК из 9 цифр и счётом из 20 цифр; одно непустое ФИО выгодоприобретателя.
- **AC-9.** После успешной единой отправки создаётся ровно один файл и ровно один ответ, `form_data` сохранён, а запрос переходит из `requested` в `provided`.
- **AC-10.** Повторный запрос с тем же ключом идемпотентности не создаёт дубликаты; новая попытка после успеха получает конфликт и не меняет историю.
- **AC-11.** Клиент и другая ЛК не получают чужие `form_data`, файлы, presigned-ссылки или статусы; СНИЛС не попадает в логи, Kafka/DWH, уведомления и последующее клиентское чтение в полном виде.
- **AC-12.** Исторические запросы без формы продолжают отображаться и принимать один обязательный файл без регрессии.
