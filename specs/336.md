## Цель и бизнес-результат

Администратор должен отдельно управлять видимостью модельного ряда и наличием
промежуточного выбора марки для каждой публичной витрины. Для витрины с одним
логическим брендом, например `/faw`, пользователь должен открывать пункт
«Модели» и сразу видеть полный модельный ряд, без лишнего экрана выбора марки.

Страница моделей должна показывать все доступные в текущей витрине модели,
характеристики, изображения и цены, а любой переход из неё должен сохранять
slug витрины.

## Подтверждённое текущее состояние

### 1. Одного переключателя недостаточно

В публичной матрице видимости есть только ключ `models`. Он одновременно
управляет входом в раздел, но не позволяет отключить промежуточный экран марок.
На `test` для FAW `public.models=true`, а `/faw/models` всё равно сначала
показывает выбор бренда, хотя в storefront facets доступна одна логическая
марка `FAW`.

### 2. Часть моделей теряется на границе объединённых марок

Backend намеренно объединяет одинаковые отображаемые названия марок. На
31.08.2026 FAW возвращает одну логическую марку с основным `id=42342231` и
массивом из 170 физических `ids`. Текущая страница передаёт в models facets
только `brand.id`:

- запрос с `mark_id=42342231` возвращает 1 модель;
- запрос с полным CSV из `brand.ids` возвращает 170 моделей.

Минимальный HTTP-replay воспроизводит дефект детерминированно: сравнение этих
двух количеств завершается с `current-page-models=1 expected-models=170`.

### 3. Изображения и статистика не загружаются из-за невалидного limit

`frontend/pages/models/index.vue` запрашивает автомобили с `limit=10000`, а
`frontend/pages/models/[brandId].vue` — с `limit=1000`. Публичный backend
разрешает максимум `100`, поэтому `test` отвечает `422 VALIDATION_ERROR`.
Ошибки подавляются в `console.error`, и пользователь получает пустые
изображения, цены и статистику.

При корректном `limit=100` проверенные 100 из 100 автомобилей FAW содержат
изображения. Следовательно, наблюдаемый дефект не объясняется отсутствием
изображений в данных.

### 4. Характеристики в данных есть, но клиентская загрузка не масштабируется

Публичный endpoint характеристик на `test` для проверенной модели возвращает
реальные значения объёма, мощности и разгона. Сейчас frontend делает отдельный
последовательный запрос для каждой модели. После исправления полного набора FAW
это станет 170 дополнительными запросами и оставит страницу уязвимой к
частичным сбоям. Нужен один витринно-ограниченный read-контракт карточек
модельного ряда.

### 5. Переход с карточки теряет storefront

`navigateToModel` использует жёсткий `path: '/cars'`, а не
`publicRoute('/cars')`. Из `/faw/models/*` пользователь попадает в корневой
каталог и теряет контекст витрины.

## Функциональные требования

### 1. Раздельные настройки публичной видимости

В области «Публичный сайт» для каждой основной или дополнительной витрины
должны быть два отдельных переключателя:

1. **«Модели»** (`models`) — существующий переключатель входа в модельный ряд.
2. **«Выбор марки перед моделями»** (`model_brand_selection`) — новый
   переключатель промежуточного экрана марок.

Правила применения:

- `models=false` скрывает пункт «Модели» в публичной навигации, как сейчас;
  значение `model_brand_selection` при этом не открывает раздел самостоятельно;
- `models=true` и `model_brand_selection=true` открывают `/models` со списком
  логических марок, после выбора марки показывается её полный модельный ряд;
- `models=true` и `model_brand_selection=false` открывают `/models` сразу со
  всеми моделями текущей витрины, без поиска, сортировки и карточек марок;
- настройка хранится и применяется отдельно для каждой витрины;
- значение по умолчанию для `model_brand_selection` — `true`, чтобы существующие
  витрины сохранили текущее поведение до явного изменения администратором;
- новая витрина наследует эффективное значение основной витрины тем же
  механизмом, что и остальные публичные настройки;
- настройка управляет представлением, но не вводит запрет прямого URL
  `/models` или `/models/{brandId}`.

Если администратор отключил выбор марки для витрины с несколькими логическими
марками, `/models` показывает единый список моделей всех доступных марок. Это
fail-safe поведение не создаёт тупикового маршрута; на карточке в таком режиме
должно быть видно название марки.

### 2. Полный и корректный модельный ряд

- Логическая марка должна использовать весь массив `ids`, полученный из marks
  facets, а не только основной `id`.
- `/models/{brandId}` должен находить логическую марку, в чей массив `ids`
  входит `brandId`, и показывать модели всех физических записей этой марки.
- На `/models` без промежуточного выбора должны отображаться все модели,
  доступные в выбранной витрине.
- Карточка модели показывает название, марку при смешанном списке, годы выпуска,
  количество доступных автомобилей, изображение или явный placeholder, диапазон
  цен и три характеристики: объём двигателя, максимальную мощность и разгон до
  100 км/ч.
- Нулевые или отсутствующие цены не должны отображаться как фиктивный диапазон
  `0–0`; вместо него показывается согласованный нейтральный текст
  «Цена по запросу».
- Отсутствующая характеристика отображается как `—`, без вывода технического
  `N/A` пользователю.
- Ошибка загрузки показывает локальный понятный error-state с кнопкой повтора,
  а не маскируется под пустой каталог и не остаётся только в консоли.
- Экран загрузки, пустое состояние, управление с клавиатуры и focus-visible
  должны соответствовать существующему desktop UI; интерфейс ниже 768 px не
  добавляется.

### 3. Storefront-aware навигация

- Все ссылки, breadcrumbs, CTA и программные переходы страницы моделей должны
  строиться через `publicRoute`.
- Клик по модели из `/{slug}/models*` ведёт в `/{slug}/cars` с фильтром выбранной
  модели и полным набором физических `mark_id` логической марки, когда он нужен.
- Переход не должен сбрасывать storefront на корневой `/cars` ни при клиентской
  навигации, ни при прямом открытии/SSR.
- Неизвестный `brandId` не должен молча показывать пустую успешную страницу:
  используется контролируемое состояние «марка не найдена» либо storefront 404.

## Реализованный технический контракт

### Backend

1. Добавить `model_brand_selection: true` в доменный каталог публичной
   видимости и покрыть его значениями по умолчанию, чтением, административным
   PATCH и инициализацией новой витрины.
2. Схему таблицы `section_visibility` не менять: ключи валидируются доменным
   каталогом, а существующие строки дополняются эффективным default при чтении.
   Отдельная Alembic-миграция не требуется, если реализация не обнаружит
   фактического DB constraint по `section_key`.
3. Добавить один read-only endpoint карточек модельного ряда:
   - `GET /api/v1/cars/model-showcase` для основной витрины;
   - `GET /api/v1/storefronts/{storefront_slug}/cars/model-showcase` для
     дополнительной витрины;
   - необязательный `mark_id` принимает один ID, CSV либо повторяющиеся
     параметры и фильтрует по полному набору физических марок.
4. Endpoint возвращает одну запись на модель без пагинации автомобилей и без
   N+1-запросов. Ответ обёрнут в совместимый объект `items`/`pagination`, при
   этом все агрегированные модели возвращаются одной полной страницей:
   - `id`, `name`, `mark_id`, `mark_name`, `year_from`, `year_to`;
   - `vehicles_count`, `image_filename`;
   - `min_price`, `max_price`;
   - структурированные `volume`, `horse_power`, `time_to_100`.
5. Агрегация учитывает только доступные автомобили текущего `CatalogScope`,
   выбранные склады витрины и действующие правила публичной доступности.
   Иностранные для витрины модели, автомобили, цены и изображения не попадают
   в ответ.
6. Статический маршрут `model-showcase` регистрируется до динамического
   `/{vehicle_id}`, чтобы его не перехватывал detail endpoint.
7. Существующие `/cars/facets` и `/cars/specifications/{model_id}` остаются
   совместимыми для текущих клиентов; страница моделей перестаёт собирать
   карточки через невалидные listing limits и последовательные spec-запросы.

### Frontend

1. Расширить каталог и safe defaults feature-модуля `sectionVisibility` новым
   ключом и отдельной строкой переключателя в существующей вкладке
   «Публичный сайт».
2. Добавить типизированный метод `carsApi.getModelShowcase` и типы ответа без
   `any` и без числового преобразования идентификаторов.
3. Вынести сетевую загрузку и представление модельных карточек в общий
   feature-компонент/composable, используемый `/models` и
   `/models/[brandId]`, чтобы две страницы не расходились по данным, ошибкам и
   storefront-навигации.
4. `/models` читает активную публичную матрицу:
   - при включённом `model_brand_selection` показывает список марок;
   - при выключенном сразу отображает общий model showcase.
5. При выборе логической марки frontend сохраняет её основной URL `id`, но для
   фильтрации использует весь непрозрачный массив `ids`.
6. Удалить запросы `limit=10000` и `limit=1000`, последовательный цикл
   `getCarSpecifications` и жёсткий переход в `/cars`.
7. Для изображения использовать общий `vehicleImageUrl`; при ошибке загрузки
   показывать `car-placeholder.png`. Для отсутствующего логотипа марки не
   скрывать пустое место, а показывать нейтральный fallback с названием марки.

### Backend

- Domain/application tests подтверждают новый public default, валидацию ключа,
  раздельное сохранение по storefront и наследование новой витриной.
- Repository/application tests model showcase проверяют:
  - две физические марки с одинаковым названием и модели под обеими;

  - отсутствие недоступных и чужих для витрины данных;

- HTTP integration tests проверяют root и scoped маршруты, 404 неизвестной
  витрины, статический route order и отсутствие авторизации у публичного GET.

### Frontend architecture/regression

- Каталоги frontend/backend содержат одинаковый ключ
  `model_brand_selection` с default `true`.
- Обе models-страницы используют новый API и `publicRoute`, не содержат
  `limit=1000/10000`, жёсткого `path: '/cars'` и N+1 spec-цикла.
- Логическая марка разворачивает полный массив opaque `ids` без `Number`,
  `parseInt`, `parseFloat` и резервного выбора другого ID-поля.
- Проверяются loading/error/empty/image fallback и смешанный список моделей.

5. После выключения `/{slug}/models` сразу показывает обе модели и не показывает

## Фактический результат реализации

- В backend добавлены публичные root/scoped endpoints `model-showcase` и одна
  витринно-ограниченная SQL-агрегация моделей, доступных автомобилей, цен,
  изображений и характеристик без N+1.
- Логические марки нормализуют пустое имя до непрозрачного ID и всегда
  раскрываются в полный набор физических `ids`. Версия snapshots facets
  повышена, чтобы ранее закэшированный nullable-контракт не сохранялся.
- В матрицу видимости добавлен независимый ключ
  `model_brand_selection=true`; UI показывает отдельный переключатель
  «Выбор марки перед моделями» для каждой витрины.
- Обе страницы models используют общие feature-компоненты и composable,
  storefront-aware маршруты, явные loading/error/retry/empty/fallback состояния
  и единый model-showcase API.
- Fallback изображения работает и для SSR-гонки, когда ошибочный ответ успел
  завершиться до гидрации Vue: компонент после монтирования проверяет уже
  загруженный `<img>` и заменяет источник при `naturalWidth=0`.
- Namespace-aware E2E fixture создаёт одно- и многобрендовую витрины, две
  физические записи одной логической марки, модели, характеристики, цены и
  реальный PNG в объектном хранилище. Suite 22130 включён в общий E2E runner и
  правила GitLab job.
- Выполнены три независимых цикла review по стандартам репозитория и по этой
  спецификации. В финальном срезе замечаний по обеим осям нет.

## Критерии готовности

1. В «Публичном сайте» выбранной витрины администратор видит независимые
   переключатели «Модели» и «Выбор марки перед моделями».
2. Существующие витрины после релиза продолжают показывать выбор марки, пока
   второй переключатель явно не выключен.
3. Для FAW при выключенном выборе марки `/faw/models` сразу показывает полный
   модельный ряд всех физических FAW mark IDs.
4. Все ожидаемые модели имеют корректные характеристики, изображение/fallback
   и цену/«Цена по запросу»; частичный сбой не маскируется под пустой каталог.
5. Прямой `/faw/models/{brandId}` также показывает полный логический бренд, а
   неизвестная марка обрабатывается контролируемо.
6. Все переходы остаются под `/faw`; ни одна ссылка страницы моделей не
   выбрасывает пользователя в корневой storefront.
7. Новая настройка и модельные данные изолированы между витринами.
8. Backend, frontend, E2E, сборка, runtime smoke и просмотр логов выполнены и
   перечислены в MR.
9. MR создаётся только в `test`; после создания спецификация переименовывается
   в `specs/<номер-MR>.md` и отправляется в ту же ветку.

## Границы и решения для review

- Не меняются права доступа, JWT, роли, cart/favorites и прямой доступ к
  публичным routes.
- Не добавляется mobile UI ниже 768 px.
- Не вводится отдельная таблица настроек модели и не дублируется storefront
  branding.
- Не исправляются данные FAW массовым объединением строк марок: frontend и API
  обязаны корректно поддерживать действующий контракт логической марки с
  массивом `ids`.
- Предлагаемое имя нового стабильного ключа — `model_brand_selection`, default
  `true`. Если на review требуется другое пользовательское название, ключ и
  семантика всё равно должны оставаться отдельными от `models`.
