# Bitrix #21822 — единая привязка компании клиенту

**Задача:** https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/21822/

## Текущее поведение

1. В админском окне «Создать пользователя» поле «Компания» не показывается для роли `Клиент`: компонент выводит его только для дилера, лизинговой компании и дистрибьютора.
2. При добавлении компании из профиля клиента фронтенд использует `CompanyAutocomplete` и отправляет объект выбранной компании в `POST /api/v1/users/me/companies`.
3. Backend создаёт или находит компанию по ИНН и создаёт связь в `user_companies`, но не заполняет основное поле `users.company_id`.
4. Админский список пользователей показывает компанию только через `users.company_id`. Поэтому у клиента в профиле компания есть, а в строке админского списка отображается «Не указан/Не найдено».
5. Отсутствие основной компании в `users.company_id` нарушает единый контекст компании клиента и приводит к недоступности его заявок в связанных сценариях.

## Целевое поведение и причина

Клиент всегда должен иметь согласованную основную компанию как в личном кабинете, так и в админской панели. Это необходимо, чтобы администратор видел фактическую компанию клиента, а клиент продолжал работать со своими заявками в корректном контексте компании.

Должны поддерживаться два равнозначных пути:

- администратор создаёт клиента и сразу выбирает компанию по названию или ИНН;
- клиент, созданный без компании, добавляет первую компанию из своего профиля.

В обоих случаях основная компания сохраняется в `users.company_id`, поэтому отображается в админском списке. Связь через `user_companies` сохраняется для списка компаний и прав доступа.

## Выбранный подход

Использовать уже применяемый безопасный поток `CompanyAutocomplete` и backend-логику `create_or_get_company`, без прямых вызовов DaData из браузера и без отдельной таблицы или миграции.

1. Для роли `Клиент` в форме администратора показать поле выбора компании тем же `CompanyAutocomplete`, что используется в профиле.
2. Передавать в `POST /api/v1/users` полный объект компании, выбранный через `@select`; backend находит или создаёт запись по ИНН в рамках создания пользователя.
3. Для клиента с выбранной компанией установить её как `users.company_id` и создать/сохранить связь `user_companies` с правами администратора компании, чтобы клиент мог создавать и видеть заявки в её контексте.
4. При `POST /api/v1/users/me/companies` для клиента без основной компании после успешной привязки установить первую добавленную компанию в `users.company_id`. При добавлении второй и последующих компаний уже установленную основную компанию не заменять автоматически.
5. Оставить существующее поведение для ролей дилера, дистрибьютора и лизинговой компании без изменений.

## Рассмотренные варианты

### Вариант A — изменить только админский список

Показывать первую запись из `user_companies`, если `users.company_id` пуст.

Не выбран: маскирует рассинхронизацию данных и не восстанавливает основной контекст компании, от которого зависят сценарии заявок.

### Вариант B — создать отдельный admin-эндпоинт добавления компании после создания пользователя

Не выбран: создаёт неатомарный двухшаговый сценарий. Пользователь может быть создан, а привязка компании — не выполниться.

### Вариант C — единый атомарный поток при создании и дополнение self-service сценария

Выбран: повторно использует существующий поиск и создание/поиск компании, сохраняет одну согласованную основную связь и минимизирует изменения интерфейса и API.

## Планируемые изменения

### Frontend

- `frontend/features/auth/components/UserFormModal.vue`
  - для роли `client` отображать выбор компании через `CompanyAutocomplete`;
  - хранить выбранный объект компании отдельно от его отображаемой строки;
  - передавать объект в запрос создания пользователя только при фактическом выборе из подсказок;
  - не менять существующий select компаний для остальных ролей.

- `frontend/tests/architecture/` — добавить или расширить регрессионный тест на контракт формы:
  - для `client` используется `CompanyAutocomplete`;
  - объект из `@select` передаётся в запрос создания;
  - техническая строка поиска не отправляется вместо объекта компании.

### Backend

- `backend/presentation/schemas/users.py`
  - расширить контракт `UserCreateBody` необязательным объектом компании по существующей схеме полей компании;
  - сохранить UUID-тип для `company_id` и не вводить числовых преобразований идентификаторов.

- `backend/presentation/routers/users.py`
  - передать объект компании в команду создания пользователя.

- `backend/application/commands/admin_users/create_user.py`
  - для клиента с выбранным объектом найти или создать компанию через существующий репозиторий;
  - в одной транзакции сохранить `users.company_id` и связать клиента с компанией через `user_companies` с правами администратора;
  - сохранить текущую валидацию дубликатов телефона, email, роли и явного `company_id`.

- `backend/application/commands/user_companies.py`
  - после self-service добавления первой компании клиенту без `users.company_id` назначить эту компанию основной;
  - не переписывать уже назначенную основную компанию при последующих добавлениях;
  - не менять правила для других ролей.

- `backend/infrastructure/repositories/admin_users_repository.py` и/или `backend/infrastructure/repositories/company_registration_repository.py`
  - добавить минимальный репозиторный метод для установки основной компании пользователя и идемпотентного создания связи, если существующих методов недостаточно;
  - не выполнять `commit()` в репозитории.

- `backend/tests/test_admin_users_handler.py`
  - покрыть создание клиента с компанией: заполнены `users.company_id` и запись `user_companies` с правами создания/просмотра заявок;
  - покрыть повторное использование уже существующей компании по ИНН.

- `backend/tests/integration/test_users_me_router.py`
  - покрыть добавление первой компании клиентом: обновляется основная компания;
  - покрыть добавление второй: исходная основная компания не меняется.

## Критерии готовности

1. Администратор при выборе роли «Клиент» видит поле поиска компании по названию или ИНН; оно использует существующие подсказки и требует выбрать вариант из списка.
2. При создании клиента с выбранной компанией в `users.company_id` хранится UUID этой компании, а в `user_companies` есть связь клиента с правами администратора.
3. В админском списке после обновления отображаются название и ИНН выбранной компании вместо «Не указан/Не найдено».
4. Если клиент без основной компании добавляет первую компанию через «Профиль → Добавить компанию», она видна и в профиле, и в админском списке.
5. Добавление второй компании не меняет основную компанию клиента незаметно для него.
6. Клиент, которому компания назначена любым из двух путей, имеет права просматривать и создавать заявки в контексте этой компании.
7. Поведение создания пользователей других ролей и добавления компаний ими не изменяется.
8. Выполнены backend-проверки из `AGENTS.md`: `ruff`, `lint-imports`, `mypy`, целевые и полный `pytest`; выполнены frontend architecture tests, production build и `git diff --check`.
9. Перед MR сценарии проверены Hermes в Docker/браузере с тестовыми данными: создание клиента администратором и добавление первой компании существующим клиентом. В MR приложены результаты проверок.

## Риски и ограничения

- Компания выбирается только из результата `CompanyAutocomplete`; ручная строка не должна создавать некорректную связь без ИНН.
- Затрагивается контекст доступа к заявкам, поэтому изменения должны быть атомарными: при ошибке создания/поиска компании пользователь не должен остаться с частично созданной привязкой.
- Полный набор backend-проверок может выявить ранее существующие несвязанные ошибки. Их нужно отделить от результатов целевых тестов, а не считать исправление проверенным без объяснения.

## Открытые вопросы

Блокирующих вопросов нет. В этой задаче основной компанией считается первая компания, добавленная клиенту из профиля; дальнейшие добавления не меняют её автоматически.
