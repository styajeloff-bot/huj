## 1. Постановка задачи и контекст

Ранее при доставке выполненных задач агенты сталкивались с несколькими проблемами:
1. Разделение отправки ветки (`git push`) и создания Merge Request на отдельные шаги, что требовало дополнительных команд от пользователя и приводило к ответу `Everything up-to-date` при попытке создать MR повторно.
2. Неопределённость способа создания MR: агенты пытались использовать внешние CLI (`glab`) или API, запускали лишнюю сетевую диагностику (`ssh -Tv`, `which glab`).
3. Фатальные ошибки при использовании GitLab Push Options из-за наличия переносов строк (`\n`) в описании MR (`fatal: push options must not have new line characters`).
4. Повторные коммиты и пуши в ветку задачи исключительно ради внесения ссылки на созданный MR в файл спецификации в `specs/`, что вызывало запуск повторных пайплайнов CI в GitLab.

Требуется структурировать и зафиксировать правила:
- Создать файл `AGENTS.local.md` с пунктами 1 и 2 (однострочность push options и запрет коммита ссылки на MR в спецификацию), упомянуть его в `AGENTS.md` и добавить в `.gitignore`.
- В общий `AGENTS.md` внести пункты 3 и 4 (атомарное создание MR с автослиянием через GitLab Push Options при первом же пуше и канонический способ создания без лишней диагностики).

## 2. Требования

### 2.1. Локальные инструкции (`AGENTS.local.md`)
1. **Строго однострочные параметры Push Options:**
   Значения параметров `-o merge_request.title="..."` и `-o merge_request.description="..."` должны быть строго в одну строку без символов переноса строки `\n`. Для разделения блоков описания использовать символы `;` или `—`.
2. **Запрет повторного коммита ради спецификации:**
   После отправки ветки и создания MR запрещено делать коммит и повторный пуш исключительно ради добавления ссылки на MR в файл спецификации задачи. Спецификация фиксируется до коммита реализации; ссылка на MR возвращается пользователю в чат и фиксируется GitLab.
3. **Запрет разведочной диагностики окружения:**
   Создание MR через Git Push Options по SSH является каноническим способом: запрещено выполнять предварительную разведочную диагностику окружения (например, `ssh -Tv`, `which glab`) и полагаться на внешние CLI-утилиты (`glab`) или API-токены GitLab.

### 2.2. Конфигурация Git (`.gitignore`)
- Добавить `AGENTS.local.md` в `.gitignore` репозитория, чтобы локальные правила разработчика не коммитились в общий репозиторий.

### 2.3. Общие инструкции монорепозитория (`AGENTS.md`)
1. **Упоминание `AGENTS.local.md`:**
   В начале документа указать, что локальные правила разработчика/агента могут определяться в файле `AGENTS.local.md`, который не отслеживается git и дополняет правила монорепозитория.
2. **Атомарный пуш и создание MR через GitLab Push Options (п. 10–11):**
   - Доставка ветки и создание MR выполняются сразу при первом же пуше через Push Options GitLab:
     ```bash
     git push -u origin HEAD \
       -o merge_request.create \
       -o merge_request.target=test \
       -o merge_request.title="<title>" \
       -o merge_request.description="<description>" \
       -o merge_request.merge_when_pipeline_succeeds
     ```
   - Запрещено разделять доставку на предварительный пуш и отдельный запрос создания MR.
   - Флаг автослияния (`merge_when_pipeline_succeeds`) выставляется сразу при создании MR.
