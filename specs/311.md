## Контекст и исходное состояние

В `test` уже присутствует частичная реализация задачи из merge request !287
(`2e976c4d`, merge `0bd6020d`). Актуальная редакция v5.16 расширяет и местами
меняет прежний контракт:

- отбор кандидатов-надстроек по `role=attachment` и серверный `root_items`
  в основном уже реализованы; их необходимо сохранить и покрыть регрессиями;
- `component_blocks` сейчас опционален и имеет прежнюю схему, а плоские
  характеристики составного объявления по-прежнему смешиваются;
- trim-таблицы и базовые маршруты уже созданы миграцией 089, поэтому их нельзя
  создавать повторно; требуется адаптация существующей схемы и API к v5.16;
- неявный контекст категории по одной модификации реализован частично и
  асимметрично для `/facets`, `/products` и фронтенда;
- удалённая ветка `origin/feature/22098-attribute-contract` отстаёт от `test` и
  содержит только узкий фрагмент контракта. Она не переносится целиком; нужные
  изменения типов и тестов воспроизводятся на актуальной базе.

Все шесть доработок входят в один релиз и не имеют взаимных приоритетов.

## Область задачи

Изменения выполняются только в модуле каталога спецтехники
`special-equipment`: публичная витрина, административный каталог, его FastAPI
контракты, модели/репозитории, импорт значений характеристик, миграция и тесты.

Модуль `cars`, мобильный интерфейс и viewport меньше 768 CSS-пикселей не
изменяются. Для сущностей используются UUID: в Python — `uuid.UUID`, во
фронтенде — непрозрачные строки без числового преобразования.

## Функциональные требования

### 1. Кнопка «С пробегом»

- В административной форме каталога подпись и радиокнопка «С пробегом» не
  переносятся на разные строки при ширине viewport не менее 1280 пикселей.
- Существующий набор переключателей, семантика выбора, focus-состояние и
  клавиатурное управление не меняются.
- Изменение локально для desktop-формы спецтехники и не добавляет мобильных
  media query.

### 2. Кандидаты-надстройки

- `GET /api/v1/admin/special-equipment/products?role=attachment` остаётся
  единственным источником списка кандидатов в редакторе составного объявления.
- Сервер включает только несоставные объявления, чья активная категория
  является категорией-надстройкой либо её активным рекурсивным потомком.
- Проверка `compatible-attachments` не ограничивает видимость кандидата.
- Фильтр роли применяется до поиска и пагинации; `total` и страницы считаются
  по уже отфильтрованному набору.
- Фронтенд не выполняет повторную эвристическую фильтрацию ответа.

### 3. Блоки характеристик публичной карточки

`GET /api/v1/special-equipment/products/{id}` всегда возвращает
`component_blocks` как массив, никогда не `null` и не отсутствующее поле.

Один блок имеет контракт:

- `product_id: UUID`;
- `role: "base" | "attachment"`;
- `title: string`;
- `groups: array`, где группа содержит `group_id: UUID | null`,
  `group_name: string | null` и `attributes`;
- характеристика содержит `attribute_id`, `name`, `data_type`, `unit`, `value`,
  обязательные nullable-поля `option_id` и `option_label`.

Правила формирования:

- атомарное объявление имеет ровно один блок `base` для самого себя;
- составное объявление имеет первым блок `base`, затем по одному блоку
  `attachment` для каждой надстройки;
- надстройки сортируются без учёта регистра по `title`, затем по `product_id`;
- при одинаковом исходном `title` ко всем конфликтующим заголовкам добавляется
  ` (<публичный code объявления>)`; VIN не используется и не раскрывается;
- группы и характеристики внутри блока сохраняют действующий порядок;
- межблочная дедупликация запрещена: одинаковый `attribute_id` показывается в
  каждом компоненте со своим значением;
- отдельного поля/строки «Источник» и ссылки на исходную модификацию в блоке
  нет;
- для `group_id = null` API возвращает также `group_name = null`, а витрина
  отображает псевдо-группу «Без группы» без создания сущности в БД;
- для `select` фронтенд показывает `option_label`, для `number` — `value` с
  `unit`, для `text` и `boolean` — отображаемое значение по текущим правилам.

Плоские `attributes` и `attribute_groups` остаются в ответе. Для атомарного
объявления их семантика не меняется; для составного они содержат только
характеристики базового компонента. Это зафиксированный breaking change данных.

### 4. Корневые категории витрины

- `GET /api/v1/special-equipment/categories` возвращает `root_items` всегда.
- Сервер строит его по полному активному набору корневых категорий: активная
  категория без активного родителя считается корневой, включая ребёнка
  неактивного родителя.
- Сортировка выполняется сервером по названию без учёта регистра с русской ICU
  collation, затем по UUID; `sort_order` не участвует.
- Сортировка применяется к полному набору до выдачи, не к отдельной странице.
- Порядок остальных `items` и графа не меняется.
- Главная страница использует порядок `root_items` без клиентской пересортировки.
- Существующие индексы и план запроса проверяются; новый индекс добавляется
  только если текущая схема не обеспечивает приемлемый план.

### 5. Характеристики комплектаций

Существующая trim-схема миграции 089 адаптируется следующей Alembic-миграцией,
а не создаётся заново. Дополнительные совместимые поля (`code`, `slug`,
`sort_order`) сохраняются, если не нарушают v5.16.

#### 5.1. Схема и инварианты

- `special_equipment_trims` принадлежит ровно одной `modification_id`, имеет
  `is_active` и `lock_version >= 1`.
- `special_equipment_trim_attributes` хранит назначение
  `(trim_id, attribute_id)`, nullable `group_id`, `is_required` и
  `is_filterable`; FK группы использует `ON DELETE SET NULL`.
- `special_equipment_trim_attribute_values` хранит ровно один типизированный
  value на назначение и имеет составной FK на trim-назначение.
- `special_equipment_products.trim_id` nullable. Единственный составной FK
  `(trim_id, modification_id)` гарантирует принадлежность комплектации той же
  модификации; отдельный FK только по `trim_id` удаляется, если он присутствует.
- Составное объявление не хранит собственный `trim_id`.
- Create/PATCH/import принимают nullable `trim_id`; при несовпадении
  модификаций возвращается 409 `TRIM_MODIFICATION_MISMATCH`. При PATCH смена
  модификации требует одновременно совместимый `trim_id` либо явный `null`.
- Архивация комплектации выполняется через
  `PATCH /api/v1/admin/special-equipment/trims/{trim_id}` с `is_active` и не
  удаляет назначения/значения. Новый hard-delete endpoint не вводится.

#### 5.2. Кандидаты и назначения

- `GET /trims/{trim_id}/attribute-candidates` собирает effective-набор всех
  активных характеристик всех активных категорий модификации.
- Одинаковая пара `(attribute_id, group_id)` возвращается один раз; порядок
  детерминирован действующими `sort_order`, затем UUID.
- Если один `attribute_id` связан с разными `group_id` в категориях одной
  модификации, ответ — 409 `CATEGORY_ATTRIBUTE_GROUP_CONFLICT` с перечнем
  конфликтующих категорий/групп.
- Nullable `group_id` является штатным кандидатом.
- Кандидат содержит `modification_value`, `is_available` и `block_reason`.
  Заполненная на уровне модификации характеристика недоступна для trim с
  `ATTRIBUTE_ALREADY_USED_IN_MODIFICATION`.
- Пустой effective-набор возвращает 200 `{ "candidates": [] }`.
- `GET /trims/{trim_id}/attributes` возвращает `{ items: [...] }` по полной
  схеме назначения и сохранённого значения, отсортированный по `attribute_id`.
- `POST /trims/{trim_id}/attributes` добавляет одну активную пару из candidates;
  повтор — 409 `ATTRIBUTE_ALREADY_ASSIGNED`.
- `DELETE /trims/{trim_id}/attributes/{attribute_id}` удаляет назначение и его
  значение; отсутствие назначения является успешным no-op с 204.
- Текущий внутренний сценарий массовой замены назначений переводится на
  POST/DELETE в том же релизе. Старый PUT не используется новым фронтендом;
  вопрос его временного сохранения как совместимого маршрута решается по
  реестру потребителей, без расхождения бизнес-инвариантов.

#### 5.3. Значения, ETag и конкуренция

- `PUT /trims/{trim_id}/attribute-values` принимает `{ values: [...] }` и имеет
  patch-семантику: отсутствующие в запросе характеристики не меняются;
  пустое текстовое значение удаляет прежнюю запись, а пустые значения для
  number/boolean/select невалидны.
- Повторный `attribute_id` отклоняет всю пачку с
  `ATTRIBUTE_VALUE_DUPLICATE`; значение неназначенной характеристики —
  `ATTRIBUTE_NOT_ASSIGNED`; чужой/неактивный option — `INVALID_OPTION`.
- Вся пачка атомарна. Ответ содержит только фактически применённые изменения в
  `{ saved: [...] }`; `values: []` — no-op.
- Все мутации существующей trim требуют `If-Match`; отсутствие даёт 428,
  устаревшее значение — 412, без частичного сохранения.
- Сильный ETag имеет форму
  `"<trim_id>:<lock_version>:<sha256-канонического полного GET attributes>"`.
  Канонизация детерминирована. `lock_version` и ETag меняются только при
  фактическом изменении хранимого состояния.
- Два параллельных запроса с одним актуальным ETag дают ровно один изменяющий
  2xx и один 412.
- Безопасный повтор после сетевого сбоя выполняется через повторный GET,
  сравнение состояния и новый `If-Match`, а не слепым повтором старого запроса.

#### 5.4. Межуровневый инвариант

Одна характеристика не может одновременно иметь непустое значение на уровне
модификации и хотя бы одной её комплектации.

- Trim-мутация блокирует modification и trim в детерминированном порядке.
- Management PATCH модификации, import worker и все остальные writers значений
  используют тот же порядок блокировок и общий валидатор.
- Синхронный конфликт возвращает 409
  `ATTRIBUTE_ALREADY_ASSIGNED_IN_TRIM` либо
  `ATTRIBUTE_ALREADY_USED_IN_MODIFICATION` по направлению записи.
- Для импорта ATOMIC завершается failed с машинным кодом; BEST_EFFORT пропускает
  конфликтующую строку и создаёт issue с тем же кодом, не сохраняя двойное
  значение.

#### 5.5. Ошибки и права

Новые trim-маршруты, изменяемые `/facets` и `/products`, а также их
auth/scope/validation ошибки возвращают `application/problem+json` с полями
`type`, `title`, `status`, строковым `detail` и обязательным `code`.

Поддерживаются коды из v5.16: `TRIM_NOT_FOUND`, `ATTRIBUTE_NOT_FOUND`,
`VALIDATION_ERROR`, `ATTRIBUTE_VALUE_DUPLICATE`, `ATTRIBUTE_NOT_ASSIGNED`,
`INVALID_OPTION`, `ATTRIBUTE_ALREADY_USED_IN_MODIFICATION`,
`CATEGORY_ATTRIBUTE_GROUP_CONFLICT`, `PRECONDITION_REQUIRED`,
`PRECONDITION_FAILED`, `ATTRIBUTE_NOT_AVAILABLE_FOR_TRIM`,
`ATTRIBUTE_ALREADY_ASSIGNED`, `ATTRIBUTE_ALREADY_ASSIGNED_IN_TRIM`,
`TRIM_MODIFICATION_MISMATCH` и `CATEGORY_CONTEXT_REQUIRED`.

Для batch-ошибки верхний `code` — `ATTRIBUTE_VALUES_BATCH_FAILED`, а отдельные
ошибки сохраняются в `errors[]`; HTTP 400 имеет приоритет при смеси 400/409,
иначе используется 409. Scope `special-equipment-catalog:read` нужен для GET,
`special-equipment-catalog:write` — для мутаций.

### 6. Фильтры по единственной модификации

Одинаковый resolver контекста используется для
`GET /api/v1/special-equipment/facets` и
`GET /api/v1/special-equipment/products`.

- Явный `category_path` всегда имеет приоритет и работает при любом количестве
  выбранных `modification_id`.
- Без `category_path` и при ровно одной `modification_id` сервер использует её
  активную `is_primary`-категорию, если она входит в публичный граф.
- В этом контексте `/facets` возвращает те же dynamic/usage-фильтры, а
  `/products` применяет их так же, как при явном пути.
- Без доступной primary-категории scalar facets и обычная выдача остаются
  доступны, но category-specific параметры запрещены.
- Без `category_path` при 0 или 2+ модификациях любой из `attribute`,
  `mileage_min`, `mileage_max`, `engine_hours_min`, `engine_hours_max` даёт 422
  `CATEGORY_CONTEXT_REQUIRED`; параметры не игнорируются.
- Фронтенд показывает и сохраняет dynamic/usage-фильтры только при явной
  категории либо ровно одной выбранной модификации с успешно разрешённой
  primary-категорией.
- При переходе к 0 или 2+ модификациям без явной категории фронтенд до запроса
  очищает category-specific state и URL: `attribute`, `usage_min`, `usage_max`
  и соответствующие API-параметры `mileage_*`/`engine_hours_*`.
- На этапах выбора только марки либо марки и модели фильтры не показываются.

## Архитектура и планируемые изменения

- В application-слое выделить общий resolver category context для обоих
  публичных запросов и общий trim state/invariant service для кандидатов,
  назначений, значений, канонического ETag и блокировок.
- Presentation-слой оставить тонким: UUID/Pydantic-схемы, точные маршруты,
  заголовки и единый scoped adapter RFC 9457 без переноса бизнес-правил в router.
- Infrastructure-репозитории отвечают за запросы, row locks, атомарные записи и
  адаптацию существующей схемы 089; application не зависит от SQLAlchemy.
- Existing writers management/import переводятся на один контракт проверки
  межуровневого инварианта, чтобы API и worker не расходились.
- Публичный `component_blocks` строится в application query из данных
  offerings repository; legacy-поля формируются отдельно только из базы.
- Во фронтенде контракты и presentation helpers размещаются в feature
  `specialEquipment`; компоненты получают готовое состояние и не дублируют
  серверную сортировку/фильтрацию.
- Административная trim-форма переводится на candidates по `trim_id`,
  POST/DELETE назначений, patch PUT значений и один актуальный ETag; 412
  показывает понятное состояние конфликта и предлагает перезагрузку.
- Следующая миграция после 095 изменяет только необходимые FK/ограничения/
  индексы и имеет upgrade/downgrade для пустой и заполненной базы.

Ожидаемые зоны изменений:

- `backend/application/queries/special_equipment.py` и management commands;
- `backend/infrastructure/repositories/special_equipment_*_repository.py`,
  import repository/worker и ORM-модели;
- management/public schemas, routers и OpenAPI contracts;
- новая Alembic-миграция;
- `frontend/features/specialEquipment/types.ts`, публичная карточка,
  catalog filters/composables и management correction API/form;
- существующие и новые backend integration/unit, frontend architecture и E2E
  тесты задачи 22098.

## Проверки и тестовое покрытие

### Backend

- Контрактные тесты `component_blocks` для атомарного/составного объявления,
  duplicate attribute, одинаковых title, nullable group и select option.
- Repository/integration тесты кандидатов-надстроек, полного `root_items` и
  двух симметричных публичных filter-маршрутов.
- Migration-тесты на пустой и заполненной PostgreSQL-базе для всех FK,
  `ON DELETE`, CHECK и сохранения существующих данных.
- HTTP-тесты полного trim API, problem details, scopes, 400/409 priority,
  428/412 и детерминированного ETag/no-op.
- Конкурентные integration-тесты: два trim writers; trim против management
  PATCH modification; trim против import worker в ATOMIC и BEST_EFFORT.
- Product create/PATCH/import тесты nullable `trim_id`, mismatch и составного
  объявления.
- Обязательные `ruff`, `lint-imports`, `mypy` и полный `pytest` из корневого
  процесса и профильных backend-инструкций.

### Frontend и браузер

- Architecture/unit-тесты обязательных nullable `option_id/option_label`,
  presentation blocks, implicit category state и нового trim API client.
- E2E публичной карточки и фильтров: явная категория, 0/1/2+ модификаций,
  отсутствие primary, повторяющаяся характеристика и «Без группы».
- E2E административной формы: перенос «С пробегом» при 1280+, список
  надстроек, trim candidates/POST/DELETE/PUT, 412 и повторная загрузка.
- Ручной smoke в авторизованном браузере на desktop viewport 1280+; сценарии
  меньше 768 не добавляются.
- Docker build/up для backend, frontend и nginx, затем health check и просмотр
  логов без новых ошибок.

## Release gate потребителей `attributes` / `attribute_groups`

Breaking change из раздела 3 нельзя объединять/выпускать отдельно от клиентов,
которые отображают характеристики составного объявления. Реестр ведётся в этой
же спецификации, без отдельного документа.

| Потребитель | Ответственный | Подтверждение | Срок перехода |
| --- | --- | --- | --- |
| Публичный web-фронтенд этого репозитория | требуется назначить | будет обновлён в этом MR; подтверждение до merge | тот же релиз |
| Мобильные клиенты, если существуют и читают legacy-поля | требуется ответ пользователя/владельца API | ожидается | до merge |
| Внешние/партнёрские интеграции публичной карточки | требуется ответ пользователя/владельца API | ожидается | до merge |

До заполнения ответственных и фактического подтверждения всех существующих
потребителей MR не переводится в автоматическое объединение.

## Критерии готовности

- Все шесть доработок v5.16 реализованы в одном MR в `test` и не меняют `cars`.
- Публичные и административные API соответствуют точным контрактам выше;
  UUID не приводятся к числам, ошибки имеют `application/problem+json` и code.
- `component_blocks` всегда присутствует, legacy-поля составного объявления
  содержат только базу, а все подтверждённые клиенты перешли на новый массив.
- Trim schema/API/ETag/locks и все writers обеспечивают атомарность и запрет
  двойного значения на уровне modification и trim.
- `root_items`, attachment candidates и category resolver формируются сервером
  в детерминированном порядке; фронтенд не воспроизводит эти правила.
- Все изменённые сценарии покрыты автоматическими тестами, обязательные backend
  проверки зелёные, Docker-сервисы здоровы, логи просмотрены, browser smoke на
  1280+ пройден.
- Спецификация после создания MR переименована в `specs/<номер-MR>.md` и
  отправлена в ту же ветку.

## Вне объёма

- Любые изменения каталога `cars` и нативного мобильного приложения.
- Responsive/mobile-only UI и тесты для viewport меньше 768.
- Hard delete комплектаций и физическое удаление legacy-полей
  `attributes`/`attribute_groups`.
- Раскрытие VIN или других непубличных данных в публичном API.
- Отдельная постоянная документация, ADR, план или отчёт вне этой спецификации.
