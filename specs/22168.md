# Разделение динамических характеристик и массы в карточке автомобиля

## Контекст

- Bitrix: https://carcraftpro.bitrix24.ru/company/personal/user/738/tasks/task/view/22168/
- Экран: публичная детальная карточка автомобиля `/cars/{vehicle_id}`.
- Сейчас `frontend/pages/cars/[id].vue` выводит одну карточку «Динамические характеристики». В неё одновременно попадают скорость/разгон и массовые параметры.
- На карточках грузовой техники, где заполнены только массовые параметры, заголовок «Динамические характеристики» не соответствует содержанию.
- В актуальном контракте детализации уже доступны значения `weight`, `full_weight`, `permitted_gross_train_weight` и `permitted_axle_loads`. API, импорт XLSX и БД для этой задачи менять не требуется.

## Цель и бизнес-результат

Показать массовые характеристики в самостоятельной карточке «Масса», а скорость и разгон — только в карточке «Динамические характеристики».

Пользователь должен видеть семантически точные разделы без потери существующих значений, единиц измерения и без изменения других характеристик автомобиля.

## Утверждённое решение

Ввести две независимые проверки видимости разделов в `useCarSpecs` и два независимых блока в детальной странице.

### Карточка «Динамические характеристики»

Показывается только если заполнено хотя бы одно поле:

- `max_speed` — «Макс. скорость»;
- `time_to_100` — «Разгон 0-100».

В этой карточке не отображаются никакие поля массы.

### Карточка «Масса»

Показывается только если заполнено хотя бы одно поле:

- `weight` — «Снаряженная масса»;
- `full_weight` — «Допустимая полная масса»;
- `permitted_gross_train_weight` — «Допустимая полная масса (тягача / автопоезда)»;
- `permitted_axle_loads` — «Допустимая нагрузка на оси (передняя / задняя)».

`permitted_axle_loads` переносится из карточки «Подвеска и тормоза» в карточку «Масса»: оно описывает допустимую нагрузку, выраженную в массовых единицах, и не должно дублироваться.

Карточка «Подвеска и тормоза» после переноса остаётся видимой только по своим оставшимся полям: `suspension`, `front_suspension`, `back_suspension`, `front_brake`, `back_brake`, `wheel_size`.

Для карточки «Масса» используется самостоятельная нейтральная иконка массы/весов. Не добавлять библиотеку иконок и не менять общую сетку, классы карточек, порядок остальных разделов или API-вызовы.

## Границы

Входит в задачу:

- изменение состава и заголовков двух карточек детальной страницы;
- перенос `permitted_axle_loads` в смысловой раздел «Масса»;
- точечное расширение существующего frontend architecture-теста;
- локальная desktop-проверка в браузере.

Не входит в задачу:

- изменение backend API, Pydantic-схем, ORM-моделей, миграций и таблиц БД;
- изменение Excel-шаблонов и логики импорта;
- переименование или изменение других характеристик;
- изменение списка товаров `/cars`, карточек каталога, корзины, фильтров и мобильного интерфейса.

## Планируемые изменения

### 1. Зафиксировать регрессионный контракт разделов

**Файл:** `frontend/tests/architecture/car-detail-extended-specifications-22170.test.ts`.

Сначала расширить существующий тест детальных характеристик следующими проверками исходного кода:

- `useCarSpecs` экспортирует отдельные `hasDynamicSpecs` и `hasMassSpecs`;
- `hasDynamicSpecs` учитывает только `max_speed` и `time_to_100`;
- `hasMassSpecs` учитывает ровно `weight`, `full_weight`, `permitted_gross_train_weight`, `permitted_axle_loads`;
- шаблон содержит самостоятельную карточку с заголовком «Масса» и условием `hasMassSpecs`;
- строки всех четырёх массовых полей находятся в карточке «Масса» по одному разу;
- `permitted_axle_loads` отсутствует в разметке карточки «Подвеска и тормоза»;
- прежние поля скорости и разгона остаются в карточке «Динамические характеристики»;
- сохранены существующие утверждённые названия полей и правила вывода единиц: составные значения не получают дополнительный суффикс единицы, а `full_weight` продолжает использовать `formatSpecWithUnit(..., 'кг')`.

Запустить точечный тест и убедиться, что до изменения он падает по отсутствующему `hasMassSpecs`/карточке «Масса».

### 2. Разделить условия видимости характеристик

**Файл:** `frontend/features/cars/composables/useCarSpecs.ts`.

- Сузить `hasDynamicSpecs` до двух динамических полей: `max_speed` и `time_to_100`.
- Добавить `hasMassSpecs` с четырьмя массовыми полями из утверждённого решения.
- Удалить `permitted_axle_loads` из `hasSuspensionSpecs`, чтобы карточка подвески не появлялась только из-за этого массового параметра.
- Вернуть `hasMassSpecs` из composable рядом с другими проверками видимости.
- Использовать существующие `hasAnyCarSpecValue` и `hasCarSpecValue`; пустая строка, строка из пробелов, `null` и отсутствующее значение не показывают карточку, значение `0` считается заполненным по текущему контракту.

После изменения запустить точечный тест: проверки нового контракта должны стать зелёными.

### 3. Разделить разметку карточек без дублирования значений

**Файл:** `frontend/pages/cars/[id].vue`.

- Оставить «Динамические характеристики» отдельной карточкой с текущими строками `max_speed` и `time_to_100` и условием `hasDynamicSpecs`.
- Добавить непосредственно после неё карточку «Масса» с условием `hasMassSpecs`, самостоятельной иконкой весов и прежней общей разметкой `card`/сеткой характеристик.
- Переместить в «Массу» строки `weight`, `full_weight`, `permitted_gross_train_weight`, `permitted_axle_loads` без изменения одобренных русских подписей и форматирования значений.
- Удалить строку `permitted_axle_loads` из карточки «Подвеска и тормоза».
- Не изменять `CarDetail`: все четыре нужных поля уже типизированы и приходят из текущего ответа деталей.

После изменения повторно запустить тест из шага 1. Он должен пройти.

### 4. Выполнить регрессионную проверку frontend

**Файлы:** изменённая страница, composable и architecture-тест.

- Запустить `bunx vitest run tests/architecture/car-detail-extended-specifications-22170.test.ts`.
- Запустить `bun run test:arch`.
- Запустить доступные frontend-проверки TypeScript/линтера, определённые в `frontend/package.json`, без установки новых зависимостей.
- Собрать и запустить frontend в Docker по проектной инструкции, просмотреть логи frontend и backend на отсутствие новых ошибок.
- Открыть детальную страницу на desktop-viewport не менее 768 CSS-пикселей с контролируемыми данными и проверить четыре сценария:
  - только скорость или разгон — видна только «Динамические характеристики»;
  - только любое массовое поле — видна только «Масса»;
  - есть динамика и масса — показаны две карточки, каждое поле только в своей карточке;
  - есть только `permitted_axle_loads` — видна «Масса», а «Подвеска и тормоза» не появляется, если других подвесочных полей нет.

## Критерии готовности

- На карточке с двумя значениями допустимой полной массы, как на предоставленном скриншоте, заголовок блока — «Масса», а «Динамические характеристики» не показаны при отсутствии скорости и разгона.
- Массовые поля отображаются только в «Массе» и не дублируются в «Динамических характеристиках» или «Подвеске и тормозах».
- Максимальная скорость и разгон отображаются только в «Динамических характеристиках».
- При одновременном наличии динамических и массовых значений пользователь видит две отдельные карточки с корректными заголовками.
- Отсутствующие, `null` и состоящие из пробелов значения не создают пустых карточек; значение `0` продолжает отображаться.
- Составные массовые значения не получают повторный суффикс единицы; числовое `full_weight` получает `кг` один раз.
- Карточка «Подвеска и тормоза» сохраняет свои оставшиеся характеристики и не показывается только из-за `permitted_axle_loads`.
- API, БД, импорт файлов, каталог `/cars` и другие разделы пользовательского интерфейса не изменены.
- Пройдут точечный тест, полный `bun run test:arch`, доступные frontend-проверки, Docker-сборка/запуск и просмотр логов.

## Риски и решения

- Риск: массовое поле останется в двух карточках. Решение: единый список массовых полей в `hasMassSpecs`, перенос единственной строки `permitted_axle_loads` и тест на единственное присутствие подписей.
- Риск: карточка «Подвеска и тормоза» станет пустой. Решение: удалить `permitted_axle_loads` из её условия видимости и проверить сценарий с единственным массовым параметром.
- Риск: у существующей записи одновременно есть скорость, разгон и масса. Решение: показывать две карточки; данные не скрываются и не смешиваются.
- Риск: изменение единиц исказит импортированное составное значение. Решение: сохранить существующие `formatSpecWithUnit` и прямой вывод составных значений.

## Дополнение: утверждённый вариант 2

### Текущее поведение

После первоначального разделения «Динамических характеристик» и «Массы» карточки «Масса», «Топливная система» и «Подвеска и тормоза» используют неоднородную сетку. В «Топливной системе» остаётся `lg:grid-cols-4`, а отдельная короткая строка может занимать только одну из двух desktop-колонок. Длинные составные значения не во всех семантически широких строках имеют гарантированную возможность переноса.

### Целевое поведение

- Поддерживается только desktop web от 768 CSS-пикселей; в трёх указанных карточках — не более двух колонок (`md:grid-cols-2`). Поведение для viewport меньше 768 пикселей не добавляется.
- Семантически широкие поля всегда занимают обе desktop-колонки: `permitted_gross_train_weight`, `permitted_axle_loads`, `fuel_tanks`, `suspension`, `front_suspension`, `back_suspension`.
- Широкие строки и их значения используют `min-w-0` и перенос текста внутри value (`break-words`), без `truncate` и абсолютного позиционирования.
- Короткими остаются `weight`, `full_weight`, тип топлива, объём бака, экокласс, расход, выбросы, запас хода, `front_brake`, `back_brake` и `wheel_size`.
- `full_weight` занимает обе колонки, когда `weight` отсутствует; когда `weight` есть, оба поля остаются короткой парой. `wheel_size` занимает обе колонки, когда после полного числа коротких пар тормозов остаётся без пары (в том числе без тормозов); при ровно одном из `front_brake` и `back_brake` она завершает короткую пару.
- Русские подписи, видимость карточек, порядок полей и правила единиц сохраняются: `full_weight` продолжает выводиться через `formatSpecWithUnit(..., 'кг')`, а составные значения не получают добавленной единицы.

### Границы дополнения

Входят только статическая Vue-разметка `frontend/pages/cars/[id].vue`, точечный architecture-тест и эта единственная спецификация. Общий helper в `useCarSpecs` не добавляется: классы и ветвления определяются семантическими ключами в шаблоне. Не входят API, backend, импорт, данные, мобильный интерфейс, Docker, коммиты и push.

### Критерии готовности дополнения

- В «Топливной системе» нет `lg:grid-cols-4`; её desktop-сетка и сетки «Массы»/«Подвески и тормозов» имеют максимум две колонки.
- Все шесть широких полей имеют `md:col-span-2`, `min-w-0` и перенос значения.
- Архитектурный тест фиксирует шесть широких строк, двухколоночную топливную сетку и обе ветки полного размера для `full_weight` и `wheel_size`, сохраняя предыдущие проверки разделения характеристик, подписей и единиц.
- Выполняется `bunx vitest run tests/architecture/car-detail-extended-specifications-22170.test.ts`.
