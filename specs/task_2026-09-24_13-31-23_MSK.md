# Задача #21822 — управление компаниями клиента из административного ЛК

- Bitrix: https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/21822/
- Ветка: `feature/21822`
- Статус: спецификация для согласования

## Постановка

Администратор в ЛК открывает раздел «Пользователи» и редактирует пользователя с ролью «Клиент». В текущем модальном окне редактирования нет блока компаний. При создании клиента администратор может найти компанию по названию или ИНН и привязать её, а сам клиент в профиле может добавлять компании через отдельный сценарий.

Для клиента компания не является заменяемым одиночным полем: у пользователя может быть несколько привязанных компаний. Удаление и изменение существующей привязки не допускаются, в том числе из профиля клиента. Администратору требуется видеть все уже привязанные компании клиента и добавлять новые, не меняя и не удаляя старые.

## Текущее поведение

- В `frontend/features/auth/components/UserFormModal.vue` блок поиска компании показывается при создании клиента, но намеренно скрыт при его редактировании.
- Форма редактирования передаёт в `PATCH /api/v1/users/{id}` только базовые поля пользователя. Передача `company_id` в этом API меняет одиночное поле `users.company_id`, поэтому использовать её для клиентского сценария нельзя.
- Список клиентских компаний строится из `user_companies` и основного `users.company_id` через `GET /api/v1/users/me/companies`.
- Добавление компании сейчас доступно только самому текущему пользователю через `POST /api/v1/users/me/companies`.

## Целевое поведение

Для роли `client` в модальном окне «Редактировать пользователя» после поля «Роль» и перед чекбоксом «Активный пользователь» отображается блок «Компании».

- Все текущие компании пользователя выводятся отдельными disabled-полями с названием и ИНН, если ИНН есть.
- В блоке доступна кнопка «+ Добавить ещё компанию».
- По кнопке открывается поиск компании, визуально и по контракту использующий существующий `CompanyAutocomplete`: поиск по названию или ИНН, выбор только из найденной карточки компании.
- После подтверждения выбранная компания добавляется как новая связь с клиентом, список обновляется без закрытия формы редактирования.
- Добавление компании не изменяет основную компанию, если у клиента она уже есть. Если основной компании ещё нет, используется существующее правило установки первой добавленной компании основной.
- Существующие компании нельзя редактировать, заменять или удалять. Кнопок удаления и запросов удаления не будет.
- Дубликат уже привязанной компании не создаёт вторую связь; пользователь получает понятную ошибку.
- Для ролей `dealer`, `leasing_company` и `distributor` текущая форма и смена их одиночной компании не меняются.

## Бизнес-цель

Дать администратору возможность безопасно поддерживать несколько юридических лиц одного клиента в административном ЛК, сохраняя историю и все существующие связи клиента с компаниями.

## Выбранный подход

Добавить отдельный административный API для чтения и добавления компаний конкретному пользователю-клиенту:

- `GET /api/v1/users/{user_id}/companies` — возвращает компании целевого пользователя;
- `POST /api/v1/users/{user_id}/companies` — добавляет компанию по уже существующему контракту `{ company: {...} }`.

Оба метода доступны только обладателю scope `users:admin`. `POST` дополнительно проверяет существование пользователя и его роль `client`; для другой роли возвращает понятную клиентскую ошибку без изменений данных. Команда переиспользует существующую логику создания/поиска компании, защиты от дубликатов, записи `user_companies`, установки первой основной компании и фонового обогащения.

Связь, добавленная администратором, получает те же права администратора компании, что и первая компания клиента, созданная администратором. Это сохраняет действующую бизнес-модель: клиент вправе работать от имени добавленного юридического лица.

В UI расширить `UserFormModal.vue` только для редактируемого клиента: получить его список компаний, показать disabled-поля и предоставить компактную форму добавления с `CompanyAutocomplete`. Для иных ролей не менять текущий селект компании.

## Рассмотренные варианты

1. Использовать `PATCH /api/v1/users/{id}` с `company_id`.
   - Не выбран: этот запрос заменяет одиночную основную компанию и не создаёт безопасную дополнительную связь в `user_companies`.

2. Вызвать из админского интерфейса `/api/v1/users/me/companies`.
   - Не выбран: маршрут намеренно привязывает компанию только к текущему авторизованному пользователю, а не к редактируемому клиенту.

3. Отдельные административные GET/POST-маршруты с повторным использованием существующей команды добавления.
   - Выбран: соответствует границе прав администратора, не меняет схему БД и исключает замену либо удаление существующих компаний.

## Планируемые изменения

### Backend

- `backend/presentation/routers/users.py`
  - зарегистрировать конкретные маршруты `/{user_id}/companies` до широких маршрутов пользователя;
  - потребовать `users:admin`;
  - реализовать чтение списка и добавление компании с commit только в роутере;
  - вернуть стандартизированные `UserCompaniesResponse` и `AddCompanyResponse`.
- `backend/application/commands/user_companies.py`
  - добавить командный сценарий административного добавления: проверить целевого пользователя и роль `client`, затем вызвать существующий `handle_add_company_to_user` с правами администратора.
- `backend/infrastructure/repositories/admin_users_repository.py`
  - при необходимости добавить узкий метод чтения целевого пользователя, достаточный для проверки роли; не дублировать запись компании.
- `backend/presentation/schemas/users.py`
  - переиспользовать существующие схемы тела и ответа, добавить новую схему только если текущая не описывает административный список.
- `backend/tests/integration/test_admin_users_router.py`
  - добавить проверки прав, чтения, добавления, дубликата и запрета работы с не-клиентом.

### Frontend

- `frontend/features/auth/components/UserFormModal.vue`
  - показывать клиентский блок «Компании» только при редактировании роли `client`;
  - получать и отображать все привязки выбранного пользователя в disabled-полях;
  - открыть и закрыть форму добавления, передать объект из `CompanyAutocomplete` в новый административный маршрут;
  - обновить список после успешного добавления и показать ошибку без потери формы;
  - оставить существующий сценарий создания клиента и форму всех остальных ролей без регрессий.
- `frontend/tests/e2e/` либо существующий целевой E2E-сценарий админ-пользователей
  - добавить или обновить сквозной сценарий согласно фактическому test-набору репозитория.

## Критерии приёмки

1. Администратор с `users:admin` открывает редактирование пользователя с ролью «Клиент» и видит блок «Компании» после поля «Роль».
2. В блоке показаны все компании, связанные с клиентом через `users.company_id` и `user_companies`; поля недоступны для редактирования.
3. В модальном окне есть кнопка «+ Добавить ещё компанию», а поиск принимает название или ИНН и использует выбранный объект компании.
4. После успешного добавления новая компания отображается в том же списке; ранее отображённые компании остаются неизменными.
5. Добавление второй компании не меняет `users.company_id`, если основная компания уже существует.
6. Добавление уже привязанной компании возвращает понятную ошибку и не создаёт дубль.
7. Запросы административного списка и добавления без `users:admin` получают отказ в доступе; добавление компании пользователю не с ролью `client` отклоняется.
8. У администратора не появляется возможность редактировать, заменять или удалять существующую привязку клиента.
9. Поведение формы дилера, лизинговой компании и дистрибьютора не изменяется.
10. Сценарий проверен E2E на работающем приложении для администратора; дополнительно проверены отказ в доступе и ошибка дубликата. После реализации выполнены профильные линтеры, просмотрены логи сервисов и проверено, что Alembic autogenerate не предлагает изменений схемы.

## Риски и меры

- Риск: случайно использовать `PATCH` и заменить основную компанию. Мера: отдельный POST-маршрут и тест, подтверждающий неизменность `users.company_id`.
- Риск: дать административной форме доступ к компаниям не-клиентов. Мера: серверная проверка роли, не зависящая от скрытия UI.
- Риск: создать дубликат связи. Мера: повторное использование существующей проверки `user_companies` и интеграционный тест.
- Риск: отобразить неполный список для старых данных. Мера: использовать существующий запрос, объединяющий `users.company_id` и `user_companies`.

## Вопросы

Блокирующие вопросы отсутствуют.

Не блокирующее решение, зафиксированное в этой спецификации: новая привязка, добавленная администратором, даёт клиенту права администратора компании — так же, как при создании клиента администратором.

## Проверка спецификации

- Требования конкретны: замена, редактирование и удаление существующих связей явно исключены.
- Схема БД, ORM-модели и миграции не меняются.
- Все пользовательские и серверные результаты имеют проверяемые критерии.
