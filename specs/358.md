# Bitrix #21700 — восстановление отображения цели и регионов в карточках заявок

## Контекст

После внедрения единой витрины предметов заявки (`items`) цель приобретения и регионы перестали отображаться в карточках всех заявок. Проблема воспроизводится в общих списках заявок, где используется `ApplicationCard`:

- кабинет клиента;
- панель «Мои заявки»;
- другие экраны, использующие эту общую карточку.

Детальные данные автомобиля и сами значения в базе не удалены.

## Текущее поведение

1. API списка заявок формирует единый массив `items` для автомобилей и спецтехники.
2. Проекция автомобильной строки в `items` не включает `leasing_purpose` и `regions`. Для значения «Прочее» текст уже хранится в `leasing_purpose`; отдельного поля комментария у автомобильной строки нет.
3. `ApplicationCard` ищет цель и регионы только в устаревшем массиве `application.vehicles`.
4. Ответ списка заявок больше не заполняет `vehicles`; в результате условие отображения не выполняется и блок цели/регионов скрывается для всех карточек.

## Требуемое поведение

Для каждой карточки заявки, содержащей автомобиль с заполненной целью или регионами:

1. Показывается «Цель приобретения» с прежним человекочитаемым названием.
2. Показывается «Регион».
3. При нескольких регионах сохраняется прежний компактный раскрывающийся список: часть значений видна сразу, остальные открываются пользователем.
4. Если цель и регионы у автомобиля отсутствуют, соответствующий блок не отображается.
5. Карточки со спецтехникой не получают выдуманных значений и сохраняют текущий вид.

## Бизнес-цель

Цель приобретения и регионы нужны участникам лизингового процесса для оценки заявки. Их отсутствие во всех списках заявок лишает пользователей важного контекста и делает проверку заявок медленнее.

## Рекомендуемый вариант

Исправить контракт единой витрины и её отображение.

1. Backend: включить `leasing_purpose` и `regions` в унифицированную строку автомобиля `items`.
2. Frontend: расширить тип unified-item нужными необязательными полями.
3. Frontend: в `ApplicationCard` брать цель и регионы из автомобильного `item`, а не из отсутствующего в списковом ответе `vehicles`.
4. Повторно использовать существующие `formatLeasingPurpose` и `VehicleRegionsDisplay`; не создавать второй формат раскрывающегося списка.
5. Добавить регрессионные тесты API-проекции и карточки, включая несколько регионов.

### Почему это предпочтительно

- Устраняет причину, а не маскирует её проверками на `undefined`.
- Сохраняет единый контракт `items`, принятый для автомобилей и спецтехники.
- Не требует миграций и не изменяет пользовательские данные.
- Не влияет на детальный endpoint, где обратная совместимость `vehicles` уже сохранена.

## Риски и защита

- **Риск:** в unified-item поля могут прийти пустыми у исторических строк.
  **Защита:** отображать блок только при фактически заполненной цели или хотя бы одном регионе.
- **Риск:** может измениться представление спецтехники.
  **Защита:** выбирать только item с типом `vehicle`; поля спецтехники не показывать.
- **Риск:** список может показывать несколько автомобилей с разными значениями.
  **Защита:** сохранить ранее принятое правило карточки — отображать первый автомобиль с заполненной целью или регионом.

## Критерии приёмки

- [ ] `GET /api/v1/applications` возвращает для автомобильных `items` цель и массив регионов.
- [ ] В карточке заявки с целью и одним регионом видны оба значения.
- [ ] В карточке с несколькими регионами используется существующий раскрывающийся список регионов.
- [ ] В карточке без цели и регионов пустые подписи не отображаются.
- [ ] В карточке со спецтехникой без автомобильной строки цель и регионы не появляются.
- [ ] Существующие детальные представления заявок не регрессируют.
- [ ] Пройдут целевые тесты, frontend architecture tests, frontend build, проверка diff и независимый review.

## Вопросы

Блокирующих вопросов нет.

Неблокирующее уточнение: исправление относится к общим карточкам в списках заявок. Детальный экран уже получает legacy-массив `vehicles` с целью и регионами; отдельно менять его не планируется без подтверждённого дефекта.

3. Передать цель и регионы из `ApplicationVehicle` в unified-item автомобиля.
4. Перевести `ApplicationCard` на данные `items` с использованием имеющегося `VehicleRegionsDisplay`.
5. Выполнить целевые и общие проверки, независимый review и merge-проверку с `origin/test`.
