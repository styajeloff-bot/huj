# Slug как виртуальный корень публичной витрины

## Контекст

- Это внутренняя follow-up задача к складским витринам из MR !325.
- Реализация задачи оформлена в MR !329.
- Пользователь сообщил, что после перехода из `/faw` карточка автомобиля и
  личный кабинет могут возвращать его на корневой сайт вместо текущей витрины.
- Пользователь уточнил, что slug должен работать как корень сайта, а не как
  набор точечных исправлений отдельных ссылок.
- Речь идёт о динамическом логическом корне публичной витрины. Глобальный Nuxt
  `app.baseURL` не используется: он один для всей сборки и несовместим с
  одновременной работой `/`, `/faw` и других создаваемых администратором slug.

## Требования

1. После входа в активную витрину `/{slug}` её slug считается виртуальным
   корнем всех принадлежащих витрине публичных маршрутов.
2. Любой клиентский переход из `/faw/*` на root-вариант storefront-owned
   маршрута автоматически нормализуется в `/faw/*` до загрузки страницы и её
   данных. Это распространяется на главную, каталог, карточку автомобиля,
   модельный ряд, корзину, авторизацию, кабинет, заявки, заказы и уведомления.
3. Правило применяется централизованно на уровне storefront routing seam, а не
   исправлением отдельных `NuxtLink`, `router.push()` или `navigateTo()`.
4. Прямой запрос или перезагрузка root URL без storefront-контекста продолжает
   открывать основной сайт. Правило не определяется HTTP `Referer`.
5. Переход на другой активный `/{slug}` разрешён и переключает витрину.
6. `/workspace`, `/admin`, юридические страницы и специальная техника являются
   явными глобальными маршрутами и не получают storefront-префикс.
7. Нормализация маршрута сохраняет query string и hash и не создаёт redirect
   loop на SSR, client navigation, browser Back/Forward или канонизации slug.

## Планируемые изменения

- Зафиксировать единым manifest перечень storefront-owned публичных маршрутов.
- Добавить в глобальный storefront middleware раннюю нормализацию перехода из
  scoped-контекста на root-вариант маршрута через существующий route builder.
- Оставить `publicRoute()` публичным способом строить корректные ссылки, но
  сделать middleware системной защитой от любой пропущенной абсолютной ссылки.
- Добавить чистые unit/regression-тесты для определения storefront-owned
  маршрутов и переноса root target под slug, а также architecture-контракт на
  подключение защиты в global middleware.
- Проверить сценарии `/faw/cars/{id}` и `/faw/cabinet` в desktop-браузере.

## Критерии готовности

1. Из любого `/faw/*` переходы на `/`, `/cars`, `/cars/{id}`, `/models`,
   `/cart`, `/auth`, `/cabinet`, `/application/{id}`, `/orders/{type}/{id}` и
   `/notifications` остаются внутри `/faw/*`.
2. В частности, карточка автомобиля возвращает в `/faw/cars`, а кабинет и его
   вложенные клиентские сценарии не выводят пользователя на основной сайт.
3. На root-сайте те же маршруты остаются root-маршрутами; глобальные разделы не
   захватываются витриной.
4. Query/hash сохраняются; неизвестная или выключенная витрина по-прежнему
   возвращает `404`, а out-of-scope автомобиль — scoped `404`.
5. Regression-тест сначала воспроизводит дефект, затем проходит после
   централизованного исправления; полный `bun run test:arch`, TypeScript-проверка,
   production build и browser-smoke не выявляют новых ошибок или предупреждений.
6. MR направлен только в `test`, спецификация после создания MR переименована в
   `specs/<номер-MR>.md`, auto-merge включён после успешных проверок.

## Границы задачи

- Не менять backend scope, схему БД и миграции: scoped API уже определяется
  storefront route context и остаётся fail-closed.
- Не менять правила видимости разделов и branding витрин.
- Не создавать отдельные копии страниц под каждый slug.
- Не менять глобальный Nuxt `app.baseURL` и не создавать отдельную frontend
  сборку на каждый slug.
- Не добавлять мобильную навигацию для viewport меньше 768 CSS-пикселей.
