# Bitrix №22226 — нормализация срока договора в калькуляторе корзины

- Bitrix: https://carcraftpro.bitrix24.ru/company/personal/user/738/tasks/task/view/22226/
- Ветка: `bugfix/22226`, создана от актуального `origin/test` (`a4556fc9`).
- Статус: `implemented`; реализация и локальные проверки завершены, ветка подготовлена к MR в `test`.

## Цель и бизнес-причина

Не допускать, чтобы пользователь вручную оставлял в параметрах расчёта корзины срок договора за пределами доступного диапазона. Это устраняет расхождение между подписями слайдера «1 год» / «7 лет», введённым числом и расчётом, а также делает поведение поля таким же предсказуемым, как у ограничиваемых финансовых параметров.

## Подтверждённое текущее поведение

- В `frontend/features/cart/calculator/CartLeasingCalculator.vue` у поля срока есть HTML-атрибуты `min="12"`, `max="84"` и `step="6"`, а слайдер ограничен 12–84.
- HTML-атрибуты не заменяют уже введённое вручную число: пользователь может оставить в поле `11` или `85`.
- Локальная проверка расчёта не выполняет запрос для значений вне 12–84 и очищает результат.
- API калькулятора уже защищён: `backend/presentation/schemas/calculator.py` принимает `lease_term_months` только как целое число в диапазоне 12–84 и отклоняет выходящее за границы значение.
- Серверную валидацию менять не требуется: она остаётся границей защиты для прямых и некорректных API-запросов.

## Целевое поведение

После завершения ручного ввода срока в поле «Срок договора»:

- значение меньше `12` автоматически заменяется на `12`;
- значение больше `84` автоматически заменяется на `84`;
- целое значение от `12` до `84` остаётся без изменений;
- после замены запускается штатный debounced-пересчёт, и результат, данные checkout и сохранённое состояние используют уже нормализованный срок;
- слайдер продолжает работать с существующим шагом 6 месяцев и не может выйти за границы.

Нажатие Enter в поле также должно сначала применить нормализацию, а затем инициировать расчёт; пользователь не должен видеть очистку результата из-за промежуточно введённого `11` или `85`.

## Границы задачи

В scope:

- нормализация границ только в калькуляторе корзины;
- защита от отправки дробного срока: срок договора — целое число месяцев, что соответствует существующему backend-контракту;
- автоматические frontend-тесты граничных значений.

Вне scope:

- изменение диапазона 12–84;
- округление допустимого целого срока к шагу слайдера 6 месяцев: например, 13, 25 и 83 месяца не изменяются, поскольку такого бизнес-правила нет;
- изменение API, БД, заявок, коммерческих предложений, уже созданных расчётов или специальных условий лизинговых компаний;
- молчаливая коррекция некорректного прямого API-запроса на сервере.

Для пустого или дробного ручного значения фронтенд не подменяет число бизнесовым значением: такой ввод остаётся нерассчитываемым до исправления пользователем. Это исключает скрытое изменение финансового параметра без явно согласованного правила округления.

## Варианты и решение

### Вариант A — только `min` / `max` у HTML-поля

Не подходит: атрибуты уже существуют, но не нормализуют вручную введённое значение.

### Вариант B — нормализовать на каждый символ ввода

Не подходит: при попытке набрать `12` первая цифра `1` сразу превратится в `12`; поле станет неудобным и непредсказуемым.

### Вариант C — нормализация при фиксации ручного ввода, сервер остаётся строгим

Выбранный вариант.

Обработчик поля срабатывает при `change`/потере фокуса и при Enter. Он ограничивает только числовые значения за пределами 12–84, обновляет `leaseTerm`, после чего используется существующий debounced-пересчёт. Отдельная проверка целочисленности не позволяет отправить дробный срок. Backend остаётся источником истины для API-контракта и продолжает возвращать ошибку для обхода интерфейса.

## План реализации

1. Создать чистую frontend-функцию нормализации срока в `frontend/features/cart/calculator/`:
   - константы минимума `12` и максимума `84`;
   - нормализация только нижней и верхней границы;
   - отдельная проверка, что значение является целым числом месяцев.
2. В `frontend/features/cart/calculator/CartLeasingCalculator.vue` подключить функцию к ручному полю срока:
   - выполнить нормализацию при завершении редактирования и при Enter;
   - не выполнять подстановку на каждом `input`;
   - гарантировать, что расчёт вызывается с нормализованным значением;
   - дополнить `canCalculate` проверкой целого числа, согласованной с API.
3. Добавить тесты в `frontend/tests/architecture/`:
   - `11 → 12`;
   - `85 → 84`;
   - `12`, `36`, `84` не меняются;
   - дробное значение не признаётся допустимым параметром расчёта;
   - компонент использует обработчик нормализации для ручного поля и не ослабляет существующий серверный контракт.
4. Выполнить адресный Vitest, полный `bun run test:arch`, TypeScript-проверку и production build фронтенда. Затем воспроизвести в браузере на desktop: `11`, `85`, 12, 84, изменение слайдером и Enter.

## Критерии готовности

- Ввод `11` и завершение редактирования отображает `12`; API расчёта получает `12`.
- Ввод `85` и завершение редактирования отображает `84`; API расчёта получает `84`.
- Ввод `12`, `36` и `84` не меняет значение.
- Enter после `11` или `85` не отправляет исходное некорректное значение и не оставляет устаревший результат расчёта.
- Слайдер сохраняет текущие пределы 12–84 и шаг 6 месяцев.
- Дробный срок не отправляется в API.
- Существующая серверная схема сохраняет диапазон `ge=12`, `le=84`.
- Пройдены адресные и обязательные frontend-проверки; непрошедшие или недоступные проверки отдельно зафиксированы до MR.

## Риски и меры

- Риск: повторный запуск расчёта из нескольких событий поля. Мера: использовать существующий debounce и не вызывать сетевой расчёт непосредственно из нескольких обработчиков.
- Риск: округление срока изменит финансовый результат без согласованного правила. Мера: не округлять допустимые целые значения и не подменять дробные значения.
- Риск: обход UI через API. Мера: не ослаблять существующую Pydantic-валидацию backend.

## Неблокирующие вопросы

Нет. Правило применяется к диапазону, указанному в задаче: 12–84 месяца.
