# Подключение EQID к обязательной Mobile ID-верификации

## Контекст

- Bitrix: https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/21502/
- В проекте уже реализован пользовательский сценарий Mobile ID: запуск из профиля, ввод SMS-кода, хранение серверного статуса, отображение статуса «Верифицирован» и запрет подписания СОПД без успешной проверки.
- Текущий production-провайдер напрямую интегрирован с Mobile ID МТС и использует OIDC/JWS/JWE и callback endpoints.
- Для проекта подготовлен шлюз EQID с двухшаговым API `premiuminfo_match`: создание запроса и подтверждение SMS-кодом. EQID самостоятельно взаимодействует с Mobile ID и возвращает только признаки совпадения персональных данных.
- Токен EQID является секретом окружения: он не должен попадать в исходный код, спецификацию, логи, ответы API или историю Git.

## Цель и бизнес-результат

Использовать EQID как серверного провайдера существующего сценария «Верификация через Mobile ID», не меняя привычный интерфейс пользователя и обязательную проверку перед подписанием СОПД.

После ввода корректного SMS-кода пользователь считается верифицированным только тогда, когда EQID завершил запрос и вернул успешное совпадение переданных персональных данных. Ошибка, истечение запроса или несовпадение данных не должны создавать статус верификации.

## Решение

- Добавить отдельный инфраструктурный адаптер EQID, реализующий действующий доменный контракт провайдера верификации.
- При запуске проверки backend отправляет в EQID `operation=premiuminfo_match`, телефон, дату рождения, фамилию, имя и отчество пользователя.
- Полученный `request_id` сохраняется в существующей попытке верификации как внешний идентификатор процесса.
- При подтверждении backend отправляет SMS-код в `POST /api/v1/gateway/requests/{request_id}/code` с тем же Bearer-токеном.
- Попытка помечается успешной только при `status=completed` и `result.matched=true`. Флаги `N` и `N-AV`, отсутствие результата либо противоречивый ответ рассматриваются как неуспешная проверка.
- Публичный frontend-контракт и текущие маршруты `/api/v1/users/me/identity-verification*` сохраняются, поэтому профиль, модальное окно и блокировка подписания СОПД продолжают работать без отдельной EQID-разметки.
- Прямой адаптер МТС и его callback endpoints не удаляются. Выбор реального провайдера выполняется настройкой backend, чтобы сохранить возможность возврата к прямой интеграции и не ломать уже существующие контракты.
- Локальный fake-провайдер и код `0000` сохраняются для изолированной разработки, когда внешняя интеграция отключена.

## Планируемые изменения

### Backend: настройки и выбор провайдера

- `backend/infrastructure/settings.py`
  - добавить настройки выбора провайдера, базового URL EQID, Bearer-токена и таймаута;
  - валидировать обязательные настройки при выборе EQID;
  - не читать секреты напрямую через `os.environ`.

- `backend/infrastructure/services/mobile_id/`
  - добавить EQID-адаптер рядом с существующим провайдером либо в выделенном модуле пакета;
  - переключить фабрику провайдера на явный режим `local`, `mts` или `eqid`;
  - не передавать и не логировать Bearer-токен, полный SMS-код и лишние персональные данные;
  - сопоставить сетевые ошибки, `401`, `404`, истёкший запрос, неверный код, несовпадение данных и некорректный ответ с существующими доменными ошибками.

### Backend: прикладной сценарий и хранение

- `backend/application/commands/identity_verification.py`
  - переиспользовать текущую оркестрацию запуска и подтверждения попытки;
  - при необходимости расширить результат провайдера так, чтобы успешность EQID определялась сервером по `matched`, а не frontend-состоянием;
  - сохранять внешний `request_id` и финальный статус в существующей модели без хранения токена или SMS-кода;
  - исключить перевод попытки в `verified` при неполном или отрицательном результате.

- `backend/domain/services/identity_verification.py`
  - изменить общий контракт провайдера только в минимально необходимом объёме, без зависимости доменного слоя от формата EQID.

- Миграция БД не планируется: существующие поля попытки должны быть переиспользованы. Если реализация докажет невозможность корректного аудита без нового поля, изменение модели и миграция сначала вносятся в эту спецификацию и повторно согласовываются.

### Frontend и API

- Сохранить существующие API-маршруты запуска и ввода SMS-кода и существующее модальное окно Mobile ID.
- Добавить точечные изменения UX-текстов только если это потребуется для понятного отображения отдельных ошибок EQID.
- Не раскрывать пользователю внутреннее имя шлюза, токен или технические ответы провайдера.
- Удалить из профиля серую кнопку «Получить данные через PremiumInfo (тест)» и весь отдельный экспериментальный сценарий, который она запускала: модальное окно, frontend API/composable/types, тестовые backend endpoints, Redis-кеш результатов и специальную обработку callback PremiumInfo.
- Не удалять `premiuminfo_match` из EQID-адаптера: это внутреннее название основной production-операции EQID и оно не связано с удаляемым тестовым интерфейсом.

### Конфигурация и локальный запуск

- Добавить безопасный пример переменных EQID без реального токена в шаблон окружения/compose-конфигурацию, если такие файлы уже используются проектом.
- Реальный токен задаётся только в локальном или серверном окружении и не коммитится.
- Проверить интеграцию на локальной Docker-копии с реальным EQID отдельно от автоматических тестов; тестовые персональные данные и SMS-коды не фиксировать в Git и логах.

### Тесты

- Unit-тесты EQID-адаптера с `MockTransport`/мокированным HTTP:
  - корректный запрос `premiuminfo_match` и Bearer-аутентификация;
  - сохранение `request_id` после ответа `201`;
  - успешное подтверждение при `completed` и `matched=true`;
  - отказ при `matched=false`, `N`, `N-AV`, неполном и некорректном ответе;
  - обработка неверного/истёкшего кода, `401`, `404`, таймаута и недоступности EQID;
  - отсутствие секрета и SMS-кода в логах и пользовательских ошибках.
- Прикладные/API-тесты:
  - пользователь не становится верифицированным до успешного ответа EQID;
  - отрицательный результат не снимает запрет подписания СОПД;
  - успешный результат создаёт серверный статус и разрешает подписание;
  - существующий локальный и прямой MTS-режимы не ломаются.
- Существующие frontend architecture-тесты и сценарий блокировки подписания должны остаться зелёными; при изменении UX-текстов добавить соответствующую проверку.

## Критерии готовности

- В режиме EQID запуск существующего процесса создаёт `premiuminfo_match` и возвращает пользователю шаг ввода SMS-кода.
- SMS-код подтверждается через EQID с тем же токеном продукта и с внешним `request_id` текущей попытки.
- Только `status=completed` вместе с `result.matched=true` создаёт серверный статус «Верифицирован».
- Несовпадение, неполный результат, неверный код, истёкший запрос и сбой EQID не разрешают подписать СОПД и показываются понятным сообщением.
- Неверифицированному пользователю по-прежнему автоматически открывается процесс Mobile ID при попытке подписания СОПД.
- После успешной проверки пользователь видит «Верифицирован» и может вернуться к подписанию.
- Токен EQID и SMS-коды отсутствуют в репозитории, логах и публичных ответах API.
- Прямой MTS-адаптер, callback endpoints и локальный fake-провайдер остаются работоспособными.
- В профиле отсутствует кнопка тестового PremiumInfo, а маршруты `/api/v1/users/me/mobile-id/premiuminfo-attempts*` больше не зарегистрированы; основной Mobile ID/EQID-сценарий продолжает работать.
- Пройдут Ruff, import-linter, mypy, backend pytest, профильные frontend-проверки, Docker-сборка/запуск и просмотр логов.
- До отдельного явного разрешения пользователя изменения остаются локальными: не выполняются `git push`, создание MR и merge.

## Границы и риски

- В задачу не входит изменение общей модели подписания документов, ролей, JWT-аутентификации или дизайна личного кабинета.
- В задачу не входит удаление прямой интеграции МТС и её callback endpoints.
- Реальная E2E-проверка зависит от действующего EQID-токена, тестового номера и полученного SMS-кода; автоматические тесты не должны обращаться к внешнему сервису.
- Перед началом реализации требуется подтвердить эту спецификацию и отдельно подтвердить, что для положительного результата достаточно агрегированного `result.matched=true`, а отдельные `N-AV` не допускаются как успешная верификация.
