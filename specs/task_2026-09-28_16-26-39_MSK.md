## 1. Постановка задачи

### Текущее поведение
В публичном каталоге спецтехники (`SpecialEquipmentFilters.vue`) фильтры марки, модели и модификации уже выстроены в цепочку:

| Фильтр | Когда доступен | Какие варианты показывает |
|---|---|---|
| Марка | всегда | все марки из фасетов |
| Модель | после выбора марки (`disabled`, «Сначала выберите марку») | модели выбранных марок (`availableModels`) |
| Модификация | после выбора модели (`disabled`, «Сначала выберите модель») | модификации выбранных моделей (`availableModifications`) |
| **Комплектация** | **всегда** | **все комплектации из фасетов (`facets.trims`)** — в т. ч. чужих модификаций |

Дополнительно найдено:
- при удалении чипа марки / модели / модификации в `SpecialEquipmentCatalogPanel.vue` (`removeActiveFilter`) выбранные комплектации **не очищаются** — остаются «осиротевшие» `trim_id`;
- ссылка с `?trim_id=…` без `modification_id` применяет фильтр по комплектации без выбранной модификации.

Админская форма объявления (`CatalogCorrectionForm.vue`) уже показывает «Комплектацию» только после выбора модификации — **в эту задачу не входит**.

### Требуемое поведение
1. **Пока не выбрана ни одна модификация** фильтр «Комплектация» показывается неактивным с подсказкой **«Сначала выберите модификацию»** — так же, как «Модель» и «Модификация».
2. **После выбора модификаций** в списке — только комплектации выбранных модификаций (`trim.modification_id ∈ modificationIds`). Названия выводятся как есть, без уточнения модификации (решение заказчика): одинаковые названия разных модификаций идут отдельными строками.
3. **Выбранные комплектации всегда принадлежат выбранным модификациям.** При любом изменении модификаций (диалог, чип модификации, каскад от чипа марки/модели, ссылка) комплектации, не относящиеся к оставшимся модификациям, снимаются.
4. **Старые ссылки** с `trim_id` без `modification_id` или с комплектацией чужой модификации: лишние `trim_id` отбрасываются на фронтенде (из фильтра, чипов и URL), выдача строится без них. API не меняется.

Фильтр отображается только если у каталога есть хотя бы одна комплектация (`facets.trims.length > 0`) — как сейчас.

## 2. Требования к реализации

### 2.1. `composables/catalogQuery.ts` — чистая функция очистки
```ts
/**
 * Keep only trims that belong to the selected modifications.
 * No modification selected -> no trims. A trim missing from facets (not loaded
 * yet or zero count under other filters) is kept: ownership cannot be proven.
 */
export const pruneTrimSelection = (
  query: SpecialEquipmentCatalogQuery,
  trimFacets: readonly SpecialEquipmentTrimFacet[],
): SpecialEquipmentCatalogQuery => {
  if (query.trimIds.length === 0) return query
  if (query.modificationIds.length === 0) return { ...query, trimIds: [] }
  const selected = new Set(query.modificationIds)
  const owner = new Map(trimFacets.map(trim => [trim.id, trim.modification_id]))
  const trimIds = query.trimIds.filter((id) => {
    const modificationId = owner.get(id)
    return modificationId === undefined || selected.has(modificationId)
  })
  return trimIds.length === query.trimIds.length ? query : { ...query, trimIds }
}
```
Правила безопасности:
- Без модификации комплектации снимаются **всегда** — фасеты для этого не нужны, поэтому правило работает и при SSR, и до загрузки фасетов.
- Комплектация, которой нет в фасетах, **не** снимается: иначе фильтр «мигал» бы, пока фасеты грузятся, или пропадал бы при нулевом количестве из-за других фильтров.
- Функция не создаёт новый объект, если ничего не изменилось (без лишних `router.replace`).

### 2.3. `SpecialEquipmentCatalogPanel.vue`
1. **Центральная очистка в `updateCatalogQuery`:** после сборки `next` применять `pruneTrimSelection(next, facets.value.trims)`. Это покрывает все пути изменения модификаций: чип модификации, каскад от чипов марки/модели (они уже пересчитывают `modificationIds`), диалоги фильтров.
2. **Нормализация URL при входе по ссылке:** добавить watcher (по образцу существующих watcher'ов очистки категорийных фильтров):
   ```ts
   watch(
     () => [catalogQuery.value.modificationIds, catalogQuery.value.trimIds, facets.value.trims] as const,
     () => {
       const cleaned = pruneTrimSelection(catalogQuery.value, facets.value.trims)
       if (cleaned !== catalogQuery.value) emit('update:queryState', cleaned)
     },
     { immediate: true },
   )
   ```
3. **Запросы к API:** `productsParams`/`facetsParams` строить из уже очищенного состояния, чтобы старая ссылка сразу давала выдачу без лишних `trim_id`: `requestQuery` = `catalogQueryForCategoryContext(pruneTrimSelection(catalogQuery.value, facets.value.trims), …)`.
4. **Чипы:** строятся из `requestQuery` — чипы отброшенных комплектаций не появляются. `removeActiveFilter` для `trim` не меняется.

### 2.3.1. Уточнение по актуальному контракту фасетов

При реализации проверен `get_facets`: фасет комплектаций снимает только
`trim_ids`, сохраняя `modification_ids` и остальные ограничения. Поэтому
прямая ссылка `baseBlack + safetyAll` возвращает пустой `facets.trims`;
предложенного watcher по текущим фасетам недостаточно для сценария 3.1.7.

Для выполнения исходного требования без изменения API панель запоминает
известную принадлежность комплектаций из загруженных фасетов. Если у выбранной
комплектации при выбранных модификациях владелец ещё неизвестен, перед запросом
выдачи и рабочих фасетов выполняется общий запрос фасетов категории без
сужающих фильтров, с обеими доступностями. Результат используется только для
проверки принадлежности; варианты диалога по-прежнему берутся из рабочих фасетов.

- Одновременные запросы используют один lookup на категорию за жизнь компонента.
- Начальная принадлежность определяется до регистрации `useAsyncData`,
  чтобы SSR payload сразу использовал очищенные ключи запросов.
- Запросы сохраняют snapshot query, пути категории и единицы пробега до await;
  существующая защита от устаревших ответов сохраняется.
- SSR и восстановление cached данных также заполняют сведения о принадлежности.
  Они передаются через Nuxt `useState` с ключом API витрины, категории и блока
  результатов, чтобы первый клиентский рендер совпадал с SSR и не показывал
  отброшенный чип до повторной загрузки фасетов.
- Если lookup не удался или комплектации нет даже в широких фасетах, она
  сохраняется согласно правилу «неизвестная принадлежность не доказывает ошибку».
- Без модификации комплектации удаляются сразу, без дополнительного запроса.
- Дополнительные E2E проверяют корректную ссылку после reload, нулевую выдачу
  из-за цены, сохранение неизвестного UUID и отсутствие чужого trim в запросах.
