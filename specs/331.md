# Ролевая видимость разделов по витринам

## Контекст

- Задача является внутренней и не связана с Bitrix.
- Реализация из MR !330 хранит независимую матрицу по витринам только для
  области `public`.
- Области `leasing_company`, `dealer` и `distributor` по-прежнему глобальны:
  одна настройка одновременно действует в основной и всех дополнительных
  витринах.
- Область `carcraft_employee`, показанная в интерфейсе как «Администратор», по
  требованиям должна оставаться глобальной.
- Workspace остаётся на маршрутах `/workspace/*`, а витрина, из которой он был
  открыт, передаётся валидированным `return_storefront` context из MR !330.
- Внутри `/{slug}` автомобильные изображения сейчас не загружаются: frontend
  ошибочно преобразует канонический `/api/v1/cars/images/{filename}` в
  несуществующий
  `/api/v1/storefronts/{slug}/cars/images/{filename}`.
- Минимальный frontend-воспроизводитель для `buildStorefrontApiPath('faw',
  '/cars/images/demo.webp')` возвращает ошибочный scoped URL вместо ожидаемого
  root URL; backend router inspection подтверждает наличие только
  `/cars/images/{filename}` и отсутствие image route в `storefront_router`.
- Ошибочный `apiPath` используется в карточке автомобиля, деталях, модельном
  ряду и dropdown избранного, поэтому дефект воспроизводится на нескольких
  публичных поверхностях одной общей причиной.
- Видимость разделов управляет навигацией и перенаправлением с скрытых страниц,
  но не заменяет ролевую авторизацию backend API.

## Цель

Сотрудник CarCraft должен настраивать видимость разделов отдельно для основной
и каждой дополнительной витрины во всех областях, кроме «Администратор»:

- «Публичный сайт» (`public`);
- «Лизинговая компания» (`leasing_company`);
- «Дилер» (`dealer`);
- «Дистрибьютор» (`distributor`).

«Администратор» (`carcraft_employee`) сохраняет одну общую матрицу для всех
витрин.

Пользователь бизнес-роли, открывший workspace из `/faw`, должен видеть
ролевую навигацию витрины `faw`; при прямом входе в `/workspace` должна
использоваться матрица основной витрины.

## Функциональные требования

### Матрицы по витринам

- Каждая витрина хранит независимые матрицы областей `public`,
  `leasing_company`, `dealer` и `distributor`.
- Матрица `carcraft_employee` хранится без витрины и применяется глобально.
- Изменение любой storefront-scoped матрицы основной витрины не меняет
  соответствующую матрицу `/faw`, и наоборот.
- Отсутствующие ключи продолжают получать безопасные domain/frontend defaults
  своей области.
- Ограничение каталога спецтехники действует только для `public`: в
  дополнительной витрине `special_equipment_catalog` всегда выключен.
- Ролевые матрицы не получают специальных ограничений из публичного каталога.

### Копирование при создании и миграции

- При создании новой витрины в той же транзакции сохраняется полный
  эффективный снимок всех четырёх storefront-scoped матриц основной витрины.
- В публичном снимке дополнительной витрины каталог спецтехники принудительно
  сохраняется как скрытый.
- После создания матрицы основной и дополнительной витрин изменяются
  независимо, без дальнейшего наследования.
- При миграции существующие глобальные overrides лизинговой компании, дилера и
  дистрибьютора становятся настройками основной витрины.
- Каждая существующая дополнительная витрина получает полный эффективный
  снимок этих трёх матриц основной витрины.
- Существующие публичные матрицы из MR !330 сохраняются без изменения.

### Административный экран

- Единый selector витрины показывается на вкладках «Публичный сайт»,
  «Лизинговая компания», «Дилер» и «Дистрибьютор».
- На вкладке «Администратор» selector отсутствует; интерфейс явно сообщает,
  что настройка общая для всех витрин.
- Если экран открыт из workspace с валидным `return_storefront`, эта витрина
  выбрана первоначально; при прямом входе выбирается основная витрина.
- Неактивные витрины доступны администратору для предварительной настройки и
  явно помечаются как выключенные.
- Черновики, сохранённые значения, загрузка и ошибки изолируются по сочетанию
  `scope + storefront UUID`.
- Переключение вкладки или витрины не теряет несохранённые черновики.
- Сохраняется только выбранное сочетание области и витрины.
- Ошибка одной матрицы не подменяет и не очищает состояние другой.
- Блокировка публичной спецтехники видна только для дополнительной витрины на
  вкладке «Публичный сайт».
- Состояния загрузки, ошибки, повтора, несохранённых изменений и успешного
  сохранения остаются доступны не только через цвет.

### Применение в workspace

- Для `leasing_company`, `dealer` и `distributor` прямой `/workspace/*`
  загружает матрицу основной витрины.
- Для тех же ролей workspace с валидированным
  `return_storefront=faw` загружает матрицу витрины `faw` через отдельный
  storefront-scoped API path.
- Внутренняя workspace-навигация и refresh сохраняют тот же target.
- Sidebar, topbar, landing page и guard прямых URL используют один общий
  resolver текущего visibility target.
- Скрытый раздел отсутствует в меню и при прямом открытии перенаправляет на
  первый доступный раздел той же витрины.
- Для `carcraft_employee` workspace всегда использует глобальную матрицу с
  `storefront_id = null`, даже если сохранён контекст возврата в `/faw`.
- Неизвестный или неактивный slug не должен приводить к загрузке другой
  витрины: context удаляется централизованно, после чего явно загружается
  основная витрина.
- Гонка деактивации между проверкой context и запросом матрицы обрабатывается
  так же, без молчаливого применения defaults или матрицы другой витрины.

### Автомобильные изображения под slug

- Карточки каталога, страница автомобиля, модельный ряд и другие публичные
  поверхности внутри `/{slug}` загружают те же разрешённые изображения, что и
  соответствующие страницы основной витрины.
- Storefront prefix применяется к API данных каталога, но не к бинарному
  image endpoint: канонический URL изображения остаётся
  `/api/v1/cars/images/{filename}`.
- Все frontend callers формируют URL автомобильного изображения через один
  общий helper и безопасно кодируют filename.
- В коде не остаётся вызовов storefront `apiPath` для `/cars/images/*`.
- Ошибка конкретного файла продолжает показывать существующий placeholder и не
  ломает загрузку карточки или страницы.
- Backend не получает фиктивный scoped image alias: существующий бинарный
  endpoint публичен, а filename сам по себе не содержит storefront/vehicle
  identity, необходимую для честной проверки принадлежности витрине.

## Планируемый технический контракт

### Domain и persistence

- Ввести явное разделение:
  - storefront-scoped scopes: `public`, `leasing_company`, `dealer`,
    `distributor`;
  - global scope: только `carcraft_employee`.
- Единый target validator требует UUID витрины для storefront-scoped scope и
  запрещает UUID для global scope.
- `GetSectionVisibilityQuery` и `UpdateSectionVisibilityCommand` передают
  target целиком до repository без отдельных public-only веток.
- CHECK constraint разрешает `storefront_id IS NULL` только для
  `carcraft_employee` и требует UUID для остальных четырёх областей.
- Storefront-уникальность обеспечивается по
  `(storefront_id, scope, section_key)`; глобальная — по
  `(scope, section_key)` для `carcraft_employee`.
- Upsert выбирает conflict target по типу validated visibility target, а не по
  специальной проверке `scope == 'public'`.

### Backend API

Публичные endpoints остаются без изменений:

- `GET /api/v1/section-visibility/public`;
- `GET /api/v1/storefronts/{storefront_slug}/section-visibility/public`.

Workspace получает симметричные runtime endpoints:

- `GET /api/v1/workspace/section-visibility` — default storefront для
  бизнес-роли, global matrix для администратора;
- `GET /api/v1/storefronts/{storefront_slug}/workspace/section-visibility` —
  активная дополнительная витрина для бизнес-роли; unknown/inactive slug
  возвращает `404`.

Административные endpoints:

- `GET /api/v1/admin/section-visibility` возвращает `{items: [...]}` только с
  глобальной матрицей `carcraft_employee`;
- `PATCH /api/v1/admin/section-visibility/carcraft_employee` обновляет только
  глобальную матрицу администратора;
- `GET /api/v1/admin/storefronts/{storefront_id}/section-visibility`
  возвращает `{items: [...]}` с полными матрицами `public`,
  `leasing_company`, `dealer` и `distributor` указанной витрины;
- `PATCH /api/v1/admin/storefronts/{storefront_id}/section-visibility/{scope}`
  частично обновляет одну из четырёх storefront-scoped матриц и возвращает
  полный итоговый ресурс.

Администратор может читать и изменять неактивную витрину по UUID. Неизвестный
UUID возвращает `404`; `carcraft_employee` на storefront path и storefront
scope на global path отклоняются с `422`. Public-only admin PATCH без scope из
MR !330 удаляется, compatibility wrapper не добавляется.

### Migration 103

- Revision `103` продолжает единственную PostgreSQL-цепочку от `102`.
- Upgrade удаляет старые partial indexes и target CHECK, переносит текущие
  глобальные overrides бизнес-ролей на UUID основной витрины, материализует
  полные эффективные snapshots для дополнительных витрин и создаёт новые
  constraints/indexes.
- Public rows и global `carcraft_employee` rows сохраняются.
- Downgrade удаляет storefront-role rows дополнительных витрин, сворачивает
  значения основной витрины обратно в глобальные бизнес-матрицы и
  восстанавливает ограничения revision `102`.
- Потеря различий дополнительных витрин при downgrade явная и неизбежна:
  схема `102` не умеет их представить; каноническими становятся значения
  основной витрины.
- Проверяется полный цикл `102 -> 103 -> 102 -> 103` на реальном PostgreSQL.

### Frontend

- Ввести единый typed visibility target: global administrator либо
  storefront-scoped `scope + {id, slug}`.
- Runtime cache, pending, attempts и errors ключуются по scope и UUID витрины;
  администратор хранится отдельной глобальной записью.
- Slug используется только для выбора API path; идентичность и проверка ответа
  используют UUID.
- Ответ backend принимается в cache только при точном совпадении `scope` и
  `storefront_id`; несовпадение завершается fail-closed в target запроса.
- Workspace return-context middleware хранит валидированный `{id, slug}`, а не
  доверяет сырому query-параметру.
- Общий resolver передаёт один target в sidebar, topbar, landing и
  `require-workspace` guard.
- Административные drafts/saved/status обобщаются с public-only maps на четыре
  storefront-scoped области.
- PATCH заменяет cache entry только выбранного target.
- Logout и смена роли сбрасывают активный runtime target; переключение между
  root и `/faw` в одной вкладке не переиспользует чужую матрицу.
- В feature автомобилей вводится единый builder канонического image URL;
  `CarCard`, детали автомобиля, модели, избранное и остальные customer callers
  используют его вместо storefront `apiPath`.

## Рассмотренные варианты

### Storefront slug как query-параметр одного workspace endpoint

Вариант уменьшает число объявленных routes, но смешивает глобальный и scoped
ресурсы в одном URL и добавляет отдельный parsing seam. Выбран отдельный
slug-scoped path: он совпадает с существующим storefront API и явно
fail-closed для неизвестной или выключенной витрины.

### Сохранить public-only admin endpoints и добавить отдельные role routes

Вариант уменьшает локальный diff, но закрепляет две разные модели одного
ресурса и умножает frontend branches. Выбран общий storefront resource для
четырёх областей без compatibility wrapper.

### Отдельные stores для public и workspace visibility

Вариант проще в каждой отдельной точке, но дублирует правила cache, ошибок,
гонок и валидации UUID. Выбран единый typed target и общий state seam.

### Добавить backend alias `/{storefront_slug}/cars/images/{filename}`

Вариант заставил бы текущие ошибочные frontend URL отвечать, но не обеспечил
бы реальную storefront-изоляцию: по одному filename backend не может проверить
принадлежность изображения автомобилю выбранной витрины. Выбран канонический
root image endpoint и единый frontend builder; scoped остаются запросы данных
автомобилей, где проверяется warehouse membership.

## Тестирование

### Backend

- Domain target matrix принимает четыре storefront-scoped области с UUID и
  только `carcraft_employee` без UUID; обратные сочетания отклоняются.
- DB CHECK и partial unique indexes запрещают неверную форму target и дубликаты.
- Root и `/faw` матрицы каждой бизнес-роли читаются и изменяются независимо.
- Workspace root/custom endpoints возвращают правильные UUID и scope;
  неизвестная, выключенная и деактивированная между запросами витрина не
  подменяется основной.
- Admin list, storefront list и PATCH проверяют точные response shapes,
  разрешённые scopes, inactive UUID и ошибки `404/422`.
- Создание витрины копирует четыре матрицы одной транзакцией и затем остаётся
  независимым от основной.
- Migration покрывает отсутствие overrides, частичные overrides каждой роли,
  несколько активных/неактивных витрин и round-trip `103 <-> 102`.
- Alembic graph имеет единственный head `103` и линейную цепочку.

### Frontend

- Два UUID в одном scope и один UUID в двух scopes не смешивают matrix, error,
  attempt или pending state.
- Ответ с чужим `scope` или `storefront_id` не попадает в cache.
- Параллельные ответы не меняют активный target.
- Валидный workspace context содержит `{id, slug}`; invalid/inactive context
  удаляется через replace-navigation.
- Sidebar, topbar, landing и direct-route guard используют один target resolver.
- Selector присутствует на четырёх storefront-scoped вкладках и отсутствует
  только на «Администратор».
- Черновики переживают переключение scope/витрины; save очищает только
  выбранный target.
- Контрактные тесты фиксируют новые URLs и отсутствие legacy public-only admin
  методов.
- Regression test доказывает, что `faw` не добавляется к
  `/api/v1/cars/images/{filename}`, а source-contract запрещает передавать
  `/cars/images/*` в storefront `apiPath`.
- Production build и desktop browser-сценарии проверяют root, `/faw`, refresh,
  внутреннюю workspace-навигацию, скрытый direct URL, возврат на сайт и
  фактическую загрузку изображений на карточке и странице автомобиля.

## Критерии готовности

- В разделе «Видимость разделов» витрина выбирается для «Публичный сайт»,
  «Лизинговая компания», «Дилер» и «Дистрибьютор».
- На «Администратор» selector отсутствует, а настройка одинакова для `/` и
  `/faw`.
- Изменение ролевого переключателя основной витрины не меняет `/faw`, и
  изменение `/faw` не меняет основную витрину.
- Бизнес-пользователь внутри workspace видит матрицу витрины, указанной в
  валидированном return-context; прямой `/workspace` использует основную.
- Скрытая workspace-страница не остаётся доступной через прямой UI URL и
  перенаправляет в первый видимый раздел текущей витрины.
- Новые и существующие дополнительные витрины получают независимый снимок всех
  четырёх storefront-scoped матриц.
- В `/faw` изображения загружаются на карточках, странице автомобиля,
  модельном ряду и остальных публичных customer surfaces без несуществующего
  storefront image API.
- Миграция `103`, backend checks, frontend architecture tests, production
  build, Docker build/run, логи и desktop browser acceptance выполнены до MR.
- MR создаётся только в `test`; после создания спецификация переименовывается в
  `specs/<номер-MR>.md`.

## Границы

- Не делать `carcraft_employee` зависимой от витрины.
- Не превращать visibility в backend ACL для бизнес endpoints.
- Не добавлять storefront-scoped данные workspace: по витрине меняется только
  интерфейсная видимость разделов.
- Не вводить наследование настроек после создания витрины.
- Не добавлять mobile-only UI или сценарии для viewport меньше 768 пикселей.
