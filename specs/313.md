# Bitrix 21514: статусы автомобилей заявки

## Постановка

Задача Bitrix: https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/21514/

В интерфейсе статусы автомобилей заявки отображаются как `Активна` или сырым
значением `confirmed`, а после части действий дилера сохраняется неверный
статус. Необходимо привести переходы и пользовательские названия к единому
контракту.

## Подтверждённые причины

- новый автомобиль заявки получает внутренний статус `active`, но в сводке он
  переводится как `Активна`, хотя для автомобиля должен отображаться как
  `Подтверждается`;
- завершённое действие `discount` не меняет `active` на `confirmed`;
- завершение замены в текущем интерфейсе отправляет действие `replace_vin`,
  которое ошибочно устанавливает `confirmed` вместо `replacement`;
- часть фронтенда не знает коды `confirmed`, `not_confirmed` и `replacement`,
  поэтому показывает пользователю сырой код;
- справочник `cars_status` уже содержит правильные русские названия, но
  представление автомобилей заявки его не использует.

## Требования

1. Сохранить четыре внутренних статуса автомобиля заявки:
   `active`, `not_confirmed`, `confirmed`, `replacement`.
2. Новый автомобиль заявки автоматически получает `active`, который во всех
   пользовательских представлениях автомобиля называется `Подтверждается`.
3. После действия `reject` сохранять `not_confirmed` и отображать
   `Не подтверждено`.
4. После завершения резервирования (`reserve`) сохранять `confirmed` и
   отображать `Подтверждено`.
5. После сохранения скидки (`discount`) сохранять `confirmed` и отображать
   `Подтверждено`.
6. После завершения замены автомобиля (`replace_vin`) сохранять `replacement`
   и отображать `Замена ТС`. Промежуточное действие `contact_client` не должно
   само менять статус.
7. Во фронтенде использовать единое сопоставление кодов статуса автомобиля с
   указанными русскими названиями. Не показывать сырой код статуса и не
   использовать название `Активна` для автомобиля.
8. Статус самой заявки `Активна` не менять: он относится к заявке, а не к
   автомобилю.
9. Для уже сохранённых данных исправлять только записи, которые можно
   определить однозначно без изменения результата более позднего действия.
   Активный автомобиль с сохранённой скидкой переводить в `confirmed`.
   Исторические замены без достоверного признака действия автоматически не
   переклассифицировать.
10. Для каждого из четырёх статусов автомобиля использовать собственный цвет
    плашки во всех представлениях: синий для `active`, красный для
    `not_confirmed`, зелёный для `confirmed` и янтарный для `replacement`.

## Планируемые изменения

- скорректировать таблицу переходов дилерских действий в backend;
- добавить безопасную миграцию существующих активных автомобилей с уже
  сохранённой скидкой;
- вынести пользовательские названия статусов автомобиля в общий frontend
  helper вместе с цветами плашек и применить его в деталях заявки, сводке
  позиций и карточке заявки;
- учесть нормализованный исторический статус отклонённого автомобиля в сводке,
  не меняя правила расчёта итоговой стоимости;
- добавить backend- и frontend-регрессионные тесты на переходы и подписи.

## Критерии готовности

- каждый из четырёх сценариев возвращает и сохраняет ожидаемый статус;
- во всех затронутых представлениях автомобиля показана точная русская подпись;
- четыре статуса автомобиля визуально различаются собственными цветами;
- тесты воспроизводят прежние ошибки для `discount`, `replace_vin`, `active` и
  сырого `confirmed`, затем проходят после исправления;
- обязательные backend-проверки `ruff`, `lint-imports`, `mypy` и `pytest`
  проходят без новых ошибок;
- frontend-проверки проходят, сценарий вручную проверен в браузере при ширине
  не менее 768 CSS-пикселей;
- backend, frontend и nginx собраны и запущены через Docker Compose, в логах
  нет ошибок, связанных с изменением.
