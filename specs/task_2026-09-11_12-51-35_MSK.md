## Требуемый результат

1. Существующие заявки клиента отображаются в «Моих заявках» и ответе `GET /api/v1/applications`.
2. Запрошенные дополнительные документы доступны при обычном входе в заявку, без обязательного перехода из уведомления. При отсутствии запросов нет ложного «Нет доступа к документу».
3. Комментарий клиента виден возле соответствующего автомобиля у клиента, дилера и лизинговой.
4. Открытая клиентом заявка после назначения лизинговых автоматически показывает третий шаг. Первые два шага доступны для просмотра, изменение и повторная отправка через них недоступны.

## 1. Пустой список заявок

### Воспроизведение и причина

Минимальная конфигурация: клиент имеет право работать с компанией B, в JWT выбрана компания A либо компания отсутствует; заявка B содержит `created_by=client.id`.

Фактические ответы исходного кода:
- `GET /api/v1/applications/{id}`: 200, заявка доступна.
- `GET /api/v1/applications`: 200, `applications=[]`, `total=0`.
- При совпадающей компании JWT контрольный сценарий успешен.
- Дополнительно пройден реальный `POST /api/v1/applications/draft` для компании B с JWT компании A: создание 201, карточка 200, следующий список пуст.

Причина подтверждена сравнением одного фактора: карточка учитывает авторство, список — только текущую компанию и её разрешение:
- `backend/application/queries/applications/get_application.py:get_authorized_application` и `backend/domain/entities/leasing_application.py:_owned_by_client` разрешают доступ автору.
- `backend/application/queries/applications/list_applications.py:handle_list_applications` может вернуть пустой результат до выборки, если нет `can_view_applications`.
- `backend/infrastructure/repositories/application_repository.py:list_for_user` для клиента выбирает только `company_id`; при отсутствии компании возвращает пустой список.

Версии о влиянии статуса, машин, запросов документов или назначенных лизинговых не объясняют результат: минимальная заявка без этих связей уже воспроизводит ошибку. Свежие права сами по себе не исправляют несовпадающий контекст.

### Что будет изменено

1. В `ListApplicationsQuery` явно передать признак включения авторских клиентских заявок.
2. В `handle_list_applications` отдельно определить право просмотра текущей компании. Отсутствие этого права не должно исключать собственные авторские заявки клиента, уже доступные через карточку.
3. В `list_for_user` для обычного клиентского списка построить одну SQL-область:
   - `created_by == user_id`;
   - либо `company_id == actor_company_id`, только когда есть действующее право просмотра этой компании.
4. Применять ту же область к строкам и `total`; сохранить сортировку, фильтр статуса, пагинацию и отсутствие дублей.
5. В `backend/presentation/routers/applications.py:list_applications` при явном `notification_company_id` выключать авторское расширение: такой запрос остаётся ограниченным выбранной и проверенной компанией.
6. Не добавлять неавторские заявки остальных компаний пользователя. Изменение выбора компании в интерфейсе кабинета не требуется.

Существующее исключение авторства карточки действует даже после отзыва членства. План сохраняет это правило для собственных заявок в общем списке; расширение доступа к документам из него не следует. Явный selector с отозванными правами по-прежнему запрещён.

Реальная клиентская точка входа — `frontend/pages/cabinet.vue:fetchApplications`, вызывающая список без контекста компании; `MyApplicationsPanel.vue` — отдельное представление, не причина этого сценария.

## 2. «Нет доступа к документу» при обычном входе

### Воспроизведение и причина

На тех же данных:
- история запросов без контекста компании заявки: 403 «Нет доступа к документу»;
- та же история с `notification_company_id=B`: 200;
- загрузка без контекста: 403; с B: 201;
- скачивание с B: 200 и точные тестовые байты;
- история после загрузки содержит `provided`;
- повтор без контекста снова возвращает 403.

Даже при отсутствии запросов документов история возвращает ложный для разрешённого клиента 403. Это объясняет сообщение под заявкой из пункта 4 до запроса файлов.

Backend намеренно проверяет компанию в:
- `backend/application/queries/documents/list_document_requests.py:_resolve_leasing_company_filter`;
- `backend/application/commands/documents/upload_for_application.py`.

Авторизованная карточка и её дочерние запросы получают разный контекст: `frontend/pages/application/[id].vue` передаёт через `provideNotificationCompanyContext` только параметр URL. Прямой вход этого параметра не содержит, переход из уведомления содержит.

Проверены и настоящие frontend-компоненты: `ApplicationPage` + `DocumentRequestHistory`, выбор файла и ссылка скачивания. Неизменный тест прямого входа падает на исходниках, проходит после исправления контекста, снова падает после отката.

### Что будет изменено

Изменить контекст в `frontend/pages/application/[id].vue`:

1. Сохранить отдельный UUID-валидируемый getter явного контекста URL для запросов самой страницы и сравнения контекста до/после асинхронной гидратации.
2. Для дочерних компонентов клиента, когда явный `notification_company_id` отсутствует, передавать `applicationCompanyId` из успешно авторизованного ответа карточки.
3. При явно заданном валидном UUID-контексте сохранять его приоритет; не заменять явный параметр другой компанией и сохранить текущую валидацию.
4. Применять автоматический контекст только к клиенту. Для дилера, дистрибьютора и сотрудника сохранить прежнее поведение.
5. `DocumentRequestHistory` и `documentsApi` уже используют переданный контекст для истории, загрузки и скачивания; их ACL и формат запросов менять не требуется.

Почему нужен пункт 4: эксперимент с автоматическим контекстом для всех ролей менял запросы дилера на компанию клиента. Контрольный тест обнаружил регрессию; версия с ограничением клиентской ролью проходит проверки дилера, дистрибьютора и сотрудника.

Backend-проверки доступа остаются действующими. Для чужой компании, отозванного права просмотра и удалённого членства проверены 12 отрицательных HTTP-запросов к списку, карточке, истории и загрузке: все 403. Полученный из карточки UUID не становится самостоятельным разрешением доступа к файлам.

## 3. Комментарии около автомобилей

### Воспроизведение и причина

Рендер реальных компонентов показывает названия и цены машин, но не переданные в API разные `comment`. Проверены клиентские карточки, окно дилера, страница лизинговой, подробности КП и история состава.

Причина: значение доходит до данных компонентов, но отсутствует в шаблонах просмотра. CSS исключён — текста нет в сформированном HTML. Backend `item_projection.py` уже передаёт `comment`.

Однофакторная проба добавления вывода только в общий summary уменьшила количество падений с 8 до 5: самостоятельные карточки требуют собственного подключения. Полная временная правка вывода дала 11 passed; откат снова дал 8 failed / 3 passed.

### Что будет изменено

1. Добавить `frontend/features/commerce/components/CommerceApplicationItemComment.vue`:
   - вход `comment?: string | null`;
   - подпись «Комментарий клиента»;
   - вывод только при непустом `comment?.trim()`;
   - обычная Vue-интерполяция, `whitespace-pre-wrap` и перенос длинных слов.
2. Подключить его к следующим представлениям:
   - `CommerceApplicationItemsSummary.vue`: активные и исторические позиции;
   - `features/applications/components/ApplicationCard.vue`: карточки списка;
   - `features/applications/components/ApplicationDetailModal.vue`: собственные карточки машин дилера;
   - `features/checkout/components/CheckoutOfferModal.vue`: машины в подробностях КП, используя существующий `stringField(applicationItem, 'comment')`;
   - `pages/workspace/leasing-applications/[id]/index.vue`: самостоятельные карточки ЛК; нормализованные позиции исправляются через общий summary.
3. Добавить `comment?: string | null` в интерфейс `ApplicationVehicle` в `features/applications/api/applicationsApi.ts`: сейчас это поле в интерфейсе отсутствует.
4. Сохранить отдельное значение `dealer_comment` и существующие правила редактирования.
5. Закрепить реальным рендером разные комментарии у двух автомобилей, пустое/null/пробельное значение, переносы, длинную строку и HTML-подобный текст без исполнения разметки.

## 4. Автоматический переход и первые два шага

### Воспроизведение и причина

Подтверждён точный вариант:
1. Заявка уже создана со статусом `active` и доступна администратору.
2. Клиент переходит с анкеты на «О компании».
3. Администратор назначает лизинговую до последней кнопки отправки на этой странице.
4. Через 15 секунд страница всё ещё на `company`; нового GET заявки нет.

`startWaitingDistributionPolling` запускается через `watch(isWaitingForDistribution)`. Этот признак зависит от локально завершённого финального submit и маркера сохранения. Серверная активная заявка до этого клика уже может быть распределена, а страница за назначением ещё не наблюдает.

Контроль: после полностью завершённого финального submit при исправном localStorage текущий код уже автоматически открывает третий шаг. Изменять таблицу статусов не требуется: настоящий admin API создаёт LCA `submitted`, который уже входит в раздел `sent`.

Проверка реального HTTP admin assignment подтвердила:
- назначение: 200; detail содержит LCA `submitted` и его `leasing_company_id`;
- история без запросов при правильном контексте: 200, пустые `batches`;
- изменения анкеты, компании и состава после назначения: 400 «Заявка уже отправлена в лизинговые компании».

Таким образом, успешное изменение данных на сервере после назначения не воспроизведено. Подтверждены устаревший редактируемый интерфейс и повторная попытка PUT; сервер уже отклоняет изменение.

### Что будет изменено

Только `frontend/pages/application/[id].vue`:

1. Запускать наблюдение за распределением для клиентской серверной заявки `active`, когда у неё ещё нет доступного статусного раздела; не привязывать начало опроса к финальному клику/localStorage.
2. Сохранить интервал 15 секунд, остановку после появления распределения и при уходе со страницы.
3. В `refreshWaitingDistribution` получать свежую заявку, но обновлять только `status` и `leasing_company_applications` текущей заявки.
4. В `hydrateApplication` предусмотреть этот режим обновления и проверку актуальности application ID/контекста; не перезаписывать редактируемые questionnaire/items/company во время фонового запроса.
5. Сохранять текущий признак отправки в памяти при недоступном localStorage, когда обновляется та же заявка.
6. В `onNext` добавить ранний выход при ожидании распределения наряду с `saving`, чтобы запоздалый повторный обработчик не отправлял PUT.
7. После полученного назначения использовать существующий переход на первый доступный статусный шаг. Блокировку полей анкеты первого шага закрепить нативной disabled-группой `fieldset` с `min-w-0`: CSS `pointer-events-none` оставлял возможность изменить текст с клавиатуры. Навигация по шагам и загрузка документов находятся вне этой группы. Второй шаг `CheckoutCompanyData` уже информационный: вкладки, выбор года и просмотр отчётов должны оставаться доступными. Его не отключать ни через `fieldset`, ни через `pointer-events-none`; искусственный readonly-prop ему не требуется.

Опасность наивного решения проверена экспериментом: полный `hydrateApplication` каждые 15 секунд заменяет введённый адрес старым серверным значением. Исправление должно включать сохранение несохранённых данных, а не только более ранний запуск таймера.

## Реализация после подтверждения

При переносе polling в рабочий код отдельными RED → GREEN тестами подтверждены и закрыты гонки: поздний ответ или 403 прежней загрузки не перезаписывает новую заявку/контекст; для одной заявки выполняется не более одного фонового запроса; ответ polling не вмешивается в сохранение анкеты. Сетевые ошибки, 429 и 5xx фонового опроса сохраняют введённые данные и допускают следующую попытку; актуальные 403/404 по-прежнему закрывают доступ. Это уточняет защиту актуальности запроса из пункта 4 плана.
