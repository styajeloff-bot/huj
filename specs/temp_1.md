# Исправление привязки выбранных автомобилей к складу

## Контекст

- Bitrix: https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/21742/
- Экран: административный раздел «Склады» → действие с иконкой автомобиля → модальное окно «Привязка машин к складу».
- Наблюдаемый сценарий: пользователь выбирает один или несколько автомобилей и нажимает «Привязать выбранные». В интерфейсе появляется общее сообщение «Ошибка привязки машин».

Текущий frontend отправляет на `POST /api/v1/admin/warehouses/{warehouse_id}/vehicles` тело с массивом `vehicle_ids` и ожидает объект статистики. Текущий backend принимает только одно поле `vehicle_id` и возвращает сведения об одной привязке. Поэтому запрос с выбором из модального окна не проходит валидацию.

Дополнительно список кандидатов отправляет `exclude_warehouse_id`, который скрывает машины только выбранного склада. Автомобили, уже привязанные к другому складу, могут остаться в списке, хотя одиночный backend-контракт правильно отклоняет их с конфликтом. Это создаёт ошибочный доступный выбор.

## Цель и бизнес-результат

Администратор должен суметь привязать один или несколько выбранных непривязанных автомобилей к складу одним действием. После успешной операции список кандидатов и вкладка «Машины на складе» должны обновиться, а пользователь должен увидеть фактическое количество привязанных машин.

Это устраняет блокировку операционного сценария распределения автомобилей по складам и не изменяет существующий безопасный контракт одиночной привязки, отвязки, массовой привязки по марке или переноса между складами.

## Решение

Рекомендуемый вариант — добавить отдельный массовый API-контракт для выбора в модальном окне и оставить текущий `POST /api/v1/admin/warehouses/{warehouse_id}/vehicles` для одной машины без изменений.

- Добавить endpoint с отдельным, однозначным маршрутом для привязки списка выбранных UUID, например `POST /api/v1/admin/warehouses/{warehouse_id}/vehicles/bulk`.
- Backend принимает непустой массив `vehicle_ids` размером до 500 элементов, предварительно проверяет существование склада и наличие всех выбранных автомобилей, затем выполняет привязки одной транзакцией.
- В ответе возвращается фактическая статистика операции: число успешно привязанных машин и число пропущенных из-за конкурентного изменения состояния. Такой частичный успешный результат допустим только после предварительной проверки входных UUID; отсутствующий склад или автомобиль завершают запрос ошибкой без частичных изменений. Перенос между складами не выполняется и не заявляется как результат этой операции.
- Frontend направляет выбранные UUID в новый массовый маршрут, отображает фактический результат и перезагружает обе таблицы только после успешного ответа.
- Запрос списка кандидатов дополняется `only_unbound=true`, чтобы в интерфейс не попадали машины, уже находящиеся на любом складе.
- Обработка ошибок читает стандартное поле FastAPI/problem-details `detail` и сохраняет запасной понятный текст, если сервер не передал сообщение.

### Рассмотренные альтернативы

1. **Отправлять одиночный запрос для каждой выбранной машины из браузера.**
   - Плюс: меньше серверного кода.
   - Риск: частичная операция без единой транзакции, несколько сетевых запросов, сложная и ненадёжная агрегация ошибок.

2. **Изменить существующий одиночный endpoint так, чтобы он принимал и UUID, и массив UUID.**
   - Плюс: один URL.
   - Риск: два разных тела и два разных ответа на одном маршруте ухудшат контракт и могут сломать других клиентов одиночной операции.

3. **Рекомендуемый: выделить отдельный массовый endpoint.**
   - Чётко отделяет один автомобиль от массового выбора.
   - Позволяет атомарно обработать список и вернуть статистику, которую ожидает интерфейс.
   - Не создаёт окна «отвязать, затем привязать» и не перемещает машины между складами.

## Планируемые изменения

### Backend

- `backend/presentation/schemas/admin_warehouses.py`
  - добавить отдельные request/response-схемы массовой привязки с UUID-массивом минимальной длины 1 и числовой статистикой;
  - не менять `AddVehicleToWarehouseRequest` и `AddVehicleResponse` одиночной операции.

- `backend/application/commands/warehouses/`
  - добавить узкий use case массовой привязки выбранных автомобилей;
  - переиспользовать существующие проверки склада, существования автомобиля и защиту от конкурентной привязки;
  - не реализовывать перенос между складами и не удалять существующие связи.

- `backend/infrastructure/repositories/warehouse_repository.py`
  - использовать безопасную пакетную запись и вернуть фактическое число созданных привязок;
  - сохранить инвариант: один автомобиль может быть привязан максимум к одному складу.

- `backend/presentation/routers/admin_warehouses.py`
  - зарегистрировать отдельный массовый endpoint с теми же правами администратора;
  - выполнить commit только при успешном завершении use case;
  - вернуть структурированную ошибку при недоступном складе, несуществующем автомобиле или конкурентном конфликте.

- `backend/tests/integration/test_admin_warehouses_router.py`
  - добавить регрессионные HTTP-тесты массовой привязки одного и нескольких автомобилей;
  - подтвердить, что после ответа машины отображаются на складе;
  - подтвердить, что пустой массив отклоняется, а одиночный endpoint сохраняет действующий контракт.

### Frontend

- `frontend/features/admin/vehicles/components/VehicleWarehouseBindingModal.vue`
  - отправлять выбор в новый массовый endpoint;
  - передавать `only_unbound=true` при загрузке доступных автомобилей;
  - показывать соответствующий фактическим данным итог без несуществующего признака «перемещено»;
  - выводить серверный `detail` при ошибке, с запасным русским сообщением;
  - после успеха очистить выбор и обновить список кандидатов, список машин склада и счётчик вкладки.

- `frontend/types/admin.ts`
  - привести тип результата к новому массовому контракту и удалить из этого сценария неподтверждённый признак перемещения.

- `frontend/tests/architecture/`
  - добавить или расширить точечную архитектурную проверку контракта модального окна: отдельный bulk URL, `vehicle_ids`, `only_unbound=true`, обработка `detail` и отсутствие клиентского переноса.

## Критерии готовности

- При выборе одной непривязанной машины кнопка «Привязать выбранные (1)» приводит к успешной привязке, и машина появляется во вкладке «Машины на складе».
- При выборе нескольких непривязанных машин все они привязываются одной серверной операцией, а интерфейс показывает фактическое число привязанных машин.
- Пустой список UUID не принимается сервером.
- Одиночный `POST /api/v1/admin/warehouses/{warehouse_id}/vehicles` с `vehicle_id` продолжает работать без изменения тела и ответа.
- Автомобили, уже привязанные к любому складу, не показываются среди доступных для выбора в этом модальном окне.
- Если операция не может быть выполнена, модальное окно выводит понятное сообщение сервера, а не только общий текст.
- Операция не перемещает машину между складами, не удаляет существующие привязки и не меняет массовую привязку по марке.
- Пройдут профильные backend- и frontend-проверки; перед MR будут отдельно зафиксированы результаты линтеров, тестов, Docker-сборки, запуска сервисов и просмотра логов.
- MR будет создан только в `test`, со ссылкой на Bitrix #21742 и списком фактически выполненных проверок.

## Вопросы и границы

- Блокирующих вопросов нет: по предоставленному экрану и сетевому маршруту объём ошибки определён.
- Неблокирующее ограничение: если между загрузкой списка и нажатием кнопки машина будет привязана другой операцией, backend должен безопасно сообщить о конфликте; интерфейс покажет результат/ошибку без попытки переноса.
- В задачу не входят изменение прав доступа, массовый перенос между складами, аудит перемещений, миграции БД и изменение данных в существующих складах.
