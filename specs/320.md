# Bitrix 22144: цена по запросу для спецтехники

## Источник и статус

- Задача: <https://carcraftpro.bitrix24.ru/company/personal/user/738/tasks/task/view/22144/>.
- Название в Bitrix: «Разработка по ТЗ №15. Цена по запросу».
- Вложение: `Разработка по ТЗ №15. Цена по запросу.docx`, четыре страницы,
  полностью прочитано и визуально проверено 26.08.2026.
- Родительская задача: «Эпик. Каталог Спецтехники (грузовики)».
- Тип работы: `feature`; ветка `feature/22144` создана от актуального `test`
  (`bb1f617a`).
- Статус: спецификация согласована командой «Делай» 26.08.2026; основная
  реализация объединена через MR !320. Follow-up от 28.08.2026 переключает
  активный frontend-поток скачивания и создания импорта на v5 в MR !334.

## Цель

Дать возможность публиковать объявление спецтехники без заранее известной
точной цены как «от N ₽», включать такую позицию в обычную смешанную заявку на
лизинг, получать окончательную стоимость от дилера и не позволять сотруднику
CarCraft назначить лизинговую компанию до согласования всех таких позиций.

Решение относится только к домену спецтехники. Оно не меняет цены автомобилей
и других каталогов.

## Подтверждённое текущее состояние

1. В `special_equipment_products` есть nullable `price` и `special_price`, но
   нет явных `price_on_request` и `price_from`. Нулевая обычная цена разрешена
   ORM CHECK-ограничением, а положительная цена требуется только для отдельных
   статусов.
2. Публичная проекция считает эффективной ценой
   `COALESCE(special_price, price)`. Карточка и detail показывают
   `Цена по запросу`, когда `price = null`, без нижней границы «от N ₽».
3. Форма управления объявлением содержит обычную и специальную цену, но не
   содержит признака «Цена по запросу» и поля «От».
4. Текущий checkout считает позицию без `price` неизвестной по стоимости и
   разрешает оформить её в лизинг только отдельной заявкой, одной единицей и
   без платных либо косвенных надстроек. Смешанная заявка из обычных позиций и
   позиций без цены отклоняется.
5. `special_equipment_application_items` хранит цену расчёта в `unit_price` и
   `total_price`; отдельного статуса согласования, автора и времени установки
   цены нет. Общая сумма заявки уже пересчитывается по активным автомобилям и
   позициям спецтехники.
6. Дилер просматривает свои заявки через `/workspace/applications` и
   `ApplicationDetailModal`, где позиции спецтехники приходят в общей
   `items`-проекции. Действия установки цены для такой позиции нет.
7. Admin endpoint
   `PUT /api/v1/admin/applications/{application_id}/assign-leasing-companies`
   проверяет статус заявки, но не проверяет наличие несогласованных цен и не
   сериализован с дилерским изменением цены.
8. Кнопка назначения ЛК в административном списке доступна без учёта состава
   заявки. Серверный запрет остаётся обязательным независимо от состояния UI.
9. Текущий pipeline импорта принимает `price` и `special_price`, проверяет
   специальную цену и отдельные статусы, но действующий XLSX-шаблон v4 не
   поддерживает явную цену по запросу.
10. Отдельной массовой операции изменения коммерческих полей товара в текущем
    API нет. Все существующие точки записи — create, composite create, PATCH и
    импорт — должны использовать единый набор инвариантов, а DB constraints
    должны исключать обход при появлении новых writers.

## Область задачи

В задачу входят:

- явный коммерческий режим объявления `price_on_request` с положительным
  `price_from`;
- форма обычного и составного объявления, management API и импорт v2;
- публичные list/detail-контракты, карточки, detail, связанные представления и
  фильтрация/сортировка по цене;
- создание обычных и смешанных лизинговых заявок с предварительным расчётом по
  `price_from`;
- отдельный dealer-only API установки и повторного изменения точной цены;
- статус согласования, автор, время и неизменяемый audit trail;
- автоматический пересчёт суммы заявки в той же транзакции;
- блокировка назначения ЛК на API и в административном интерфейсе;
- журнал изменений цены, доступный администратору;
- миграция, автоматические тесты, Docker-проверка и browser smoke на desktop
  viewport не менее 768 CSS-пикселей.

Не входят:

- изменение цен или допустимости нуля в каталоге автомобилей и иных доменах;
- право сотрудника CarCraft или администратора устанавливать цену вместо
  дилера;
- право дилера выбирать либо менять лизинговые компании;
- покупка, резервирование или онлайн-оплата позиции до согласования цены;
- уведомления по email, SMS или push о необходимости выставить цену;
- мобильный интерфейс для viewport уже 768 CSS-пикселей;
- автоматическая конвертация исторических объявлений с `price = null` в новый
  режим без заданного положительного `price_from`.

## Термины и инварианты

- **Цена по запросу** — `price_on_request = true` и `price_from > 0`.
- **Предварительная цена** — `price_from`, показанная клиенту как «от N ₽» и
  использованная для первоначального расчёта заявки.
- **Согласованная цена** — положительная цена, введённая дилером для конкретной
  позиции заявки.
- **Ожидающая позиция** — активная billable-позиция спецтехники с
  `price_status = pending`.
- **Цена установлена** — `price_status = set`, заполнены `price_set_by` и
  `price_set_at`.
- Технические component-строки состава не являются самостоятельными
  billable-позициями и не получают `pending`/`set`.
- Все идентификаторы товара, заявки, позиции, пользователя и компании — UUID;
  frontend хранит их как непрозрачные строки.
- Все денежные вычисления backend выполняет через `Decimal`, без `float`.
- Валюта остаётся `RUB`.
- Ноль запрещён для заполненных `price`, `special_price`, `price_from` и цены,
  устанавливаемой дилером, только в домене спецтехники.
- Скрытие обычной и специальной цены в форме не очищает их значения. Пока
  включён `price_on_request`, публичный контракт и расчёт игнорируют эти поля.
- Признак `price_on_request` нельзя менять после первой публикации объявления,
  то есть при уже заполненном `published_at`, включая последующее архивирование.
- Выбор ЛК остаётся admin-only и разрешается только для активной заявки, у
  которой нет ожидающих цену активных позиций.

## Проектные уточнения к исходному ТЗ

Эти решения устраняют неоднозначности вложения и подлежат подтверждению вместе
со спецификацией:

1. ТЗ использует имя `agreed_price` в dealer API, но в перечне новых колонок
   позиции не добавляет такую колонку. Текущая модель уже хранит каноническую
   цену позиции в `unit_price` и `total_price`. Поэтому отдельный дублирующий
   денежный столбец не создаётся: входное и выходное поле API
   `agreed_price` отображается на `unit_price`, а `total_price` пересчитывается
   из количества. `price_status` отличает предварительную цену от окончательной,
   а исходный `price_from` фиксируется в `item_snapshot`.
2. Для совместимости со схемой проекта денежные колонки остаются
   `Numeric(15, 2)`, а не уменьшаются до `decimal(14, 2)` из вложения.
3. Вместо PostgreSQL native enum используется принятый в существующих моделях
   `String(20)` с CHECK `price_status IN ('none', 'pending', 'set')`. На wire
   контракт ограничивается `Literal`.
4. Функциональный `price_change_log` из ТЗ получает доменное имя таблицы
   `special_equipment_price_change_log`, чтобы не создавать общий журнал без
   владельца домена.
5. Требование «журнал доступен администратору» реализуется отдельным
   read-only endpoint, потому что во вложении endpoint просмотра не задан.
6. В таблице ошибок вложение использует полные коды
   `APPLICATION_NOT_ACTIVE` и `LEASING_COMPANY_ALREADY_ASSIGNED`, а в описании
   гонки — сокращённые варианты. Каноническими считаются полные коды из таблицы.

## Архитектурные границы и seam

1. Чистый модуль домена спецтехники владеет денежными инвариантами режима,
   проверкой допустимого перехода флага после публикации и переходом
   `pending -> set`. Он принимает значения и возвращает решение либо доменную
   ошибку, но не импортирует FastAPI, SQLAlchemy или другие слои.
2. Один application command `set requested equipment price` является внешним
   seam дилерского use case. Его интерфейс содержит UUID заявки/позиции,
   Decimal-цену и actor context; результат — новое состояние позиции и сумма
   заявки. Он скрывает ownership, lock/re-read, изменение строки, audit и
   пересчёт total от router и frontend.
3. Существующий admin assign command остаётся единственным seam назначения ЛК,
   но использует тот же repository lock/read primitive, что dealer command.
   Не создаётся второй endpoint или frontend-only путь назначения.
4. Repository primitive блокировки принимает только UUID заявки и при
   необходимости UUID позиции, возвращает dict-снимок заявки и активных
   billable-позиций. ORM-объекты не выходят из `infrastructure/repositories`.
5. Presentation владеет Pydantic schemas, role dependency, HTTP/error mapping
   и commit/rollback. Application не импортирует presentation, infrastructure
   models или SQL query builders; router не обращается к repository напрямую.
6. На frontend dealer action остаётся внутри
   `features/applications`; management-форма — внутри
   `features/specialEquipment`. Общий commerce summary получает только
   типизированные данные/слот и не импортирует внутренности dealer feature.
7. Основная тестовая поверхность совпадает с интерфейсами callers: product
   pricing domain module, dealer price command, admin assign command и HTTP
   endpoints. Внутренние repository helpers отдельно проверяются только на
   locking/query semantics.
8. Активные import-linter contracts сохраняются: domain не зависит от других
   слоёв, application/presentation не касаются ORM, SQLAlchemy queries остаются
   в repositories. Упомянутые в проектном design-skill `docs/glossary.md`,
   `docs/architecture/` и `docs/decisions/` в актуальной ветке отсутствуют;
   термины поэтому сверены с действующими entities, routers и UI.

## Функциональные требования

### 1. Создание и редактирование объявления

1. В форме обычного и составного объявления рядом с блоком стоимости есть
   checkbox `Цена по запросу`.
2. При включении checkbox поля `Цена` и `Специальная цена` скрываются, но их
   локальные и сохранённые значения не очищаются. Показывается обязательное
   поле `От, ₽` с шагом `0.01` и минимальным допустимым значением строго больше
   нуля.
3. При выключенном checkbox форма снова показывает ранее введённые обычную и
   специальную цену.
4. Create, composite create и PATCH принимают:
   - `price_on_request: boolean`;
   - `price_from: decimal | null`.
5. При `price_on_request = true` поле `price_from` обязательно и больше нуля.
   При `false` оно очищается либо игнорируется сервером и возвращается как
   `null`; скрытые `price`/`special_price` сохраняются.
6. Любое заполненное `price` и `special_price` должно быть больше нуля.
   Действующее правило `special_price < price` сохраняется.
7. Для статусов, которым нужна коммерческая цена, условие считается
   выполненным либо положительной обычной/специальной ценой, либо активным
   режимом с положительным `price_from`.
8. Если `published_at` уже заполнен, PATCH и импорт не позволяют изменить
   `price_on_request`; ответ management API — `409` с машинным кодом
   `PRICE_ON_REQUEST_MODE_LOCKED`. Изменение `price_from` без переключения
   режима остаётся допустимым через действующий ETag/If-Match-контракт.
9. Все ошибки денежных полей относятся к конкретному полю и возвращаются с
   HTTP `422`; frontend показывает их у соответствующего input.

### 2. Публичный каталог и карточка

1. Public list/detail product schema дополняется:
   - `price_on_request: boolean`;
   - `price_from: decimal-string | null`.
2. Для `price_on_request = true` публичные `base_price` и `special_price`
   возвращаются `null`, чтобы не раскрывать скрытые сохранённые значения;
   `price` содержит эффективную предварительную цену `price_from` для
   обратной совместимости существующего commerce-контракта.
3. Карточка, detail, избранное, корзина, совместимые надстройки и другие места,
   где показывается цена этого товара, используют явный флаг и выводят точно
   `от N ₽`, без сокращения до тысяч/миллионов.
4. Отсутствующая цена у legacy-товара без `price_on_request` не превращается в
   новый режим. До исправления данных такой товар сохраняет безопасное
   fallback-представление `Цена по запросу`, но не допускается в новый workflow
   согласования цены.
5. Price filter, price sort, facets, агрегирование одинаковых предложений и
   коммерческий fingerprint используют единую effective-price expression:
   `CASE WHEN price_on_request THEN price_from ELSE COALESCE(special_price, price) END`.
6. Фильтр считает товар с ценой по запросу подходящим по `price_from`.
   Остальные фильтры, UUID, pagination и публичная доступность не меняются.

### 3. Импорт и защита от нулевой цены

1. Добавляется XLSX-шаблон и parser v5 с колонками `price_on_request` и
   `price_from`; логические значения нормализуются тем же способом, что другие
   boolean-поля, деньги — через `Decimal` с двумя знаками. Контракты и parser
   версий v1-v4 остаются доступными без изменения заголовков.
2. Create, composite create, PATCH, импорт и репозитории записи используют одну
   доменную проверку коммерческих полей.
3. DB constraints обеспечивают:
   - `price IS NULL OR price > 0`;
   - `special_price IS NULL OR (price IS NOT NULL AND special_price > 0 AND special_price < price)`;
   - `price_from IS NULL OR price_from > 0`;
   - `NOT price_on_request OR price_from IS NOT NULL`;
   - статусные ограничения учитывают `price_on_request/price_from`.
4. Миграция сначала проверяет существующие нулевые значения. Она не заменяет
   их произвольной суммой и не включает `price_on_request` у строк без
   `price_from`. Если нули найдены, миграция останавливается с понятной
   диагностикой до исправления данных.
5. Ограничения не затрагивают таблицы и API других каталогов.
6. Экран импорта спецтехники скачивает актуальный XLSX-шаблон через
   `/api/v1/special-equipment/import-templates/v5/content` и при создании
   импорта отправляет `templateVersion: 5`. Backend-маршруты и контракты
   шаблонов v1-v4 сохраняются для обратной совместимости.

### 4. Создание лизинговой заявки

1. В одну заявку можно включить автомобили, обычную спецтехнику и несколько
   позиций спецтехники с ценой по запросу, включая разные компании-продавцы.
2. Ограничение текущего unpriced-flow «одна неизвестная позиция одной
   единицей» не применяется к явному `price_on_request`, потому что
   положительный `price_from` даёт расчётную сумму.
3. При создании заявки billable-позиция с `price_on_request = true` получает:
   - `unit_price = price_from`;
   - `total_price = price_from * quantity`;
   - `price_status = pending`;
   - `price_set_by = null`;
   - `price_set_at = null`;
   - snapshot с `price_on_request = true`, `price_from` и валютой.
4. Обычная billable-позиция получает `price_status = none` и сохраняет текущую
   логику effective price. Component-строка получает `none`.
5. `total_amount` и `total_items_price` первоначально включают `price_from`.
   Клиент видит расчётную сумму, но позиция и заявка сохраняют признак, что
   точная цена ещё ожидается.
6. Snapshot фиксирует условия на момент подачи заявки. Последующее изменение
   `price_from` в товаре не меняет ранее созданную заявку.
7. Purchase/reservation endpoints не считают `pending` окончательной ценой и
   не позволяют оплатить такую позицию до `price_status = set`.

### 5. Установка цены дилером

Добавляется endpoint:

```http
PATCH /api/v1/dealer/leasing-applications/{application_id}/items/{item_id}/price
```

Request:

```json
{
  "agreed_price": "7250000.00"
}
```

Правила:

1. Доступ только пользователю с ролью `dealer` и активной UUID-компанией.
2. Дилер может менять только billable-позицию, у которой
   `seller_company_id` совпадает с его текущей компанией. Владение другой
   позицией этой же смешанной заявки не даёт права менять целевую позицию.
3. Заявка и позиция должны существовать, позиция должна принадлежать UUID из
   path, заявка должна быть `active`, snapshot должен содержать
   `price_on_request = true`, а ЛК ещё не должна быть назначена.
4. `agreed_price` обязателен и строго больше нуля. Backend использует Decimal и
   приводит значение к двум знакам по действующему денежному контракту.
5. В одной транзакции обновляются `unit_price`, `total_price`,
   `price_status = set`, `price_set_by`, `price_set_at`, журнал и общая сумма
   заявки.
6. Дилер может повторять PATCH и менять цену, пока заявка активна и ЛК не
   назначена. Каждая успешная запись создаёт отдельную audit-запись.
7. Повтор того же значения идемпотентен по состоянию и возвращает `200`, но по
   требованию ТЗ обновляет `price_set_at` и создаёт audit-событие с одинаковыми
   old/new значениями.
8. Сотрудник CarCraft и администратор не могут вызвать этот endpoint вместо
   дилера. Дилер не получает endpoint назначения ЛК.

Response `200`:

```json
{
  "item_id": "00000000-0000-0000-0000-000000000000",
  "application_id": "00000000-0000-0000-0000-000000000000",
  "agreed_price": "7250000.00",
  "currency": "RUB",
  "status": "price_set",
  "price_set_by": "00000000-0000-0000-0000-000000000000",
  "price_set_at": "2026-08-26T12:00:00Z",
  "application_total_amount": "11000000.00"
}
```

Ошибки имеют endpoint-specific envelope без дополнительного `detail`:

```json
{
  "error_code": "ITEM_NOT_PRICE_ON_REQUEST",
  "message": "Для позиции не требуется согласование цены"
}
```

| HTTP | `error_code` | Условие |
| --- | --- | --- |
| 403 | `NOT_APPLICATION_DEALER` | текущая компания дилера не владеет целевой позицией |
| 404 | `APPLICATION_NOT_FOUND` | заявка не существует |
| 404 | `ITEM_NOT_FOUND` | позиция не существует |
| 404 | `ITEM_APPLICATION_MISMATCH` | позиция существует, но относится к другой заявке |
| 409 | `APPLICATION_NOT_ACTIVE` | заявка уже не активна |
| 409 | `LEASING_COMPANY_ALREADY_ASSIGNED` | к заявке уже назначена хотя бы одна ЛК |
| 422 | `PRICE_NOT_POSITIVE` | цена отсутствует, равна нулю или отрицательна |
| 422 | `ITEM_NOT_PRICE_ON_REQUEST` | позиция не участвует в price-on-request workflow |

### 6. Проекция заявки и кабинет дилера

1. `ApplicationSpecialEquipmentItem` и TypeScript `CommerceApplicationItem`
   дополняются `price_status`, `price_set_by`, `price_set_at` и явным
   `price_on_request` для позиции.
2. Lifecycle `status` позиции (`active`, `reserved`, исторические состояния)
   не переиспользуется для согласования цены.
3. В дилерском `/workspace/applications` у ожидающей позиции показываются badge
   `Выставить цену` и кнопка `Выставить стоимость`.
4. Кнопка открывает desktop modal с названием позиции, текущей предварительной
   либо ранее согласованной ценой и обязательным input больше нуля.
5. При успехе modal закрывается, detail заявки повторно загружается, badge,
   цена позиции и общая сумма обновляются без ручного reload; ошибки API
   показываются рядом с полем и через существующий toast.
6. После назначения ЛК кнопка исчезает/блокируется. Backend остаётся источником
   истины и возвращает `409`, если вкладка устарела.
7. Общий `CommerceApplicationItemsSummary` не получает дилерских полномочий:
   action передаётся из dealer detail через типизированный slot/callback либо
   отрисовывается отдельным dealer-owned блоком.

### 7. Блокировка назначения лизинговой компании

1. Существующий admin endpoint
   `PUT /api/v1/admin/applications/{application_id}/assign-leasing-companies`
   до любых side effects проверяет отсутствие активных billable-позиций с
   `price_status = pending`.
2. Если pending-позиция есть, endpoint возвращает `409` с кодом
   `PRICE_ON_REQUEST_PENDING`; `selected_leasing_companies`, LCA links,
   display number, purchase orders и support selections не изменяются.
3. Проверка действует при первом назначении и при последующем изменении набора
   ЛК. Позиции `removed`, `replaced`, `rejected` и component-строки не блокируют
   действие.
4. В admin list/detail возвращаются `pending_price_items_count` и
   `can_assign_leasing_companies`.
5. Кнопка получает текст `Выбрать лизинговую компанию`. При pending она
   disabled и показывает причину «Сначала дилер должен выставить цену для всех
   позиций». После согласования последней позиции данные заявки обновляются и
   кнопка становится доступна.
6. Скрытие или disabled-состояние кнопки не заменяет серверную проверку.

### 8. Конкурентность и атомарность

1. Dealer PATCH и admin assign используют один repository seam блокировки:
   строка заявки и её активные billable-позиции читаются `FOR UPDATE` в
   детерминированном порядке.
2. После получения lock каждая команда повторно проверяет статус заявки,
   назначенные ЛК и pending-позиции.
3. Если дилер первым установил последнюю цену, admin после ожидания lock видит
   `set` и может назначить ЛК.
4. Если admin первым назначил ЛК, dealer PATCH после ожидания возвращает
   `409 LEASING_COMPANY_ALREADY_ASSIGNED` без изменения цены и журнала.
5. Если статус заявки изменился, проигравшая команда возвращает
   `409 APPLICATION_NOT_ACTIVE`.
6. Изменение цены позиции, audit insert и пересчёт `total_amount` коммитятся
   одной транзакцией. Router, как и существующие presentation endpoints,
   владеет commit/rollback.

### 9. Журнал изменения цены

Создаётся `special_equipment_price_change_log`:

| Поле | Тип | Правило |
| --- | --- | --- |
| `id` | UUID | PK, `gen_random_uuid()` |
| `item_id` | UUID | FK на `special_equipment_application_items.id`, `RESTRICT` |
| `old_price` | `Numeric(15,2)` nullable | предыдущая `unit_price` |
| `new_price` | `Numeric(15,2)` | строго больше нуля |
| `changed_by` | UUID | FK на `users.id`, `RESTRICT` |
| `changed_at` | timestamptz | server default current timestamp |
| `source` | string | `dealer_ui` либо `api` |

1. Журнал append-only: update/delete application endpoints отсутствуют.
2. Для просмотра добавляется admin-only endpoint:

   ```http
   GET /api/v1/admin/applications/{application_id}/price-changes?limit=50&offset=0
   ```

3. Ответ содержит `items`, `total`, UUID позиции, старую/новую цену, автора,
   время и source в обратном хронологическом порядке с детерминированным
   fallback по UUID.
4. В раскрытых деталях admin-заявки показывается блок `История изменения цен`;
   пустое состояние отображается явно.
5. История доступна только CarCraft admin. Дилер видит текущее значение и время
   последнего изменения своей позиции, но не общий audit trail заявки.

## Изменения данных и миграция

1. Следующая Alembic-ревизия строится от единственной актуальной головы после
   `098` и проверяется командой `alembic heads` перед реализацией.
2. В `special_equipment_products` добавляются:
   - `price_on_request boolean NOT NULL DEFAULT false`;
   - `price_from Numeric(15,2) NULL`;
   - CHECK-ограничения из раздела 3;
   - effective-price index с `CASE` вместо текущего
     `COALESCE(special_price, price)`.
3. В `special_equipment_application_items` добавляются:
   - `price_status String(20) NOT NULL DEFAULT 'none'`;
   - `price_set_by UUID NULL` FK `users.id`;
   - `price_set_at timestamptz NULL`;
   - CHECK на допустимый status;
   - CHECK согласованности: `pending` не имеет setter/time, `set` имеет оба;
   - CHECK положительности заполненных `unit_price`/`total_price` для
     billable-позиций нового workflow.
4. Создаётся таблица журнала и индексы по `(item_id, changed_at DESC, id)` и
   по заявке через join-friendly `item_id`.
5. Existing products получают `price_on_request = false`, `price_from = null`.
   Existing application items получают `price_status = none`. Исторические
   `unit_price = null` не маркируются как pending.
6. Upgrade проверяет наличие нулевых коммерческих значений до установки новых
   CHECK. Downgrade удаляет только новые поля, индексы, constraints и журнал;
   существующие цены не переписываются.

## Критерии готовности

1. Checkbox «Цена по запросу» скрывает обычную/специальную цену без удаления
   и показывает обязательное поле «От».
2. `price_from = 0`, нулевая обычная/специальная цена и нулевая dealer price
   отклоняются в каждой special-equipment точке записи и DB constraint.
3. Признак нельзя поменять после первой публикации.
4. Public card/detail показывают `от N ₽`, а price filter сравнивает
   `price_from`.
5. Смешанная заявка с обычными и request-price позициями создаётся; pending
   позиция и первоначальный total используют `price_from`.
6. Только владеющий целевой позицией дилер может установить положительную цену;
   статус становится `set`, total обновляется атомарно.
7. Дилер может повторно изменить цену до назначения ЛК; одинаковое значение
   возвращает `200`, обновляет timestamp и записывает audit event.
8. Цена non-request позиции отклоняется с `422 ITEM_NOT_PRICE_ON_REQUEST`.
9. Позиция другой заявки отклоняется с `404 ITEM_APPLICATION_MISMATCH`.
10. Пока есть pending-позиция, admin UI блокирует выбор ЛК, а API возвращает
    `409 PRICE_ON_REQUEST_PENDING` без side effects.
11. После установки всех цен выбор ЛК автоматически становится доступен после
    обновления данных; право остаётся только у admin.
12. Одновременные dealer PATCH и admin assign не создают состояние с
    назначенной ЛК и более поздней неподтверждённой ценой; проигравшая команда
    получает предусмотренный `409`.
13. Admin видит полный append-only журнал изменений цены.
14. Purchase/payment не использует предварительную цену как окончательную.
15. Цены и допустимость нуля в других каталогах не меняются.
16. Все обязательные проверки зелёные, Docker-сервисы здоровы, в логах нет
    новых ошибок, desktop browser smoke пройден.
