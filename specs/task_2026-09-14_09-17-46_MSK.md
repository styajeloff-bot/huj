## 2. Цель и границы

Предоставить администратору в окне «Привязка машин к складу», вкладка «Машины на складе», три операции: физическое удаление одного автомобиля, отвязка всех автомобилей от выбранного склада и физическое удаление всех разрешённых к удалению автомобилей этого склада.

Все новые действия, предварительные проверки и сводки доступны только пользователю с ролью администратора. Дилер, дистрибьютор, лизинговая компания, клиент и остальные неадминистративные роли не получают новые кнопки или доступ к новым API. Наличие UUID, владение складом либо общее право просмотра автомобилей не дают разрешения на эти операции.

Исходное требование о UUID сохраняется: в таблицах складов внешние роли не видят UUID; администратор видит его только в подсказке. Это правило отображения, а не новая возможность внешних ролей. API продолжает возвращать UUID всем ролям, которые уже вправе читать соответствующий склад.

В задачу не входят удаление самого склада, изменения каталога спецтехники, изменение существующей поштучной отвязки и расширение прав внешних ролей. Существующие операции дистрибьютора не превращаются в новые административные endpoints; при переиспользовании общего кода необходимо сохранить их действующие контракты. Поддерживается только desktop web с viewport от 768 CSS-пикселей.

## 3. Правила удаления автомобиля

### 3.1. Блокирующие связи

Предварительная проверка, поштучное удаление, массовая сводка и массовое удаление используют один набор правил. Любая перечисленная связь блокирует физическое удаление, независимо от возможности каскадного удаления в БД. Отменённые заказы также блокируют; ограничение только «активными» статусами не применяется.

| Связь из исходного ТЗ | Проверка |
| --- | --- |
| `leasing_applications` | Прямая ссылка на автомобиль |
| `application_vehicles` | Автомобиль в составе заявки |
| `purchase_orders` | Любой заказ, включая отменённый |
| `exchange_requests` | Связь с запросом биржи |
| `shopping_cart` | Наличие автомобиля в корзине |
| `user_favorites` | Наличие в избранном, несмотря на CASCADE |
| `exchange_cart_items` | Наличие в корзине биржи, несмотря на CASCADE |
| `compensations` | Компенсация, связанная с автомобилем |
| `application_applied_supports` | Применённая мера поддержки |
| `leasing_application_vehicle_calculations` | Расчёт для автомобиля заявки |
| `calculation_history` | Вхождение UUID автомобиля в массив `vehicle_ids` |
| `guest_cart_transfers` | Связь с переносом гостевой корзины |

Перед реализацией сверить этот список с актуальными ORM, миграциями и схемой локальной БД, включая ссылки без FK, массивы и косвенные связи. Таблица описывает требования исходного ТЗ, а не результат полного аудита текущей БД. Дополнительные значимые зависимости нельзя молча удалить каскадом или игнорировать: отразить их в этой спецификации и проверке блокеров.

Каждая причина содержит стабильный `type`, количество связанных записей `count` и понятное описание `description`. Проверка собирает все причины, а не только первую. Идентификаторы сущностей остаются UUID в Python и непрозрачными строками на фронтенде.

### 3.2. Разрешённая очистка

`vehicle_warehouse_transfers` не блокирует удаление: backend явно удаляет историю перемещений перед удалением автомобиля, поскольку FK использует RESTRICT. `vehicle_warehouses` очищается каскадно вместе с автомобилем. Сам склад и справочники марки, модели, модификации, комплектации и характеристик не удаляются.

Проверка связей, удаление истории, карточки и сохранение заданий очистки файлов выполняются согласованно в одной транзакции. Не допускаются частичная очистка при отказе и события об удалении при rollback.

### 3.3. Конкурентные изменения

GET-проверка является предварительной: backend заново проверяет права и все блокеры при выполнении DELETE/POST. Если блокер появился после предварительной проверки, одиночное удаление возвращает 409; при массовом удалении автомобиль пропускается с причиной.

Нужна защита также от появления связи между последней проверкой и DELETE. Одной блокировки строки автомобиля недостаточно для таблиц без FK: при реализации определить и проверить согласованный механизм с путями создания таких связей. Не объявлять защиту завершённой только на основании повторного SELECT. Аналогично согласовать параллельные привязки и перемещения, чтобы массовая операция не затронула автомобиль другого склада и не учла один автомобиль дважды.

## 4. Пользовательские сценарии

### 4.1. Удалить автомобиль

1. Для строк списка администратор получает результат `deletion-check`. Пока проверка не завершена или завершилась ошибкой, удаление недоступно.
2. При блокерах кнопка «Удалить» неактивна, причины доступны для просмотра.
3. Если удаление разрешено, открыть подтверждение с названием автомобиля, VIN и предупреждением о физическом удалении. Обязательный ввод: VIN этого автомобиля либо точное слово «УДАЛИТЬ». При отсутствии VIN остаётся подтверждение словом.
4. Backend проверяет подтверждение, права и связи. Необязательный комментарий администратора `reason` не заменяет подтверждение.
5. После успеха обновить список, счётчики и связанные данные каталога; при 409 сохранить строку и показать актуальные причины. На время запроса блокировать повторное действие.

### 4.2. Отвязать все

Администратор видит подтверждение с количеством автомобилей всего склада и предупреждением, что текущие привязки будут сняты. Причина не запрашивается. Backend удаляет все записи `vehicle_warehouses` выбранного склада одной транзакцией; карточки автомобилей, их бизнес-связи и история перемещений сохраняются.

Операция не зависит от поискового фильтра, страницы и загруженных в браузер ID. Возвращается фактический `unbound_count`. Пустой склад и повторный вызов дают 200 и 0. После ответа UI обновляет таблицы и счётчики. Проверки блокеров физического удаления не ограничивают отвязку.

### 4.3. Удалить все

Перед подтверждением запросить серверную сводку по всему выбранному складу: общее количество, разрешённые и заблокированные автомобили, агрегированные причины. В окне явно указать, что операция действует на весь склад независимо от текущей страницы и фильтра.

Обязателен ввод слова «УДАЛИТЬ». При выполнении backend повторно применяет правила раздела 3 ко всем автомобилям выбранного набора. Разрешённые автомобили физически удаляются; заблокированные остаются на складе вместе со всеми данными. Итог может отличаться от предварительной сводки из-за изменения связей.

Ответ содержит `requested_count`, `deleted_count`, `skipped_count` и полный список пропущенных автомобилей с VIN и причинами. Для успешно завершённой операции `requested_count = deleted_count + skipped_count`. Несколько причин одного автомобиля не увеличивают число пропущенных автомобилей. Повторный вызов проверяет оставшиеся автомобили; если удалять нечего, возвращается 200 и `deleted_count = 0`.

Проектное решение для неописанного в DOCX технического сбоя: вся синхронная массовая операция выполняется в одной транзакции. Наличие бизнес-блокера — штатный пропуск, а непредвиденная ошибка БД приводит к rollback всех удалений этой операции и ошибке API. Не возвращать успешную сводку о незафиксированных изменениях. Пропущенные по бизнес-причинам автомобили не отвязывать.

### 4.4. Отображение UUID склада

Отдельного столбца с UUID нет. Только администратору доступна подсказка «ID склада: <UUID>», доступная по наведению и клавиатурному фокусу. У остальных ролей UUID не выводится также в подсказках и скрытых текстовых подписях. Не удалять поле из ответа API и не менять формат идентификатора.

## 5. Контракт API

Все перечисленные endpoints требуют аутентификации и строгой проверки административной роли на backend, включая GET-проверки. Недостаточно названия `/admin/` или scope, который может быть выдан другим ролям. Неаутентифицированный запрос получает 401, аутентифицированный неадминистратор — 403. Канонические пути работают без внешнего 307.

| Метод и полный путь | Тело запроса | Успешный ответ |
| --- | --- | --- |
| `GET /api/v1/admin/vehicles/{vehicle_id}/deletion-check` | Нет | `can_delete`, `vin`, `name`, `blocking_reasons` |
| `DELETE /api/v1/admin/vehicles/{vehicle_id}` | `confirmation: string`, `reason?: string` | `deleted: true`, `vehicle_id`, `cleaned_relations` |
| `DELETE /api/v1/admin/warehouses/{warehouse_id}/vehicles` | `confirmed: true` | `warehouse_id`, `unbound_count` |
| `GET /api/v1/admin/warehouses/{warehouse_id}/vehicles/deletion-check` | Нет | `warehouse_id`, `requested_count`, `deletable_count`, `blocked_count`, `blocking_reasons` |
| `POST /api/v1/admin/warehouses/{warehouse_id}/vehicles/bulk-delete` | `confirmed: true`, `confirmation: "УДАЛИТЬ"` | `warehouse_id`, `requested_count`, `deleted_count`, `skipped_count`, `skipped` |

Проектные дополнения к DOCX, включённые в предмет review: отдельный GET для массовой сводки и поле `confirmation` в POST массового удаления. В исходном POST был только `confirmed`; серверная проверка слова делает подтверждение обязательным также при прямом API-вызове.

В сводке `blocking_reasons` содержит агрегаты по `type`, число связанных записей `count`, число уникальных затронутых автомобилей `vehicle_count` и `description`. `blocked_count` — число уникальных автомобилей, поэтому сумма агрегатов разных причин может быть больше него. В списке `skipped` каждая запись содержит `vehicle_id`, `vin`, `blocking_reasons`.

Пустые причины и списки возвращаются как `[]`. Если VIN отсутствует, поле возвращается пустой строкой, без выдуманного VIN. `cleaned_relations` отражает фактические числа удалённых привязок и записей истории.

Ошибки бизнес-контракта:

- Неверное или отсутствующее текстовое подтверждение — 400, `confirmation_mismatch`.
- Отсутствующее либо ложное `confirmed` — 400, `confirmation_required`.
- Отсутствующий автомобиль — 404, `vehicle_not_found`; отсутствующий склад — 404, `warehouse_not_found`.
- Блокирующие связи при одиночном DELETE — 409, `vehicle_has_blocking_relations`, `deleted: false`, актуальные `blocking_reasons`.
- Пропуски из-за блокеров при массовом удалении не являются ошибкой всего запроса: 200 с результатами.

Проверку отсутствующего подтверждения реализовать так, чтобы она возвращала согласованный 400, а не случайный 422 от обязательного поля схемы. Остальные структурно некорректные запросы обрабатываются штатной валидацией API. Права проверяются до раскрытия VIN, количества или причин.

## 6. Изображения и аналитика

До удаления карточки получить принадлежащие ей ключи объектов. В транзакции удаления сохранить задания `object_storage_deletion_jobs`; обработчик начинает удалять файлы только после коммита. Очередь содержит UUID задания, `entity_type`, `entity_id`, `object_key`, `status` (`pending`, `processing`, `completed`, `failed`), `attempts`, `last_error`, `scheduled_at`, `processed_at`, `created_at`.

Обработчик использует существующую инфраструктуру фоновых задач. Удаление отсутствующего файла считается успешным. Сбой хранилища оставляет карточку удалённой, фиксирует `failed` и ошибку; предусмотреть ограниченные повторные попытки и восстановление зависших заданий. Не удалять общие изображения справочников или объекты, которыми ещё пользуется другая сущность. Повторная обработка не должна приводить к удалению посторонних объектов.

Для каждого успешно удалённого автомобиля публикуется событие `_deleted: true` в Kafka; в ClickHouse записывает только event-worker. Обеспечить восстановимую доставку после коммита: событие не должно потеряться из-за остановки процесса между удалением и отправкой. При реализации сначала проверить доступные механизмы устойчивой доставки и переиспользовать подходящий; не вводить новый общий фреймворк. Ни внешнее удаление файлов, ни публикация события не выполняются до успешного коммита. Фоновая ошибка не превращает уже зафиксированное удаление в ложный rollback.

## 9. Критерии готовности

1. Администратор видит три новые операции; остальные роли не видят их, а прямые вызовы всех новых API, включая GET, дают 403. Без аутентификации — 401.
2. Автомобиль без блокеров получает `can_delete = true`; каждая группа из раздела 3.1 отдельно приводит к `false` с корректной причиной и количеством. Несколько связей показываются одновременно.
3. Отменённый заказ, избранное, корзина и связь в массиве истории расчётов блокируют удаление наравне с остальными зависимостями.
4. Только история перемещений и привязка к складу не блокируют удаление. После успешного DELETE удалены карточка, история и привязка; склад и справочники сохранены.
5. Отсутствующее или неверное подтверждение не отправляет запрос из UI, а прямой API-вызов получает 400. Для массового удаления слово проверяется также backend.
6. Связь, появившаяся после GET, сохраняет автомобиль: одиночный DELETE даёт 409, массовый сценарий пропускает его с актуальной причиной. Проверена защита также для связей без FK.
7. Техническая ошибка внутри одиночного или массового удаления откатывает изменения операции; аналитика и удаление файлов не запускаются для откатившихся данных.
8. «Отвязать все» снимает все привязки только выбранного склада, включая невидимые страницы и строки вне фильтра. Карточки, история и значимые связи сохраняются. Число в ответе фактическое; повтор даёт 0.
9. Предварительная массовая сводка учитывает весь склад, считает уникальные автомобили и агрегирует причины без двойного учёта в `blocked_count`.
10. «Удалить все» на смешанном наборе удаляет разрешённые автомобили, оставляет заблокированные на складе без изменений и возвращает полный список пропусков. Итоговые количества согласованы.
11. Повторное массовое удаление при отсутствии разрешённых автомобилей возвращает 200 и 0. Автомобили другого склада не затронуты.
12. Повторный клик во время запроса заблокирован. После успеха обновлены строки, страницы и счётчики; при отказе показаны причины, при сбое предварительной проверки действие недоступно.

17. Новые unit-тесты не написаны. Существующие проверки сохранены; выполнены обязательные команды, интеграционные/API-проверки критических сценариев, Docker-запуск и ручная браузерная приёмка.

### 11.3. Валидация и целостность

- Ограничение файла 20 MiB, максимум 1000 витрин; неверный JSON, повторные ключи, NaN/Infinity, неверные типы/slug, неизвестные поля/ключи видимости и недопустимые цвета/контакты отклоняются до записи. Пустой словарь отклоняется с понятной ошибкой.
- Используются существующие доменные валидаторы настроек и логотипов. Нельзя скрыть выбранную главную страницу. Логотипы только JPEG/PNG/WebP, максимум 5 MiB на оригинал, MIME проверяется по содержимому. Никаких загрузок по URL из файла.
- Весь пакет БД — одна транзакция, без промежуточных commit. Конкурентные изменения повторно проверяются под блокировками. Логотипы предварительно размещаются под новыми неизменяемыми ключами, старые объекты не перезаписываются и не удаляются до commit; ошибка не должна менять действующие ссылки/настройки.
