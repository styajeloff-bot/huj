# Видимость разделов по витринам

## Контекст

- Задача является внутренней и не связана с Bitrix.
- Раздел `/workspace/section-visibility` сейчас хранит одну глобальную матрицу
  области `public`; она одновременно применяется к основной витрине `/` и ко
  всем дополнительным витринам.
- Витрины уже имеют независимые склады, featured-настройки, branding и
  storefront-aware публичные маршруты, но видимость разделов пока не входит в
  storefront scope.
- Личный кабинет клиента является частью публичной витрины и доступен как
  `/cabinet` или `/{slug}/cabinet`.
- Служебный `/workspace/*` остаётся глобальным. При переходе в него из
  дополнительной витрины контекст возврата сейчас теряется: логотип workspace
  ведёт на `/`.
- Каталог спецтехники не имеет storefront-scoped API и маршрутов
  `/{slug}/special-equipment`; поэтому он намеренно недоступен внутри
  дополнительных витрин.

## Цель

Сотрудник CarCraft должен настраивать публичные разделы отдельно для основной
и каждой дополнительной витрины. Новая витрина получает снимок эффективных
настроек основной витрины и после создания изменяется независимо.

При переходе из дополнительной витрины в глобальный workspace система должна
сохранить исходную витрину и использовать её для ссылок возврата на публичный
сайт, не создавая маршруты вида `/{slug}/workspace`.

## Функциональные требования

### Публичная видимость по витринам

- Для каждой витрины хранить независимую матрицу области `public`:
  - «О нас»;
  - «Каталог автомобилей»;
  - «Модели»;
  - «Каталог транспортных средств и специальной техники».
- Основная витрина `/` сохраняет текущие эффективные значения после миграции.
- Каждая уже существующая дополнительная витрина при миграции получает полный
  снимок эффективных настроек основной витрины.
- При создании новой витрины полный снимок эффективных публичных настроек
  основной витрины сохраняется в той же транзакции, что и витрина.
- Последующие изменения основной витрины не изменяют дополнительные витрины и
  наоборот.
- Для дополнительной витрины переключатель спецтехники всегда выключен и
  недоступен для изменения. В интерфейсе рядом показывается причина: каталог
  спецтехники пока не поддерживает изоляцию по витринам.
- Даже если основная витрина в момент копирования показывает спецтехнику,
  дополнительная витрина получает для этого раздела значение `false`.
- Отсутствующая настройка или временная ошибка публичного API используют
  существующие безопасные frontend-дефолты; ошибка одной витрины не должна
  загрязнять кэш другой.

### Административный экран

- В области «Публичный сайт» добавить выбор витрины из существующего
  административного списка: «Основная витрина (/)» и дополнительные `/{slug}`.
- Неактивные витрины остаются доступными для настройки и явно помечаются как
  неактивные.
- Переключение между витринами не теряет несохранённые черновики; состояние
  загрузки, сохранения и ошибки ведётся относительно выбранной витрины.
- Сохраняется только матрица выбранной витрины.
- Области «Администратор», «Лизинговая компания», «Дилер» и «Дистрибьютор»
  остаются глобальными и не зависят от выбранной публичной витрины.
- Если workspace открыт из дополнительной витрины, она первоначально выбирается
  на вкладке «Публичный сайт»; при прямом входе используется основная витрина.

### Публичное применение

- Основная витрина получает свою матрицу через root public endpoint.
- Дополнительная витрина получает матрицу через endpoint со slug витрины.
- Header и остальные уже управляемые поверхности используют матрицу текущей
  витрины, а не одну глобальную запись `public` в Pinia.
- Неизвестный или неактивный slug остаётся fail-closed и возвращает `404` до
  отображения публичной страницы.
- Настройка видимости управляет визуальными входами и не заменяет авторизацию
  или scoped API.

### Возврат из workspace

- При переходе пользователя из `/{slug}` или `/{slug}/*` в `/workspace/*`
  сохранить валидированный slug как явный контекст возврата.
- Контекст должен сохраняться между внутренними переходами workspace и после
  обновления страницы, не смешиваться между вкладками браузера и быть видимым
  в URL как query-параметр.
- Центральный middleware переносит контекст возврата между маршрутами
  `/workspace/*`; отдельные страницы не должны вручную добавлять slug.
- Логотип sidebar и все существующие или будущие ссылки «На сайт» используют
  единый helper и ведут в `/{slug}`, если контекст задан, иначе в `/`.
- Невалидный, неизвестный или неактивный slug удаляется из контекста, после
  чего ссылки ведут в основную витрину.
- Маршруты workspace и его API остаются глобальными: `/{slug}/workspace` не
  создаётся, данные workspace не фильтруются по витрине.

## Планируемый технический контракт

### Backend

- Расширить `section_visibility` ссылкой `storefront_id` на
  `catalog_storefronts`.
- Для `public` требовать `storefront_id`; для workspace-областей запрещать его
  check-constraint-ом.
- Обеспечить независимую уникальность публичных записей по
  `storefront_id + section_key` и глобальных записей по `scope + section_key`.
- Миграцией привязать текущие public overrides к основной витрине и
  материализовать полный эффективный снимок для существующих дополнительных
  витрин с принудительно скрытой спецтехникой.
- Root public endpoint возвращает матрицу основной витрины; добавить scoped
  public endpoint для `/{storefront_slug}`.
- Добавить admin GET/PATCH resource матрицы по UUID витрины. Текущие
  административные контракты областей workspace остаются глобальными и больше
  не принимают `public` без storefront UUID.
- При создании витрины копировать public matrix основной витрины в одной
  транзакции.

### Frontend

- Ключевать публичное состояние видимости идентификатором витрины, сохранив
  отдельные глобальные матрицы workspace-ролей.
- Загружать публичную матрицу после разрешения storefront context и выбирать
  root либо slug-scoped API.
- Расширить административный экран выбором витрины только для public-области и
  хранить черновики по UUID витрины.
- Добавить единый workspace return-context helper и middleware с сохранением
  query-параметра на всех `/workspace/*` переходах.
- Перевести workspace-ссылки на публичный сайт на единый helper.

## Тестирование

### Backend

- Доменная валидация сочетаний `scope + storefront_id` и запрет изменения
  спецтехники у дополнительной витрины.
- Изоляция чтения и записи public matrix между двумя витринами.
- Root и slug public endpoints, включая неизвестный и неактивный slug.
- Создание витрины копирует эффективную матрицу основной и не получает её
  последующие изменения.
- Миграция проверяется на состояниях без overrides, с частичными public
  overrides и с несколькими существующими витринами.
- Upgrade, downgrade и повторный upgrade миграции проходят на PostgreSQL.

### Frontend

- Public API и Pinia не переиспользуют матрицу другой витрины.
- Административный selector, независимые черновики и сохранение выбранной
  витрины.
- Спецтехника заблокирована только у дополнительных витрин.
- Переход `/faw/* -> /workspace/*`, внутренняя workspace-навигация, refresh и
  возврат логотипом сохраняют `/faw`.
- Прямой `/workspace/*` и невалидный return-context возвращают на `/`.
- Архитектурный тест запрещает точечное добавление slug в отдельных
  workspace-страницах вместо общего helper/middleware.

## Критерии готовности

- Изменение публичного переключателя основной витрины не меняет `/faw`, и
  изменение `/faw` не меняет `/`.
- Новая витрина сразу повторяет текущую публичную видимость основной, кроме
  всегда скрытой спецтехники, и затем живёт независимо.
- На `/faw` header и прочие управляемые поверхности используют матрицу `faw`.
- В `/workspace/section-visibility` сотрудник выбирает витрину для области
  «Публичный сайт»; остальные области остаются глобальными.
- Workspace, открытый из `/faw`, сохраняет контекст при навигации и refresh, а
  логотип возвращает в `/faw`.
- Не появляются `/faw/workspace` и storefront-фильтрация служебных данных.
- Backend-тесты, линтеры, mypy, import-linter, frontend architecture tests,
  Docker-сборка/запуск и просмотр логов выполнены перед MR.
- MR создаётся только в `test`; после создания спецификация переименовывается в
  `specs/<номер-MR>.md`.

## Границы

- Не добавлять storefront-scoped каталог спецтехники в рамках этой задачи.
- Не делать workspace-ролевую видимость зависимой от витрины.
- Не вводить наследование видимости после создания витрины.
- Не создавать mobile-only UI или сценарии для viewport меньше 768 пикселей.
