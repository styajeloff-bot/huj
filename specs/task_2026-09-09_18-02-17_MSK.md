# Bitrix #22006 — раздельные PDF-файлы для предварительного и итогового КП

- **Задача:** https://carcraftpro.bitrix24.ru/workgroups/group/124/tasks/task/view/22006/
- **Ветка:** `bugfix/22006-pdf-slots`
- **Статус:** ожидает согласования

## Текущее поведение

Предыдущее исправление по задаче #22006 уже находится в `test`: лизинговая компания может отправить итоговое КП без предварительного.

При этом в ответе лизинговой компании существует только один общий PDF-слот `response_pdf_*`:

- обе формы — «Предварительное КП» и «Итоговое КП» — используют один и тот же файл;
- загрузка нового PDF в одной форме заменяет ранее загруженный файл из другой;
- в интерфейсе отображается только имя файла, без ссылки для открытия;
- данные PDF находятся на уровне ответа ЛК, а не конкретного типа КП.

## Целевое поведение и причина

Каждое КП должно иметь собственный PDF-документ:

- у предварительного КП можно загрузить, заменить, удалить и открыть только его PDF;
- у итогового КП можно загрузить, заменить, удалить и открыть только его PDF;
- загрузка файла для одного типа КП не влияет на файл второго типа;
- после загрузки рядом с именем файла отображается синяя ссылка «Посмотреть», открывающая PDF в новой вкладке;
- прежнее правило из #22006 сохраняется: итоговое КП допускается без предварительного.

Это исключает потерю документов и позволяет лизинговой компании, клиенту и другим авторизованным участникам открыть именно тот документ, который относится к выбранному КП.

## Подходы и решение

### Рекомендуемый подход: хранить PDF в записи конкретного КП

1. Добавить в `leasing_proposals` отдельные поля ключа объектного хранилища, имени, размера и времени загрузки PDF.
2. Добавить только новые поля миграцией без удаления старого общего `response_pdf_*`: из старой модели невозможно достоверно определить тип файла. Исторический файл сохраняется как архивный, а все новые upload/delete операции работают только с PDF конкретного КП.
3. Изменить upload, delete и download API так, чтобы они принимали `kind` (`preliminary` или `final`), проверяли права ЛК и работали только с соответствующим КП.
4. Возвращать метаданные PDF вместе с каждым КП в состоянии ответа ЛК и в клиентском представлении ответа.
5. Разделить состояние и обработчики на странице кабинета ЛК: каждая форма получает PDF своего `kind`.
6. Показать имя загруженного файла как синюю ссылку «Посмотреть», открывающую защищённый backend-маршрут в новой вкладке. Прямая ссылка на S3 не выдаётся.

### Альтернативы

- **Оставить один файл и только подписать его тип.** Не подходит: один документ продолжит заменять другой.
- **Хранить оба файла на уровне `leasing_company_applications`.** Возможно, но модель будет хуже отражать предметную область и усложнит выдачу/проверки, потому что файлы относятся к КП, а не к ответу целиком.

## Планируемые изменения

### Backend

- Добавить Alembic-миграцию и поля PDF к модели и сущности `LeasingProposal`.
- Обновить репозиторий КП для сохранения, удаления и выдачи метаданных PDF конкретного `kind`.
- В `application/commands/leasing_response.py` выделить безопасные команды загрузки, удаления и получения PDF конкретного КП. Сохранить текущие ограничения: только PDF, не пустой, до 10 МБ, только владелец ЛК и только пока КП редактируемо.
- В `presentation/routers/leasing.py` добавить маршруты upload/delete/download с параметром `kind`; download возвращает PDF с `Content-Type: application/pdf` и `Content-Disposition: inline` после проверки доступа.
- Обновить схемы и запросы состояния/клиентских ответов: у каждого КП появляются собственные `pdf_file_name`, `pdf_file_size`, `pdf_uploaded_at` и ссылка/маршрут просмотра, если файл есть.
- Добавить интеграционные регрессии: два разных PDF сохраняются и выдаются раздельно; замена/удаление предварительного не затрагивает итоговый; доступ не выдаётся чужой ЛК; маршрут просмотра возвращает корректный PDF.

### Frontend

- Обновить типы и API-клиент лизинга для параметра `kind` и отдельной PDF-метаинформации каждого КП.
- В `pages/workspace/leasing-applications/[id]/index.vue` передавать в форму PDF выбранного КП и вызывать upload/delete только для соответствующего `kind`.
- В `LeasingProposalForm.vue` показывать рядом с именем файла синюю гиперссылку «Посмотреть» с открытием в новой вкладке и безопасными `target="_blank"` / `rel="noopener noreferrer"`.
- В клиентском блоке ответов ЛК показывать файлы рядом с соответствующим предварительным или итоговым КП, а не один общий файл на карточке ответа.

## Критерии готовности

- ЛК может отправить итоговое КП без создания или отправки предварительного — сценарий #22006 не регрессирует.
- При наличии обоих КП ЛК загружает разные PDF в предварительное и итоговое КП; после обновления страницы каждое КП показывает собственное имя файла.
- Замена или удаление PDF предварительного КП не меняет файл итогового, и наоборот.
- В каждом месте, где PDF доступен пользователю, есть синяя ссылка «Посмотреть», открывающая именно этот PDF в новой вкладке.
- Маршрут просмотра не раскрывает ключ объектного хранилища, требует действующей авторизации и не позволяет ЛК получить файл другой ЛК.
- Новые PDF-метаданные возвращаются в API только для соответствующего КП; общий файл больше не используется для новых загрузок.
- Пройдут новые backend-интеграционные тесты, проверки `ruff`, `lint-imports`, `mypy`, релевантные frontend architecture-тесты, `bun run test:arch`, production build и Docker-проверка с просмотром логов.
- MR создаётся из `bugfix/22006-pdf-slots` строго в `test` и содержит ссылку на Bitrix #22006.

## Вопросы и границы

- **Неблокирующий вопрос:** ранее загруженный общий файл нельзя достоверно классифицировать как предварительный или итоговый. Он не будет автоматически перенесён в один из новых слотов; новые файлы сразу сохраняются раздельно.
- В задачу не входят изменение условий КП, повторная реализация уже влитого перехода «итоговое без предварительного», перенос файлов между ЛК и открытый публичный доступ к документам.
