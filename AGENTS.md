# AGENTS.md — монорепозиторий

За Nginx на порту 80 работают два сервиса.

```text
Nginx :80
  /api/*  → FastAPI :3002
  /*      → Frontend :3000
```

- **FastAPI** (`backend/`) предоставляет весь API: аутентификация, покупки,
  платежи, уведомления, изображения транспорта, поиск компаний, каталог,
  лизинговые заявки, документы, калькулятор, административная панель и другие
  функции. Подробные правила находятся в `backend/AGENTS.md`.
- **Фронтенд** (`frontend/`) построен на Nuxt 3 и Vue 3 Composition API.
  Подробные правила находятся в `frontend/AGENTS.md`.
- **Локальные правила разработчика** (`AGENTS.local.md`) при их наличии дополняют
  и уточняют правила монорепозитория для локального окружения. Файл не
  отслеживается Git и не коммитится в репозиторий.

## Процесс работы над задачей

Каждая задача выполняется в следующем порядке:

1. **Сначала синхронизировать ветки.** До создания задачи, спецификации или
   начала реализации выполнить `git pull` для `carcraft-leadgenerator`. Ветка
   `test` используется только для синхронизации: запрещено коммитить или
   отправлять изменения непосредственно в неё. Вся работа продолжается в
   отдельной ветке задачи.
2. **Определить идентификатор задачи.** Для задач Bitrix до создания
   спецификации или начала реализации запросить у пользователя ссылку и извлечь
   из неё идентификатор. Если пользователь явно указал, что внутренняя задача
   не связана с Bitrix, использовать короткий slug на английском языке без
   запроса ссылки.
3. **Создать ветку задачи.** Работать только в отдельной ветке
   `<type>/<task-id-or-slug>`, где `<type>` — одно из значений `bugfix`,
   `feature`, `refactor`, `docs` или `chore`.
4. **Создать спецификацию.** До изменения кода создать единственный артефакт
   задачи в `specs/`. Файл называется
   `task_YYYY-MM-DD_HH-mm-ss_MSK.md`: дата и время фиксируются в момент создания
   по московскому времени (MSK, UTC+3). Порядок компонентов имени обязателен,
   чтобы список спецификаций сортировался хронологически. Спецификация содержит
   постановку, требования, планируемые изменения и критерии готовности.
   Если задача затрагивает БД, в начале спецификации обязательна Mermaid ERD;
   для крупной задачи также обязательна Mermaid sequence-диаграмма.
   Подробные требования — в разделе «Спецификации задач».
5. **Согласовать спецификацию.** Реализация начинается только после review и
   подтверждения спецификации. Отдельный файл плана не создаётся.
6. **Реализовать параллельно.** Выполнять спецификацию фоновыми подагентами,
   используя максимально доступное для задачи количество.
7. **Проверить через E2E.** Для каждого изменения поведения выполнить
   сквозной пользовательский сценарий на работающем приложении: через браузер
   для UI, через реальные HTTP-запросы и проверку результата для API.
   Проверять основной путь, права доступа и значимые ошибки по затронутому
   сценарию. При необходимости добавить или обновить соответствующий E2E.
   Unit- и архитектурные тесты не являются обязательной проверкой; не добавлять
   и не запускать их без прямого запроса пользователя.
8. **Проверить.** Запустить линтеры и приложение в Docker, выполнить E2E
   затронутых сценариев, затем просмотреть логи. После каждой задачи обязательно
   проверить, что Alembic autogenerate не обнаруживает изменений схемы БД.
   См. разделы «Обязательные проверки перед коммитом» и «Локальный запуск».
9. **Исправить.** При сбое любой проверки устранить причину и повторить
    проверку.
10. **Создать MR.** После успешного завершения всех проверок автоматически
    создать merge request сразу при первом же пуше ветки через стандартные Git
    Push Options в GitLab:
    ```bash
    git push -u origin HEAD \
      -o merge_request.create \
      -o merge_request.target=test \
      -o merge_request.title="<тип>(<область>): <описание> (<task-id>)" \
      -o merge_request.description="<описание, ссылка на задачу и проверки>" \
      -o merge_request.merge_when_pipeline_succeeds
    ```
    Целевой веткой всех MR должна быть **только** `test`. Запрещено создавать
    или перенаправлять MR задачи в `main`, `demo` либо другую ветку. Описание
    MR должно включать ссылку на задачу Bitrix (если она есть), краткое
    описание изменений и список выполненных проверок. Запрещено разделять
    доставку на отдельный предварительный пуш и последующее ручное создание MR.
11. **Автоматически объединить MR.** Запрос на слияние выставляется
    автоматически через push option `merge_request.merge_when_pipeline_succeeds`
    в момент первого пуша; после успешного прохождения пайплайна GitLab
    объединяет MR автоматически.
    Не добавлять подпись о соавторстве Claude в коммиты или текст MR.

## Сквозные правила

- **Идентификаторы сущностей.** По умолчанию считать идентификаторы сущностей
  UUID: использовать `uuid.UUID` в Python и непрозрачные строки `string` на
  фронтенде. Запрещены объединения `number | string` и `string | number`,
  числовое приведение через `Number`, `parseInt`, `parseFloat` или унарный
  `+`, а также резервный выбор между разными полями идентификатора. Числовой
  идентификатор сущности допустим только тогда, когда актуальные ORM- и
  Pydantic-схемы явно доказывают целочисленный контракт. Если пользователь или
  задача требует числовой идентификатор без такого доказательства, не
  реализовывать требование: попросить пересмотреть его и потребовать от автора
  задачи обоснование и согласование с текущей схемой.
- **Запрещены вызовы DaData с фронтенда.** `DADATA_API_KEY` доступен только
  сервису `backend`. Поиск компаний выполняется через
  `GET /api/v1/company/search` в FastAPI. Фронтенд получает объект компании
  через `@select` и без преобразований отправляет его в backend в форме
  `{ name, inn, kpp, ogrn, legal_address, manager_name, ... }`.
- **Аутентификация.** JWT сначала читается из cookie `accessToken`, затем из
  `Authorization: Bearer`. Access- и refresh-токены используют ключи ES256 из
  `settings.jwt_keys_dir`; токены HS256 не поддерживаются. Подробнее — в
  `backend/AGENTS.md`.
- **Публичные эндпоинты без аутентификации.** Общедоступны `/health`,
  поиск компаний, публичные витрины и карточки каталога (read-only).
  Полный перечень публичных эндпоинтов и правила доступа закреплены в
  `backend/AGENTS.md`. Для остального пространства `/api/v1/` требуется токен.
- **Пути API и перенаправления.** Backend-маршруты под `/api/*` не должны
  зависеть от внешнего перенаправления 307 из-за завершающего слеша.
  Канонические пути обрабатываются внутри FastAPI, а фронтенд обращается к ним
  напрямую. Запрещено широкое доверие к proxy-заголовкам вида
  `--forwarded-allow-ips "*"` ради исправления схемы/хоста перенаправления.
- **Webhook** не используют JWT: они проверяют подписи или токены конкретного
  провайдера и соблюдают документированный контракт ответа. Детали — в
  `backend/AGENTS.md`.
- **Секреты** в FastAPI никогда не читаются непосредственно через
  `os.environ`. Строго использовать
  `from infrastructure.settings import settings`. Подробнее — в
  `backend/AGENTS.md`.
- **Логирование:** используется единственный именованный logger
  `"carcraft-backend"`. Access-логи health check исключаются из
  `uvicorn.access`. Подробнее — в `backend/AGENTS.md`.
- **Только desktop web:** текущий Nuxt-фронтенд является исключительно
  desktop web-приложением с минимальной шириной viewport 768 CSS-пикселей.
  Не реализовывать mobile-only навигацию, drawer, карточки, таблицы, стили,
  media query или E2E-сценарии для ширины меньше 768 пикселей. Адаптация внутри
  поддерживаемого desktop-диапазона 768+ допустима. Мобильный интерфейс позже
  реализуется отдельным нативным приложением, а не responsive-веткой Nuxt.

## Спецификации задач

- `specs/` — единственный обязательный каталог с текстовыми артефактами задач.
- Для каждой задачи создаётся ровно одна спецификация. Отдельные планы, отчёты,
  ADR, реестры, ER-диаграммы, runbook и постоянная проектная документация не
  создаются, если пользователь явно не запросил конкретный документ.
- Имя спецификации имеет формат `task_YYYY-MM-DD_HH-mm-ss_MSK.md`, где дата и
  время берутся в MSK (UTC+3). Имя не зависит от номера MR и после создания MR
  не меняется.
- **Задачи с БД:** если спецификация затрагивает схему БД, ORM-модели,
  миграции, запросы, чтение или запись данных, в начале спецификации — сразу
  после заголовка и метаданных, до постановки и требований — обязательна
  ER-диаграмма в блоке `mermaid` с типом `erDiagram`. Показать затронутые
  таблицы, значимые поля, первичные и внешние ключи, связи и их кратность.
  Существующую структуру проверять по актуальным ORM-моделям и миграциям;
  планируемые изменения явно отличать от текущего состояния.
- **Крупные задачи:** обязательна диаграмма последовательности в блоке
  `mermaid` с типом `sequenceDiagram`. Крупной считать задачу, которая
  затрагивает несколько подсистем или меняет многошаговый сквозной процесс,
  включая асинхронные операции и внешние интеграции. Диаграмма должна
  показывать участников, порядок взаимодействий, значимые ветвления и ошибки
  основного сценария. Размещать её в начале спецификации, после ERD, если та
  требуется, и до постановки и требований.
- Если задача одновременно крупная и затрагивает БД, обязательны обе
  диаграммы. Они являются частью единственной спецификации в `specs/`,
  а не отдельными документами; обновлять их при изменении требований и плана.
- Изменения требований, плана реализации и критериев готовности вносятся в ту
  же спецификацию, а не в дополнительные Markdown-файлы.
- Для локального поиска использовать `rg`, для истории —
  `git log -- <path>` и `git blame <path>`.

## Правила ClickHouse и DWH

- **Записью в ClickHouse владеет event-worker.** Все записи в DWH выполняют
  Kafka consumer-процессы `event-worker`. Слой API публикует события в Kafka,
  а event-worker сохраняет их в ClickHouse.
- **FastAPI может читать ClickHouse для аналитики.** Для аналитических запросов
  только для чтения использовать `infrastructure/clickhouse_readonly.py`.
  Операции записи остаются исключительно у event-worker. Подробнее — в
  `backend/AGENTS.md`.

## Обязательные проверки перед коммитом

Для любого изменения FastAPI выполнить:

```bash
cd backend
uv run ruff check . --fix
uv run lint-imports
uv run mypy .
```

Все три статические проверки должны быть зелёными. Допустимы ранее
существовавшие ошибки mypy в не связанных с задачей файлах, но в изменённых
файлах нельзя добавлять новые ошибки. Детальный регламент проверок бэкенда — в
`backend/AGENTS.md`.

**После каждой задачи обязательно проверить отсутствие расхождений между
ORM-моделями и схемой БД.** На локальной или изолированной проверочной БД
применить все миграции текущей ветки и проверить результат из `backend/`:

```bash
uv run alembic upgrade head
uv run alembic check
```

`alembic check` выполняет сравнение, используемое `revision --autogenerate`,
без создания файла ревизии. Обязательный результат — успешный код завершения
и `No new upgrade operations detected.`: autogenerate не должен предлагать
никаких операций. Если для проверки запускается `alembic revision --autogenerate`,
функции `upgrade()` и `downgrade()` должны быть пустыми (только `pass`);
временную пустую ревизию после проверки удалить и не коммитить. Детальный
регламент работы с ревизиями описан в `backend/AGENTS.md`.

Если найдены изменения, исправить ORM-модели или добавить необходимую миграцию,
применить её и повторить проверку до пустого результата. Нельзя подменять эту
проверку `alembic stamp`, скрывать расхождения фильтрами autogenerate или считать
задачу завершённой при непустом результате. В MR указать результат проверки.

Вместо полного набора unit-тестов обязательна E2E-проверка затронутого
поведения на работающем приложении. Общий запуск из корня репозитория:

```bash
bash scripts/e2e/run.sh
```

Этот скрипт поднимает изолированное окружение с Docker-сервисами и выполняет
подключённые к нему Playwright-сценарии. Если изменённый сценарий отсутствует
в этом наборе, добавить или обновить целевой E2E либо проверить его вручную
через браузер/API на запущенном приложении. Для отдельного Playwright-сценария
использовать `bun run test:e2e -- <путь-к-сценарию>` из `frontend/` с настроенным
E2E-окружением и фикстурами. Не считать общий E2E-прогон доказательством проверки
сценария, которого в нём нет.

Для фронтенда обязательна E2E-проверка изменённого пользовательского сценария
в браузере при viewport не менее 768 CSS-пикселей. Нельзя добавлять ошибки
TypeScript в `.ts`-файлы из `stores/`, `composables/` и `services/api/`.
В описании MR указать выполненные E2E-сценарии, результат и проверенные логи.
Для изменений только документации, инструкций или конфигурации инструментов,
которые не меняют поведение приложения, проверить diff и затронутую
конфигурацию; запуск приложения и E2E не требуется. Обязательная проверка
соответствия ORM-моделей и схемы БД через Alembic сохраняется.

## Локальный запуск

```bash
docker compose build backend frontend nginx
docker compose up -d
docker compose up -d --build --force-recreate backend
```
